01 · Agent Framework 是什么

Microsoft Agent Framework（MAF）是一个用 Python 和 .NET 编写的开源框架， 帮你把"大语言模型（LLM）"接进真实应用，并编排成能干活的 Agent 和多 Agent 工作流。 它不替你训练模型，而是负责模型周边的所有管道，并面向生产环境。

🔌 生活类比
把大语言模型想成一台很强但很孤立的发动机：它能输出文字，却不知道你的数据库、 不会自己调用工具，不同厂商的接口还都不一样。MAF 就是那套标准化的"传动系统 + 仪表盘 + 配件接口"—— 让你用同一套代码驱动任何品牌的发动机，把它接到工具、记忆、其他 Agent 上，还能在生产里监控、重启、审批。

它到底解决什么问题？

直接调用某个厂商的 SDK 当然能跑，但真实应用里你很快会撞上这几类麻烦，正是 MAF 要替你抹平的：

痛点没有框架时MAF 的做法
厂商锁定换模型要重写一大片调用代码统一的 ChatClient + Agent，换厂商基本只改一行
对话拼装手动拼 role/content 的字典结构化的 Message / Role / Content
调用工具自己解析模型要调哪个函数、传什么参@tool 自动生成 schema + 解析 + 执行
多步 / 多 Agent手写"想—做—再想"循环和协作逻辑Agent 循环 + 图式 Workflows 编排
上生产自己搞监控、持久化、人工审批内置 OpenTelemetry、检查点、人在环、托管

最小的一个 Agent 长什么样

samples/01-get-started/01_hello_agent.py最小示例
from agent_framework import Agent
from agent_framework.foundry import FoundryChatClient
from azure.identity import AzureCliCredential

client = FoundryChatClient(
    project_endpoint="https://your-project.services.ai.azure.com",
    model="gpt-4o", credential=AzureCliCredential(),
)
agent = Agent(
    client=client, name="HelloAgent",
    instructions="You are a friendly assistant. Keep your answers brief.",
)

result = await agent.run("What is the capital of France?")
print(result)

三步：选一个 ChatClient（连到某个模型）→ 包成一个 Agent（给名字和系统指令）→ run 一句话。 换厂商？把 FoundryChatClient 换成 OpenAIChatClient 即可，其余不动。

1 它和 LangChain / AutoGen / Semantic Kernel 什么关系？ 点击展开
❓ 一句话定位
MAF 是微软把 Semantic Kernel（企业级、强类型、连接器丰富）和 AutoGen（多 Agent 对话与研究探索）合并演进而来的统一框架， 目标是"从原型到生产"一条路走到底，且 Python 与 .NET 双实现、API 对齐。
✅ 它的取舍
既要 LangGraph 那样的图式编排（可控、可恢复），又要 AutoGen 那样的多 Agent 协作， 还把可观测性 / 持久化 / 审批做成一等公民——这就是"生产级"的含义。
2 厂商锁定怎么破？ 点击展开详解
🧪 示例
直接用各家 SDK，写法各不相同： 
# OpenAI
from openai import OpenAI
client = OpenAI()
r = client.chat.completions.create(model="gpt-4o", messages=[...])

# Anthropic
from anthropic import Anthropic
client = Anthropic()
r = client.messages.create(model="claude-3-7-sonnet", max_tokens=1024, messages=[...])
换成 MAF 之后，只换一个 client，其余代码不动： 
from agent_framework import Agent
from agent_framework.openai import OpenAIChatClient
# from agent_framework.anthropic import AnthropicClient  # 改这一行就够了
agent = Agent(client=OpenAIChatClient(model="gpt-4o"), instructions="…")
await agent.run("你好")
❓ 为什么这件事必要
三个非常现实的理由：
① 成本：同一任务在不同模型上价格相差 5–20 倍；
② 模型迭代极快：每个季度都有新模型登顶榜单，被锁死意味着踩不上红利；
③ 合规与可用性：金融 / 政府要求私有部署，海外业务要走 Foundry，国内可能要走自研网关。
✅ MAF 的做法与优点
MAF 把所有厂商抽象成统一的 ChatClient 接口， FoundryChatClient / OpenAIChatClient / AnthropicClient / OllamaChatClient 全部实现同一组方法 （get_response() / get_streaming_response()）。 Agent、工具、工作流只依赖接口，"换一行 import"即可切换厂商。
🔀 还有什么其他方案
① LiteLLM：外部代理服务，所有请求走 OpenAI 协议——简单但多一跳网络与运维。
② 自己写适配层：能拿到最贴合业务的接口，但要自己维护流式、工具、函数调用的差异。
③ 云厂商网关（Azure AI Gateway / AWS Bedrock）：合规与配额统一，缺点是仍被云厂商锁住。
3 对话消息怎么"拼"才不出错？ 点击展开详解
🧪 示例
裸字典 vs MAF 的类型化消息： 
# 裸字典——拼错 role 直到运行时才报错
messages = [
  {"role": "sytsem", "content": "你是助手"},  # 拼写错了！
  {"role": "user",   "content": "你好"},
]

# MAF——类型受控，IDE 自动补全
from agent_framework import Message
messages = [
  Message("system", "你是助手"),
  Message("user", "你好"),
]
❓ 为什么这件事必要
真实业务里消息绝不只是字符串：还有图像、工具调用、工具结果、思维链、引用等"内容块"。 裸字典每加一种就要全工程改 if/else；用类型化的 Contents， 新内容只是多一个 Content 类型，老代码完全不动。
✅ MAF 的做法与优点
见 agent_framework/_types.py：Role 是枚举 （system / user / assistant / tool），Message 持有 contents: list[Contents]，Contents 是 Content 统一类型，用 Content.from_text() 等工厂方法构造。 好处：① 静态检查 + 补全；② 多模态 / 工具结果自然容纳；③ Workflow 跨进程序列化零成本。
🔀 还有什么其他方案
① 裸字典 + JSON Schema 校验：轻量但运行时才报错；
② Pydantic 自建模型：MAF 内部就是 Pydantic v2，自己写等于重造轮子；
③ LangChain 的 HumanMessage / AIMessage：思路相同，但内容块远不如 MAF 全面。
4 工具调用为什么不要手写 JSON？ 点击展开详解
🧪 示例
裸 function calling vs MAF 的 @tool： 
# 裸 SDK：自己写 schema、自己 dispatch、自己回灌
tools = [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "parameters": {"type": "object",
      "properties": {"city": {"type": "string"}},
      "required": ["city"]}}}]
# 后续：解析 tool_calls → 找函数 → 调用 → 把结果塞回 messages → 再发一次……

# MAF：装饰器自动生成 schema，自动跑循环
from agent_framework import tool

@tool
def get_weather(city: str) -> str:
    "返回城市天气。"
    return f"{city} 今天 23°C"

agent = Agent(client=client, tools=[get_weather])
❓ 为什么这件事必要
手写 JSON Schema 最容易出三类 bug：① 参数名/类型与函数实际签名不一致； ② 改函数忘了改 schema；③ 各家厂商对 schema 子集支持不同。 自动生成意味着函数即文档、函数即合同，重构成本接近零。
✅ MAF 的做法与优点
@tool（见 _tools.py）借助 inspect + 类型注解生成 JSON Schema，自动注入到 ChatClient 请求； 模型返回 FunctionCallContent 时，Agent 在同一个循环里 执行函数、把 FunctionResultContent 追加回消息，再次请求模型——你不用写一行胶水。
🔀 还有什么其他方案
① 手写 schema：最大可控、最大错率；
② OpenAI 官方 function calling SDK：仅限 OpenAI 系；
③ LangChain Tool / StructuredTool：思路类似，缺乏与中间件、Workflow 的统一集成；
④ MCP 协议：工具跨进程托管，MAF 也支持把 MCP 工具当本地工具用。
5 多步 / 多 Agent 怎么不变成 while 怪兽？ 点击展开详解
🧪 示例
手写循环很快就会脏掉： 
messages = [...]
while True:
    resp = client.chat.completions.create(model=..., messages=messages, tools=tools)
    msg = resp.choices[0].message
    if not msg.tool_calls:
        break
    for tc in msg.tool_calls:
        result = dispatch(tc.function.name, json.loads(tc.function.arguments))
        messages.append({"role": "tool", ...})
    # 没限次数、没异常兜底、没观测点……

# MAF：交给 agent.run() / Workflow
agent = Agent(client=client, tools=[get_weather, search_web])
result = await agent.run("先查上海天气再给我推荐衣服")
❓ 为什么这件事必要
"循环"听着简单，工程化以后要处理：最大迭代数、异常重试、上下文裁剪、并发工具、 中间件埋点（trace / cost）、多 Agent 之间的消息路由、可恢复的检查点…… 每一项自己实现都是几百行代码、上百个测试用例。
✅ MAF 的做法与优点
单 Agent 用内置循环（含 DEFAULT_MAX_ITERATIONS、 中间件管道、流式聚合）；多 Agent 用 agent_framework._workflows 提供的图式编排（节点 / 边 / 共享状态 / 检查点 / 人审）， 和 LangGraph 思想接近，但与 ChatClient、工具、可观测性原生贯通。
🔀 还有什么其他方案
① LangGraph：图式编排鼻祖，与 LangChain 生态深度绑定；
② CrewAI：角色化多 Agent，编程模型轻但工程化能力弱；
③ 手写状态机 / Temporal / Durable Functions：稳定但与 LLM 语义脱节，要再造一遍工具循环。
✅ 关键要点
  • MAF = ChatClient（连模型）+ Agent（循环）+ Tools（工具）+ Workflows（编排）+ 生产能力。
  • 它不训练模型，负责模型周边的全部管道；Python 和 .NET 双实现。
  • 定位：Semantic Kernel + AutoGen 的统一继任者，从原型直达生产。
💡 设计亮点
把"换模型只改一行"做成默认体验：ChatClient 是厂商无关的统一抽象， Agent / 工具 / 工作流全部构建在它之上，于是可移植性从第一行代码就免费获得。

02 · Monorepo 全景

MAF 是一个 monorepo：一个仓库里同时放着 Python 和 .NET 两套实现，外加文档、声明式 Agent 和 schema。理解了目录结构，你就有了一张源码导航地图。

🏢 生活类比
把仓库想成一座办公楼：core 是地基与承重墙（所有人都依赖）， 各 provider 包是不同楼层的部门（OpenAI 部、Anthropic 部……）， lab 是顶楼的实验室（前沿但不稳定）。Python 楼和 .NET 楼并排而立，户型一致。

1 core 包里到底有什么？ 点击展开详解
🧪 示例
core 一个文件一个职责，地图大致如下： 
python/packages/core/agent_framework/
├── _agents.py        # Agent 类、run() 循环、DEFAULT_MAX_ITERATIONS
├── _clients.py       # BaseChatClient 抽象基类 + Supports* 协议族
├── _tools.py         # @tool 装饰器、FunctionTool 类
├── _middleware.py    # 中间件管道：trace / retry / 自定义
├── _types.py         # Message / Role / Contents 联合类型
├── _workflows/       # 图式编排：节点、边、共享状态、检查点
├── observability/    # OpenTelemetry trace / cost / token 指标
└── __init__.py       # 公共 API，决定 from agent_framework import 什么
❓ 为什么这件事必要
如果 core 拆成几十个小包，新人要在第一周里学几十个 import 路径； 如果塞成一个 god-module，又会出现循环依赖、加载慢、测试难。 "单包多文件"是大型框架最常见且最稳的折中：一个 import 路径、清晰的内部分层。
✅ MAF 的做法与优点
所有抽象统一从 agent_framework 导出（Agent、 Message、tool、 WorkflowBuilder……）；文件命名以 _ 前缀表示"内部"， 通过 __init__.py 的 __all__ 再暴露—— 重构内部不影响用户代码。
🔀 还有什么其他方案
① 单文件 god-module：上手最快，长期维护灾难；
② 微包架构（每个抽象一个 PyPI 包）：依赖管理噩梦；
③ plugin-only：core 只有接口，所有实现都是插件——灵活但缺少"开箱即用"的体验。
2 provider 包的懒加载是怎么工作的？ 点击展开详解
🧪 示例
子模块 __init__.py 用 __getattr__ 延迟拉依赖： 
# agent_framework/azure/__init__.py（示意）
import importlib
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from ._chat_client import AzureOpenAIChatClient

_LAZY = {"AzureOpenAIChatClient": "._chat_client"}

def __getattr__(name: str):
    if name in _LAZY:
        mod = importlib.import_module(_LAZY[name], __name__)
        return getattr(mod, name)
    raise AttributeError(name)

__all__ = list(_LAZY)
所以 import agent_framework 不会拉起 azure-identity； 只有真的访问 AzureOpenAIChatClient 时才装载。
❓ 为什么这件事必要
① 启动速度：每多一个 SDK 启动就慢几十到几百毫秒，CLI / Serverless 场景极敏感；
② 可选依赖：用户只装了 OpenAI 包，不应该被 Anthropic 的 import 错误打断；
③ 安装体积：core 保持最小依赖，按需安装 extras（pip install agent-framework[azure]）。
✅ MAF 的做法与优点
采用 PEP 562 的模块级 __getattr__ + TYPE_CHECKING 守护的真实 import，对 IDE 与 mypy 完全友好；既保留懒加载，又能拿到完整类型提示。 Pyright/PyCharm 都能正确跳转。
🔀 还有什么其他方案
① 急加载（eager）：简单，但启动慢、依赖污染；
② entry_points / 插件协议：解耦得更彻底，但发现成本和调试难度上升；
③ try / except ImportError：常见小技巧，规模一大就乱。
3 Python 与 .NET 是怎么"对齐"的？ 点击展开详解
🧪 示例
同一个概念，两种语法： 
# Python
from agent_framework import Agent
from agent_framework.openai import OpenAIChatClient
agent = Agent(
    client=OpenAIChatClient(model="gpt-4o"),
    name="weather-bot",
    instructions="你是天气助手",
)
await agent.run("上海明天天气？")
// C#
using Microsoft.Agents.AI;
using Microsoft.Agents.AI.OpenAI;

var agent = new ChatClientAgent(
    chatClient: new OpenAIChatClient("gpt-4o"),
    name: "weather-bot",
    instructions: "You are a weather assistant");
var result = await agent.RunAsync("Weather in Shanghai?");
❓ 为什么这件事必要
真实企业里：算法 / 数据团队偏 Python，业务后端常是 .NET。 如果两边概念不一样，团队沟通靠翻译，文档要写两份，迁移代价巨大。 "API 对齐"意味着看一份文档能让两边都开工。
✅ MAF 的做法与优点
两套实现在概念、命名、生命周期上对齐：同样的 Agent / ChatClient / Tool / Workflow， 同样的 run / stream / observability hook；只在语法上接受各自语言的惯用法（async/await、 装饰器 vs Attribute、强类型 vs 类型注解）。
🔀 还有什么其他方案
① 只做一种语言：错过另一半市场；
② 从 IDL / proto 自动生成：易过度抽象，丢掉语言惯用法；
③ FFI / 包装（Python 调 .NET DLL 或反过来）：部署与诊断复杂。

第一部分 · 宏观全景

03 · 一次 run() 的生命周期

你写的只是 await agent.run("…") 一行，但底下发生了一串事。 看懂这条生命周期，后面所有"内部源码"课都会变得轻松。

🍽️ 生活类比
Agent 像一位餐厅服务员：你点单（输入）→ 他把你的话连同"店规"（instructions）整理成标准工单（消息） → 递进后厨（ChatClient → LLM）→ 如果厨师说"需要先去仓库取货"（工具调用），服务员就去取（执行工具）再把结果回递 → 直到厨师出菜（最终回答），服务员端给你（AgentResponse）。

一次 run 的完整数据流

1

你的输入

字符串或一组 Message，连同会话历史一起进来。

2

Agent 组装

把 instructions（系统提示）+ 历史 + 新输入 + 可用 tools 拼成一次请求。

3

ChatClient 调用

厂商无关接口把请求发给具体 LLM（Foundry / OpenAI / …），拿回 ChatResponse。

4

要调工具吗？

若响应里含 function_call，Agent 执行对应函数，把 function_result 追加进消息，再回到第 3 步。

5

收敛与返回

当模型不再要工具，循环结束，得到 AgentResponse（流式则是一串 AgentResponseUpdate）。

🌍 宏观理解
这就是经典的 Agent 循环（think → act → observe）：模型"想"，框架替它"做"（调工具）， 把"观察"喂回去，直到任务完成。你只调用一次 run()，循环在内部自动跑完。
1 多轮对话时历史从哪来？ 点击展开
🧪 示例
把同一个 会话（session）传给连续的 run，历史会自动累积： 
from agent_framework import Agent
agent = Agent(client=client, instructions="…")
session = agent.create_session()
await agent.run("我叫小明", session=session)
await agent.run("我叫什么？", session=session)  # 记得"小明"
（会话与记忆见第 07 课，这里只需知道历史是"会话"携带的。）
2 消息到底是怎么组装的？ 点击展开详解
🧪 示例
一次 run() 实际发给 LLM 的列表大致长这样： 
[
  SystemMessage("你是天气助手，回答尽量简短。"),   # ← instructions
  UserMessage("我叫小明"),                       # ← 历史 1
  AssistantMessage("你好，小明！"),               # ← 历史 2
  UserMessage("上海今天天气？"),                  # ← 本次输入
]
tools = [
  {"name": "get_weather",  "parameters": {...}},  # ← 自动生成
]
其中 instructions 在最前、历史按时间顺序、当前输入在最后、工具 schema 作为请求字段并行附带。
❓ 为什么这件事必要
三个隐藏陷阱：① system 位置——某些模型对 system 必须放首； ② 上下文窗口预算——历史 + 工具 schema + 输入加起来不能超 token 上限； ③ 工具 schema 开销——20 个工具就能吃掉几千 token。
✅ MAF 的做法与优点
Agent 在 _agents.py 中按固定顺序拼装： instructions → system、tools → schema、 history → ordered messages，并把 ChatClient 不支持的内容（如多模态）做 fallback。 用户只关心业务输入，组装细节由框架兜底。
🔀 还有什么其他方案
① 完全手动拼装：最灵活，最容易踩坑；
② 模板化（Jinja / Handlebars）：适合 prompt-engineering 重度场景，但失去类型约束；
③ 纯中间件流水线：把每一步当 middleware 拼起来，灵活但调试链路长。
3 工具循环的边界在哪？ 点击展开详解
🧪 示例
Agent 内置了一个迭代上限，撞到就停： 
# agent_framework/_agents.py
DEFAULT_MAX_ITERATIONS = 10

class Agent:
    def __init__(self, ..., max_iterations: int = DEFAULT_MAX_ITERATIONS):
        self.max_iterations = max_iterations

    async def run(self, input, ...):
        for i in range(self.max_iterations):
            resp = await self._client.get_response(...)
            if not _has_tool_calls(resp):
                return AgentResponse(...)
            await self._execute_tools(resp)
        # 达到上限：返回带告警的部分结果
        return AgentResponse(..., terminated_reason="max_iterations")
按需调高：Agent(..., max_iterations=20)。
❓ 为什么这件事必要
没有上限的循环 = 账单炸弹：模型可能把同一个工具反复调用、互相依赖死锁、 或被 prompt injection 牵着鼻子走。即便用例正常，也要有止损线。
✅ MAF 的做法与优点
默认 DEFAULT_MAX_ITERATIONS 给出安全值，可按 Agent 覆写； 终止时返回结构化的 terminated_reason，方便上层判断"重试 / 升级 / 报错"， 而不是直接 raise。
🔀 还有什么其他方案
① 不设上限：极端危险；
② 按 token 预算：更经济但实现复杂；
③ 按墙钟超时：保护延迟敏感场景；
④ 每步人工确认：成本最高但安全（金融 / 医疗常用），MAF 也可通过 Workflow 的 human approval 实现。
4 流式 vs 非流式内部差异 点击展开详解
🧪 示例
同一个 Agent，两种入口： 
# 非流式：一次性拿完整结果
result: AgentResponse = await agent.run("写一首关于秋天的诗")
print(result.text)

# 流式：逐块拿 AgentResponseUpdate
async for update in agent.run_stream("写一首关于秋天的诗"):
    if update.text:
        print(update.text, end="", flush=True)
❓ 为什么这件事必要
① 首字延迟：长回答里用户最敏感的是"开始出字"的时间；
② 长回答 UX：不流式时，等 30s 一片黑屏；流式则像打字机；
③ 调试与中断：流式可早期发现跑偏，及时取消。
✅ MAF 的做法与优点
同一个 Agent、同一组工具，run() 返回完整 AgentResponse； run_stream() 返回 AsyncIterable[AgentResponseUpdate]， 把内容、工具调用、思维块都分块吐出，且内部已对齐为同一种循环—— 切换流式不需要重写业务逻辑。
🔀 还有什么其他方案
① 纯 SSE 推流：协议简单，但要自己实现重连和心跳；
② WebSocket：双向通信，对实时交互更好；
③ 轮询：兼容性最强，体验最差；
④ 客户端缓冲：在前端把 chunk 拼回完整文本，MAF 同时支持。
5 错误处理：循环里出错怎么办？ 点击展开详解
🧪 示例
三类典型故障： 
# 1) LLM 端报错：429 / 500 / timeout
   → ChatClient 抛出 ChatClientError

# 2) 工具函数抛异常
@tool
def get_weather(city: str) -> str:
    raise RuntimeError("weather API down")
   → Agent 捕获后包成 FunctionResultContent(error=...)
     交回模型，让它决定降级、换工具或道歉

# 3) 工具执行超时
   → 中间件层兜底，写入 trace span
❓ 为什么这件事必要
Agent 循环里出错时，"重试 / 跳过 / 放弃 / 返回部分结果"的取舍每种都合理， 没有银弹。框架必须给一个有结构、可定制的失败模型，否则要么过度吞错、要么动不动崩溃。
✅ MAF 的做法与优点
错误走中间件管道（_middleware.py）：用户可注册重试策略、 熔断、降级；工具异常被包成 FunctionResultContent 回灌模型； 无法恢复时 AgentResponse 上带 terminated_reason 和原始异常链，便于上层结构化处理。
🔀 还有什么其他方案
① 到处 try/except：写起来快，可观测性几乎为零；
② 熔断器（circuit breaker）：保护下游，但要小心误熔断；
③ let-it-crash（Erlang 风格）：失败重启整个 Agent，靠上游 retry——简单但成本高。
✅ 关键要点
  • 一次 run() = 组装消息 → 调 LLM →（按需循环调工具）→ 返回 AgentResponse。
  • 工具调用是循环，不是一次性：模型可以多次要工具。
  • 流式版本逐块返回 AgentResponseUpdate，最终拼成完整响应。
💡 设计亮点
循环被封装在框架里：调用方只看到"输入→输出"，而"想—做—再想"的复杂度被 Agent 吸收， 这正是它比裸调 LLM SDK 省心的根源。
第二部分 · 用户视角

04 · 消息与内容

和模型对话，本质是来回传递一串消息。MAF 把消息做成结构化对象 Message，而不是裸字典——类型更安全，还能携带工具调用、图片等多种内容。

✉️ 生活类比
一条 Message 像一个信封：信封上写着寄件人身份（role： user / assistant / system / tool），信封里可以装多张内容卡片（contents： 一段文字、一张图、一次工具调用、一份工具结果……）。

三个核心类型

类型作用来自
Message一条消息 = role + contents_types.py
Role身份："system"/"user"/"assistant"/"tool"_types.py
Content统一内容类型，用工厂方法构造_types.py

手拼 dict vs 结构化消息

😣 裸字典

messages = [
  {"role": "system", "content": "你是助手"},
  {"role": "user", "content": "你好"},
]
# key 容易拼错，工具调用要手搓

🙂 Message 对象

from agent_framework import Message
messages = [
  Message("system", "你是助手"),
  Message("user", "你好"),
]
# 类型安全，可带多种 Content

Message 的第二个参数 contents 接受字符串（自动转成文本内容）、 Content 对象，或它们的列表。读文本用 msg.text。

1 Content 能装哪些东西？ 点击展开详解
🧪 示例
Content 是统一类型，用类方法创建不同种类： 
Content.from_text("一段文字")
Content.from_data(data=..., media_type="image/png")  # 图片/二进制
Content.from_uri(uri="https://…", media_type="image/png")
Content.from_function_call(...)      # 模型要调工具
Content.from_function_result(...)    # 工具执行结果
所以一条 Message 可以图文混排，也能承载工具调用 / 结果。
❓ 为什么这件事必要
LLM 能力已超出"纯文本问答"：GPT-4o、Claude支持图像输入，模型可请求调用工具并接收结果。如果每种内容用不同字段（text、image_url、tool_calls……），消息结构变复杂、不可扩展。统一成 Content 列表后，代码只关心"一条消息有多个内容块"，不必为每种类型特殊处理。
✅ MAF 的做法与优点
MAF 用判别联合（discriminated union）：每个 Content 都有 type 字段（"text"/"data"/"uri"/"function_call"/"function_result"），框架按 type 路由。新增内容类型（如视频、音频）只需加一个新 type，老消息仍能正常处理。类型安全由 Pydantic 保证，IDE 有完整提示。
🔀 还有什么其他方案
  • OpenAI SDK：text 放 content 字段，图像放 content 列表，工具调用放 tool_calls 字段——三种形态不一致，解析时需要分支判断。
  • Anthropic：采用 content 数组 + type 区分，与 MAF 类似，但每个厂商格式不同。
  • MAF 把各家统一成一套，跨厂商代码零修改。
2 Message 的构造方式 点击展开详解
🧪 示例
# 纯文本（字符串自动包装）
msg = Message("user", "你好")

# 单个 Content 对象
msg = Message("user", Content.from_text("你好"))

# 多个 Content：图文混排
msg = Message("user", [
    Content.from_text("这张图是什么？"),
    Content.from_uri(uri="https://example.com/img.png", media_type="image/png")
])

# 读取文本快捷方式
text = msg.text  # 自动从 contents 中提取文本
❓ 为什么这件事必要
多模态对话越来越常见：用户发一张图 + 一段问题；模型回复文本 + 图表；工具调用与工具结果也要和文本混排在同一条消息里。如果 Message 只能装一个字符串，需要拆成多条消息或手拼复杂结构。允许异构内容列表后，一条消息能自然表达"文字 + 图 + 工具调用"。
✅ MAF 的做法与优点
Message 的 contents 参数接受：
  • 字符串：自动转 Content.from_text(...)
  • 单个 Content：原样包装成列表
  • Content 列表：直接存储
同时提供 .text 属性，自动拼接所有文本内容（多个 text content时用空格连接）。用户可按需简单或复杂使用，心智模型统一。
🔀 还有什么其他方案
  • OpenAI：文本消息 vs 多内容消息用不同格式（{role, content: "str"} vs {role, content: [{type, ...}]}），工具调用另加 tool_calls 数组。框架需判断格式再解析。
  • LangChain：HumanMessage/AIMessage 各自不同构造函数。
  • MAF 统一构造函数，类型安全 + IDE提示 + 多模态开箱即用。
3 工具调用如何融入消息流 点击展开详解
🧪 示例
# 模型输出：assistant 消息带 function_call
msg_call = Message("assistant", [
    Content.from_function_call(
        name="get_weather",
        arguments={"location": "Seattle"},
        call_id="call_abc123"
    )
])

# 框架回灌：role="tool" 消息带 function_result
msg_result = Message("tool", [
    Content.from_function_result(
        name="get_weather",
        result="Sunny, 72°F",
        call_id="call_abc123"
    )
])
# 这两条追加进对话历史，模型继续生成最终答案
❓ 为什么这件事必要
工具调用是多轮交互：
  1. 模型决定"需要工具"，输出 function_call
  2. 框架执行工具，拿到结果
  3. 框架把结果追加进对话，模型读取后产出最终答案
如果工具调用/结果不是标准消息，就需要单独管道。把它们纳入 Message 后，整个对话就是一条消息链，无需特殊逻辑。
✅ MAF 的做法与优点
Content.from_function_call 和 .from_function_result 是两种特殊内容类型，完全融入消息体系：
  • 类型统一：工具调用 = assistant 消息 + function_call content；工具结果 = tool 消息 + function_result content。
  • 序列化一致：历史回放、日志、调试时，工具调用和普通消息用相同JSON结构。
  • 可扩展：未来加"并行工具调用"只需在一条消息的 contents 里放多个 function_call。
🔀 还有什么其他方案
  • OpenAI：assistant 消息加 tool_calls 数组，tool 消息用 role="tool" + tool_call_id。需两套字段。
  • Anthropic：content 数组里放 tool_use / tool_result 块，和 MAF思路接近，但每家格式不同。
  • MAF 抹平差异：开发者用统一API，框架负责转换各厂商格式。
4 序列化与反序列化 点击展开详解
🧪 示例
# 消息 → 字典（可JSON序列化）
msg = Message("user", "Hello")
d = msg.to_dict()
# → {"role": "user", "contents": [{"type": "text", "text": "Hello"}]}

# 字典 → 消息（从JSON恢复）
msg_restored = Message.from_dict(d)
assert msg_restored.role == "user"
assert msg_restored.text == "Hello"

# 工具调用也能完整序列化
msg_with_tool = Message("assistant", [
    Content.from_function_call(name="foo", arguments={"x": 1})
])
d2 = msg_with_tool.to_dict()
msg_back = Message.from_dict(d2)  # 完全恢复
❓ 为什么这件事必要
实际应用需要：
  • 持久化：把对话历史存到数据库（Redis、Cosmos、PostgreSQL）。
  • 回放调试：记录生产环境的消息流，本地重现问题。
  • 审计日志：合规要求保存所有对话（含工具调用）。
  • 跨服务传递：微服务间传递消息上下文。
如果不能无损序列化，工具调用、图像等复杂内容会丢失信息。
✅ MAF 的做法与优点
Message.to_dict() / from_dict(...) 是完全可逆的：
  • 所有 Content 类型（text/data/uri/function_call/function_result）都能无损序列化。
  • 返回的字典是纯 JSON，可直接存储、传输、日志。
  • Pydantic 模型自动处理类型验证，反序列化时类型错误会抛异常。
  • 第三方持久化库（如 redis、azure-cosmos）可直接存字典。
🔀 还有什么其他方案
  • OpenAI SDK：原生消息已是字典，但格式每版本可能变，没有类型保证。
  • LangChain：Message.dict() 返回嵌套结构，字段名不稳定，需自己处理。
  • 手工JSON：完全自定义，但schema演进时容易破坏兼容性。
  • MAF schema有版本管理，升级框架时老数据能自动迁移（见 _types.py 的兼容层）。

  • 厂商锁定：切换到 Anthropic/Ollama/Azure 需大量改动。

  • 无类型安全：拼写错误运行时才报错。

抽象层让你写一次，到处运行。

MAF 提供统一抽象，但双向转换能力齐全：
  • BaseChatClient 子类（如 OpenAIChatClient）内部自动把 Message 转成厂商格式，调完API再转回来。
  • 转换逻辑封装在客户端内部（私有方法 _prepare_messages_for_openai，见 python/packages/openai/agent_framework_openai/_chat_client.py），一般无需手动调用。
  • 类型安全：IDE 自动补全 Message(...) / Content.from_...，编译期发现错误。
  • 可测试：单元测试不依赖真实 LLM，mock Message 即可。
🔀 还有什么其他方案
  • 直接用 SDK dict：零抽象，换厂商需全盘重构。
  • LangChain MessageType：提供抽象，但HumanMessage/AIMessage/ToolMessage 分类过细，增加心智负担。
  • LlamaIndex ChatMessage：简单统一，但功能有限，多模态/工具调用支持弱。
  • MAF 恰到好处：一个 Message + 五种 Content，涵盖所有场景，各厂商无缝切换。
✅ 关键要点
  • 对话 = 一串 Message；每条 = role + contents。
  • Role 有四种：system / user / assistant / tool。
  • Content 是统一类型，用 from_text/from_data/from_function_call… 构造。
💡 设计亮点
把"文本、图片、工具调用、工具结果"统一成一种 Content，靠 type 字段区分。 消息结构因此既简单又可扩展——新增一种内容不破坏老代码。

05 · ChatClient 与创建 Agent

ChatClient 是"连到某个模型"的厂商无关接口；Agent 在它之上加了 名字、系统指令、工具和循环。本课讲怎么从 ChatClient 造出 Agent，并用 run 跑起来。

🎧 生活类比
ChatClient 像对讲机：能和某个频道（模型）通话，但不带"人设"。 Agent 像拿着对讲机、并被交代了岗位职责（instructions）和工具的值班员——你对值班员说话，他负责完成任务。

两种创建方式

方式 A：Agent(client=…)

from agent_framework import Agent
agent = Agent(
  client=client,
  name="HelloAgent",
  instructions="You are friendly.",
)

方式 B：client.as_agent(…)

agent = client.as_agent(
  name="HelloAgent",
  instructions="You are friendly.",
)
# 等价，更顺手

两种都行；as_agent 读起来更顺。底下都是同一个 Agent。

跑起来：run 与流式

非流式 vs 流式
# 非流式：一次拿到完整回答
result = await agent.run("What is the capital of France?")
print(result)

# 流式：逐块拿到 token
async for chunk in agent.run("Tell me a fun fact.", stream=True):
    if chunk.text:
        print(chunk.text, end="", flush=True)

同一个 run()：不传 stream 返回完整 AgentResponse； 传 stream=True 返回一个异步迭代器，逐块给 AgentResponseUpdate。

🔬 换厂商
把 FoundryChatClient 换成 OpenAIChatClient、 AnthropicChatClient、OllamaChatClient……Agent 那层一行都不用改。 各 client 来自对应 provider 包（见第 16 课）。
1 as_agent vs Agent(client=...) 两种创建方式 点击展开详解
🧪 示例
# 方式 A：直接构造
agent_a = Agent(
    client=client,
    name="MyAgent",
    instructions="You are helpful."
)

# 方式 B：语法糖
agent_b = client.as_agent(
    name="MyAgent",
    instructions="You are helpful."

# 两者完全等价
assert type(agent_a) == type(agent_b)  # 都是 Agent
❓ 为什么这件事必要
真实场景中，你可能先创建 ChatClient（配置好模型、API密钥、重试策略），然后基于它创建多个 Agent（不同人设、不同工具）。两种方式都需要支持：
  • Agent(client=...)：适合"Agent 是主角"的场景，显式依赖注入。
  • client.as_agent(...)：适合"client 是主角"的场景，链式调用更自然。
单一方式会让某些代码风格别扭。
✅ MAF 的做法与优点
as_agent 是语法糖，内部调用 Agent(client=self, ...)（见 python/packages/core/agent_framework/_clients.py 的 BaseChatClient.as_agent 方法）。两种方式返回同一类型的对象，行为完全一致。用户可根据上下文选择：
  • 测试时 mock Agent：Agent(client=mock_client, ...)
  • 配置多个 Agent：agents = [client.as_agent(...) for cfg in configs]
框架不强加风格，但保证语义统一。
🔀 还有什么其他方案
  • LangChain：没有 as_agent 模式，需手动包装 ChatOpenAI 到 AgentExecutor。
  • Semantic Kernel：使用 Kernel 作为容器，Agent 概念较弱。
  • OpenAI Assistants API：Agent 是服务端对象，无本地构造。
  • MAF 两种方式都支持，语法糖降低入门门槛，直接构造保留灵活性。
2 run() 的参数 点击展开详解
🧪 示例
# 最简：只传消息
result = await agent.run("你好")

# 带会话：多轮对话
session = agent.create_session()
result = await agent.run("我叫 Alice", session=session)
result = await agent.run("我叫什么？", session=session)

# 流式：逐块返回
async for chunk in agent.run("讲个故事", stream=True):
    print(chunk.text, end="")

# 组合：会话 + 流式
async for chunk in agent.run("继续", session=session, stream=True):
    print(chunk.text, end="")
❓ 为什么这件事必要
Agent 的使用场景多样：
  • 一次性查询：无状态，只需要答案（如 FAQ bot）。
  • 多轮对话：需要记住上文（如客服、助手）。
  • 流式响应：实时显示生成过程（UX 需求）。
  • 组合：多轮 + 流式（如聊天应用）。
如果每种场景用不同方法（run、run_with_session、run_stream……），API 膨胀且学习成本高。统一成一个 run()，用可选参数控制行为，更简洁。
✅ MAF 的做法与优点
run() 签名：
async def run(
    self,
    message: str | Message,
    session: AgentSession | None = None,
    stream: bool = False,
    ...
) -> AgentResponse | AsyncIterator[AgentResponseUpdate]:
  • 必需参数只有 message，其他都是可选。
  • session 默认 None：不传则无状态，传了则多轮。
  • stream 默认 False：阻塞返回完整结果；True 时返回异步迭代器。
  • 返回类型由 stream 决定：类型检查器（mypy、Pylance）能推断出正确类型。
🔀 还有什么其他方案
  • OpenAI SDK：create(...) vs create(..., stream=True)，但 Assistants API 另有 runs.create。
  • LangChain：invoke、ainvoke、stream、astream 四个方法。
  • Anthropic SDK：messages.create vs messages.stream。
  • MAF 一个方法，参数控制行为，心智负担最小。
3 流式的内部机制 点击展开详解
🧪 示例
async for chunk in agent.run("写首诗", stream=True):
    print(f"type={chunk.type}")      # "text_delta" / "tool_call" / "final"
    print(f"text={chunk.text}")      # 本块的文本增量
    print(f"is_final={chunk.is_final}")  # 是否最后一块
    
    if chunk.is_final:
        print(f"full_response={chunk.response}")  # 完整 AgentResponse
❓ 为什么这件事必要
流式响应不只是"打字机效果"：
  • 降低感知延迟：首字延迟（TTFT）比总耗时更重要。
  • 长输出场景：生成几百上千 token 时，用户等不及完整响应。
  • 中途取消：用户看到方向不对，立刻停止（节省成本）。
  • 实时处理：边生成边解析（如实时翻译、代码高亮）。
只返回原始文本流不够：需要知道"工具调用开始""最终完成"等事件，才能正确更新 UI。
✅ MAF 的做法与优点
MAF 的流式返回 AgentResponseUpdate 对象（见 python/packages/core/agent_framework/_types.py）：
  • type 字段："text_delta"（文本增量）/ "tool_call"（工具调用）/ "final"（结束）。
  • text 字段：本块新增的文本。
  • is_final：True 时是最后一块，.response 属性包含完整 AgentResponse。
  • 元数据：usage（token 消耗）、finish_reason（停止原因）等。
框架自动累积文本、解析工具调用、处理多轮循环，用户只需 async for 消费。
🔀 还有什么其他方案
  • OpenAI SDK：返回 SSE 事件流，用户需手动解析 delta、累积文本、判断结束。
  • Anthropic SDK：MessageStream 对象，事件类型多（content_block_start、content_block_delta……），学习曲线陡。
  • LangChain：astream 返回原始 chunk，格式取决于底层 LLM。
  • MAF 统一 Update 对象，抹平厂商差异，高层语义（"文本增量""工具调用""完成"）清晰。
4 多个 Agent 共享一个 client 点击展开详解
🧪 示例
client = FoundryChatClient(model="gpt-4o", api_key=...)

    name="WeatherBot",
    instructions="You are a weather assistant.",
    tools=[get_weather]

    name="Translator",
    instructions="Translate to French."

    instructions="Answer user questions.",
    tools=[search_kb, create_ticket]

# 三个 Agent 复用同一个 HTTP 连接池、API 密钥
❓ 为什么这件事必要
生产环境常见场景：
  • 多角色系统：一个应用有多个 Agent（路由员、执行员、审核员），都调用同一个模型。
  • 连接池：HTTP/2 支持多路复用，一个 TCP 连接可并发多个请求。每个 Agent 独立建连接浪费资源。
  • 配置复用：API 密钥、重试策略、超时时间只配置一次。
  • 监控 / 限流：所有请求走同一个 client，便于统一埋点、限流。
如果 Agent 和 ChatClient 耦合（每个 Agent 内部创建 client），无法共享连接。
✅ MAF 的做法与优点
ChatClient 是无状态的（见 BaseChatClient）：
  • 不持有对话历史（历史在 AgentSession 里）。
  • 只负责"发请求 → 解析响应"，可被多个 Agent 并发调用。
  • 内部用 httpx.AsyncClient（Python）或 HttpClient（.NET），自动管理连接池。
  • 线程安全（或异步安全）：多个 await agent.run(...) 可并发执行。
这种设计让资源利用率最高，也符合依赖注入原则（Agent 依赖 ChatClient 抽象）。
🔀 还有什么其他方案
  • 每个 Agent 内部创建 client：简单但浪费。OpenAI Assistants API 是服务端 Agent，不存在此问题。
  • 全局单例 client：难以测试、难以配置不同环境。
  • LangChain：ChatOpenAI 可共享，但文档不强调，用户容易每次新建。
  • MAF 明确设计：client.as_agent(...) 的语法就暗示"多个 agent 共享一个 client"。
✅ 关键要点
  • ChatClient = 连模型（厂商无关）；Agent = ChatClient + 人设 + 工具 + 循环。
  • 创建：Agent(client=…) 或 client.as_agent(…)，二选一。
  • run() 默认完整返回；run(stream=True) 逐块流式返回。
💡 设计亮点
流式与非流式共用一个 run()，靠一个 stream 开关切换返回形态。 调用心智统一，省掉两套 API。

06 · 工具 Tools

工具（Tool）让 Agent 不只是"会说"，还能"会做"：查天气、读数据库、调 API。 你写一个普通 Python 函数，用 @tool 一标，模型就能调用它。

🧰 生活类比
模型像个聪明但手短的大脑：它知道"该查天气了"，但自己摸不到温度计。 工具就是你递给它的一件件趁手家伙，并附上说明书（函数签名 + docstring），它照着说明书使用。

定义一个工具

samples/01-get-started/02_add_tools.py
from typing import Annotated
from agent_framework import Agent, tool
from pydantic import Field

@tool(approval_mode="never_require")
def get_weather(
    location: Annotated[str, Field(description="The location to get weather for.")],
) -> str:
    """Get the weather for a given location."""
    return f"It's sunny in {location}."

agent = Agent(client=client, name="WeatherAgent",
    instructions="Use get_weather to answer.",
    tools=[get_weather])

result = await agent.run("What's the weather in Seattle?")

三件事自动发生

1

生成 schema

从函数签名 + Annotated[..., Field(description=…)] + docstring 自动生成 JSON Schema，交给模型。

2

模型决定调用

模型在回答里产出一个 function_call（函数名 + 参数）。

3

框架执行并回灌

Agent 调用你的函数，把 function_result 追加进对话，再让模型继续。

⚠️ 审批模式
approval_mode="never_require" 仅为示例图省事——生产中应使用 "always_require"，在工具执行前要求人工确认（尤其是写操作 / 花钱的操作）。
1 schema 自动生成原理 点击展开详解
🧪 示例
from typing import Annotated
from agent_framework import tool
from pydantic import Field

@tool(approval_mode="never_require")
def search_products(
    query: Annotated[str, Field(description="Search keywords")],
    max_results: Annotated[int, Field(description="Max results to return", ge=1, le=10)] = 5
) -> list[dict]:
    """Search for products in the catalog."""
    ...

# 自动生成的 JSON Schema：
# {
#   "name": "search_products",
#   "description": "Search for products in the catalog.",
#   "parameters": {
#     "type": "object",
#     "properties": {
#       "query": {"type": "string", "description": "Search keywords"},
#       "max_results": {"type": "integer", "description": "Max results...", "minimum": 1, "maximum": 10, "default": 5}
#     },
#     "required": ["query"]
#   }
# }
❓ 为什么这件事必要
模型需要JSON Schema 才能理解工具签名：参数名、类型、约束、含义。手写 schema 的问题：
  • 易出错：字段名拼错、类型不匹配、忘记更新 description。
  • 双重维护：函数签名改了，schema 要同步改，容易漏。
  • 无类型检查：schema 和代码脱节，调用时参数不对只能运行时才发现。
自动生成让类型注解 = 单一事实来源，函数签名即契约。
✅ MAF 的做法与优点
MAF 用 Pydantic 自动生成 schema（见 python/packages/core/agent_framework/_tools.py 的 ToolDefinition.from_function）：
  • 类型注解 → type 字段（str → "string"，int → "integer"……）。
  • Field(description=...) → description 字段。
  • Field(..., ge=1, le=10) → minimum/maximum 约束。
  • 默认值 → default 字段，非必需参数。
  • Docstring → 工具的 description。
IDE 自动补全、类型检查器（mypy）验证调用，schema 与代码永远同步。
🔀 还有什么其他方案
  • 手写 JSON Schema：OpenAI SDK 早期做法，容易出错、维护成本高。
  • LangChain @tool：也用 Pydantic，但对复杂类型（嵌套对象、联合类型）支持弱。
  • OpenAI function calling JSON：需手动构造 {"name": ..., "parameters": {...}}，无类型保证。
  • MAF 完全自动：支持泛型、嵌套、可选参数、约束，生成的 schema 符合各厂商规范。
2 approval_mode 三种值 点击展开详解
🧪 示例
@tool(approval_mode="never_require")
def get_time() -> str:
    """Get current time (safe, always auto-execute)."""
    return datetime.now().isoformat()

@tool(approval_mode="always_require")
def send_email(to: str, subject: str, body: str) -> str:
    """Send an email (requires human approval)."""
    ...  # 框架会在执行前要求确认

@tool(approval_mode="always_require")
def create_ticket(title: str, priority: str) -> str:
    """Create a support ticket (low-priority auto, high requires approval)."""
    ...  # 可自定义风险评估逻辑
❓ 为什么这件事必要
工具能力各异，风险不同：
  • 只读查询（查天气、搜索）：无副作用，可自动执行。
  • 写操作（发邮件、删文件、转账）：有副作用，必须人工确认。
  • 灰色地带（创建草稿、添加备注）：低风险可自动，高风险需确认。
如果所有工具都自动执行（never_require），模型一个幻觉就可能发错邮件、删错数据。如果所有工具都要确认（always_require），用户体验糟糕（查个天气也要点确认）。需要分级控制。
✅ MAF 的做法与优点
MAF 的 approval_mode（见 python/packages/core/agent_framework/_tools.py）：
  • "never_require"：无需确认，自动执行（默认）。
  • "always_require"：每次都弹出确认对话框 / 回调，用户批准后才执行。
审批流程由 approval logic 接口定义（见 _tools.py），可自定义（如接入 Slack 审批机器人、钉钉审批流）。框架在工具执行前自动拦截，无需在工具函数内写审批逻辑。
🔀 还有什么其他方案
  • LangChain HumanApprovalCallbackHandler：通过回调实现，但需手动注册到每个 Agent，容易漏。
  • 手动在工具内判断：if dangerous: ask_user(); ...，把审批逻辑和业务逻辑耦合。
  • OpenAI function calling：无内置审批，需应用层拦截 function_call 自行处理。
  • MAF 声明式审批：@tool(approval_mode=...) 一行搞定，审批逻辑与工具解耦，可插拔策略。
3 异步工具 点击展开详解
🧪 示例
import httpx

# 同步工具（阻塞 I/O）
@tool(approval_mode="never_require")
def get_weather_sync(city: str) -> str:
    """Get weather (blocks event loop)."""
    resp = httpx.get(f"https://api.weather.com?q={city}")  # 阻塞！
    return resp.json()["temp"]

# 异步工具（非阻塞）
@tool(approval_mode="never_require")
async def get_weather_async(city: str) -> str:
    """Get weather (async, doesn't block)."""
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"https://api.weather.com?q={city}")
        return resp.json()["temp"]

# Agent 自动处理：sync 用 run_in_executor，async 直接 await
❓ 为什么这件事必要
工具常做 I/O：
  • HTTP 请求：调第三方 API（天气、地图、支付）。
  • 数据库查询：读用户信息、订单历史。
  • 文件读写：读配置、写日志。
同步 I/O 会阻塞事件循环：一个工具调用花 2 秒，整个 Agent 卡住 2 秒，无法处理其他请求。异步 I/O 让事件循环继续运转，多个工具调用可并发执行（一个等网络时另一个跑 CPU 任务）。Python 的 asyncio 和 .NET 的 Task 都要求异步传染性——async all the way。
✅ MAF 的做法与优点
MAF 的 @tool 同时支持同步和异步（见 python/packages/core/agent_framework/_tools.py 的 ToolDefinition.invoke）：
  • 同步工具：框架用 asyncio.to_thread（或 run_in_executor）在线程池执行，避免阻塞。
  • 异步工具：框架直接 await，不阻塞事件循环。
  • 自动检测：inspect.iscoroutinefunction(...) 判断是否异步。
  • 并发执行：多个工具调用可用 asyncio.gather 并发（未来支持 parallel tool calls）。
开发者不用关心同步 / 异步细节，框架保证高效执行。
🔀 还有什么其他方案
  • LangChain：@tool 支持异步，但 AgentExecutor 的同步 / 异步路径分离，易出错。
  • OpenAI SDK：不管工具同步 / 异步，应用层自己处理。
  • 同步 only：简单但性能差，Agent 处理并发请求时会卡住。
  • MAF 透明处理：写同步工具（简单）或异步工具（高效）都行，框架自动优化。

# 模型：调 read_page("page_123") → 读到步骤

# 用户："I still can't log in, please help"
# 模型：调 create_ticket(...) → 框架弹确认 → 用户批准 → 创建工单
❓ 为什么这件事必要
真实 Agent 需要多种能力：
  • 检索：搜索知识库、数据库、API。
  • 读写：读文件、写日志、更新记录。
  • 计算：调计算器、运行代码。
  • 交互：发邮件、创建工单、调第三方服务。
单个工具功能有限，多个工具组合才能完成复杂任务。模型需要规划：先搜索 → 再读取 → 最后创建工单。框架需要支持多轮工具调用（一个工具的输出可能触发下一个工具）。
✅ MAF 的做法与优点
MAF 的工具循环（见 python/packages/core/agent_framework/_agents.py 的 _run_non_streaming）：
  • 传所有工具 schema：Agent 初始化时把所有工具的 JSON Schema 发给模型。
  • 模型选择工具：模型根据用户问题决定调哪个（或哪几个）工具，输出 function_call。
  • 框架路由执行：根据 function_call.name 找到对应 Python 函数，传参调用。
  • 结果回灌：把 function_result 追加进对话历史，模型读取后决定：继续调工具 or 给出最终答案。
  • 循环直到完成：最多 max_tool_rounds 轮（默认 10），防止死循环。
开发者只需定义工具、把它们传给 Agent，调度和组合由框架完成。
🔀 还有什么其他方案
  • OpenAI parallel_tool_calls：支持一次返回多个 tool_call，MAF 未来也会支持（并发执行工具）。
  • Anthropic tool_use blocks：一条消息可包含多个 tool_use，MAF 已在 Content.from_function_call 抽象。
  • LangChain ToolChain：需手动编排工具调用顺序（A → B → C），不如让模型自己规划灵活。
  • MAF 自动循环 + 模型规划：给足工具，模型自己组合，框架保证安全执行（审批 + 轮数限制）。
✅ 关键要点
  • @tool 把普通函数变成模型可调用的工具，schema 自动生成。
  • 用 Annotated[..., Field(description=…)] 给参数写说明，docstring 写函数用途。
  • 把工具放进 Agent(tools=[…])；执行 + 回灌由框架完成。
💡 设计亮点
"函数即工具"：你不用手写 JSON Schema，类型注解和 docstring 就是契约。 代码与给模型的描述永远同步，因为它们本来就是同一份。
第二部分 · 用户视角

07 · 会话与记忆

默认情况下，每次 run() 都是"失忆"的。要让 Agent 记住上文， 就把同一个 会话（AgentSession）传给连续的调用。更长期的记忆，则交给 ContextProvider。

📒 生活类比
AgentSession 像一本共享记事本：每轮对话都写进同一本，下一轮模型翻看它就"记得"。 ContextProvider 则像一位助理，在每次回答前把"相关的旧记忆 / 外部知识"悄悄塞进上下文。

多轮对话：带上会话

samples/01-get-started/03_multi_turn.py
session = agent.create_session()

result = await agent.run(
    "My name is Alice and I love hiking.", session=session)

result = await agent.run(
    "What do you remember about me?", session=session)
# → 记得 Alice、喜欢徒步

关键就一点：把同一个 session 透传给每次 run()，历史便自动累积。 不传 session，则每次都是全新对话。

更长期的记忆 / 外部知识

🔬 ContextProvider
会话只在"本轮对话"内累积。要跨会话记住用户偏好，或在回答前注入检索到的知识（RAG），用 ContextProvider：例如 MemoryContextProvider 把记忆存进可检索的库， 每次 run 前自动把相关条目拼进上下文。（记忆库 / 各存储后端见第 16 课与各 provider 包。）
1 create_session vs 不传 session 点击展开详解
🧪 示例
# 不传 session：每次都是新对话（失忆）
result1 = await agent.run("我叫 Alice")
result2 = await agent.run("我叫什么？")
# → 模型不知道，之前的"Alice"已丢失

# 传 session：记住上下文
session = agent.create_session()
result1 = await agent.run("我叫 Alice", session=session)
result2 = await agent.run("我叫什么？", session=session)
# → 模型回答"Alice"

# 查看会话历史
print(session.history)  # [Message("user", "我叫 Alice"), Message("assistant", ...), ...]
❓ 为什么这件事必要
许多 AI 应用需要上下文连续性：
  • 对话式 UI：用户问"天气怎样？" → "明天呢？" → "后天呢？"，每句都依赖前文。
  • 任务流：用户说"帮我订酒店" → 模型问"哪个城市？" → "西雅图" → "几号入住？"，需保持状态。
  • 个性化：用户说"我喜欢素食"，后续对话记得这点。
如果默认有状态（隐式全局 session），会导致：不同用户的对话串了、测试时难以隔离、并发请求互相干扰。MAF 选择无状态为默认，需要状态时显式传 session。
✅ MAF 的做法与优点
AgentSession（见 python/packages/core/agent_framework/_sessions.py）：
  • 显式创建：agent.create_session() 返回一个新会话对象。
  • 透传：把同一个 session 对象传给每次 run()。
  • 自动累积：每次 run 后，用户消息 + 模型回复（+ 工具调用/结果）自动追加进 session.history。
  • 无副作用：不传 session 时，run 不改任何全局状态，完全无状态。
这种设计让并发安全（多个用户各自的 session 互不干扰）、可测试（每个测试用例独立 session）、易理解（有没有记忆一目了然）。
🔀 还有什么其他方案
  • OpenAI Assistants API：用 thread_id 标识会话，服务端管理历史。优点是无需客户端存储，缺点是无法本地调试、换厂商需重构。
  • LangChain Memory：用 ConversationBufferMemory 等类，需手动挂到 Chain。容易忘记清空，导致历史累积过长。
  • 隐式全局 session：框架内部维护 session 字典（user_id → history），简化 API 但并发不安全、难测试。
  • MAF 显式 session 对象：清晰、安全、可控。
2 ContextProvider 的工作流 点击展开详解
🧪 示例
from agent_framework import Agent, MemoryContextProvider

# 创建一个记忆提供者：在每次 run 前注入相关记忆
memory_provider = MemoryContextProvider(
    memory_store=...,  # 向量数据库 / Redis / 其他存储
    relevance_threshold=0.7
)

agent = Agent(
    client=client,
    name="Assistant",
    context_providers=[memory_provider],  # 挂载
)

# 用户首次说"我喜欢爬山"

await agent.run("我喜欢爬山", session=session)
# → MemoryContextProvider 把"用户喜欢爬山"存入记忆库

# 几天后，新会话
session2 = agent.create_session()
await agent.run("推荐周末活动", session=session2)
# → MemoryContextProvider 检索到"喜欢爬山"，注入上下文
# → 模型回答时会考虑这条记忆
❓ 为什么这件事必要
AgentSession 只在单次对话内记忆，对话结束后历史就没了。真实应用需要跨会话记忆：
  • 用户偏好：用户说"我对海鲜过敏"，所有后续会话都要记得。
  • RAG（检索增强生成）：用户问"公司休假政策？"，从文档库检索相关段落，注入上下文。
  • 个性化：根据用户历史交互（问过什么、喜欢什么）调整回答风格。
把这些逻辑硬编码在 instructions 或手动拼进每条消息，既繁琐又不可扩展。需要可插拔的上下文注入机制。
✅ MAF 的做法与优点
ContextProvider 接口（见 python/packages/core/agent_framework/）：
  • 在每次 run 前调用：Agent 执行时，遍历 context_providers 列表，调用每个 provider 的 provide_context(...)。
  • 返回消息 / 内容：provider 可返回 Message 列表（注入历史对话）、Content 列表（注入文档片段）、或修改 system prompt。
  • 内置实现：MemoryContextProvider（向量检索记忆）、InMemoryHistoryProvider（跨会话历史）、DocumentContextProvider（文档 RAG）。
  • 可组合：多个 provider 按顺序执行，可同时用记忆 + 文档检索 + 用户偏好。
这种设计让上下文逻辑解耦，Agent 不关心"记忆从哪来"，只管"有这些上下文"。
🔀 还有什么其他方案
  • LangChain Memory：ConversationBufferMemory、ConversationSummaryMemory 等，但和 Chain 耦合，不易切换存储后端。
  • LlamaIndex chat memory：专注向量检索，但不支持其他类型上下文（如用户偏好、文档片段）。
  • 手动拼接：在 run 前手动查询记忆库、拼进消息列表，重复代码多、易出错。
  • MAF 接口抽象 + 内置实现：开箱即用的 provider，也可自定义（如接入企业知识图谱）。

  • 抽象接口：子类实现 get_messages / save_messages，Agent 通过 context_providers 依赖接口。

    • InMemoryHistoryProvider：开发用，内存存储。

  • 可扩展：自定义后端（如接入 PostgreSQL、MongoDB）只需继承 HistoryProvider。
🔀 还有什么其他方案
  • LangChain：RedisChatMessageHistory、FileChatMessageHistory 等，但和 Memory 类耦合，切换存储需改 Memory 初始化。
  • OpenAI Assistants：服务端管理，开发者无法选择存储后端、无法本地调试。
  • 手动序列化：自己写 json.dump(history, file)，重复代码多、容易出错（忘记处理工具调用等复杂内容）。
  • MAF 接口 + 多实现：开发用内存、生产切 Redis，只改一行配置。
4 context window 压缩 点击展开详解
🧪 示例
from agent_framework import (
    CompactionProvider,
    SlidingWindowStrategy,
    SummarizationStrategy,
    ContextWindowCompactionStrategy,
)

# 策略 A：滑动窗口（保留最近 N 组消息，丢弃最老的）
strategy = SlidingWindowStrategy(keep_last_groups=20, preserve_system=True)

# 策略 B：摘要压缩（用 LLM 把老消息总结，需传入 client）
strategy = SummarizationStrategy(client=client, target_count=4)

# 策略 C：按上下文窗口 token 预算压缩（两阶段：工具结果驱逐 + 截断）
strategy = ContextWindowCompactionStrategy(
    max_context_window_tokens=128_000,
    max_output_tokens=16_384,
)

# 用 CompactionProvider 包装策略，作为 context provider 注入
compaction = CompactionProvider(before_strategy=strategy)
agent = Agent(
    client=client,
    context_providers=[compaction]
)

# 对话增长时，框架在每轮前自动按策略压缩
session = agent.create_session()
for i in range(30):
    await agent.run(f"第 {i} 条消息", session=session)
    # → 超出阈值时策略生效：丢弃最老的组或生成摘要
❓ 为什么这件事必要
对话历史会无限增长，问题：
  • token 限制：模型有 context window 上限（如 GPT-4 128k tokens），超过就报错或截断。
  • 成本：输入 token 也计费，历史越长、每次调用越贵。
  • 延迟：发送和处理更多 token 增加延迟。
  • 相关性衰减：50 轮前的对话可能和当前问题无关，但仍占用 context。
需要自动压缩策略：在不丢失关键信息的前提下，控制 context 大小。
✅ MAF 的做法与优点
MAF 内置多种压缩策略（SlidingWindowStrategy / SummarizationStrategy / ContextWindowCompactionStrategy，见 _compaction.py）：
  • 滑动窗口：保留最近 N 条消息，删掉最老的（适合短期对话）。
  • 摘要压缩：把老消息总结成一条 system 消息（"之前用户提到……"），保留语义、减少 token。
  • 混合策略：保留 system 消息（重要指令）+ 最近消息（当前上下文）+ 摘要中间消息。
  • 自动触发：Agent 在 run 前检查历史长度，超过阈值时调用策略压缩。
  • 可配置：keep_last_groups、target_count、max_context_window_tokens 等参数都可调。
开发者无需手动管理 context，框架自动优化。
🔀 还有什么其他方案
  • LangChain ConversationSummaryMemory：每次对话后调 LLM 生成摘要，但开销大、时机不灵活。
  • 手动截断：messages[-10:] 只取最后 10 条，简单但丢失早期重要信息。
  • 向量检索：把历史存进向量库，每次检索相关片段，但需额外基础设施。
  • MAF 多策略可选：简单场景用滑动窗口，复杂场景用摘要，还可组合 ContextProvider 做向量检索。
✅ 关键要点
  • 无状态是默认；用 AgentSession 携带多轮历史。
  • agent.create_session() 建会话，run(…, session=session) 复用它。
  • 跨会话 / 外部知识用 ContextProvider（如 MemoryContextProvider）。
💡 设计亮点
把"短期对话历史"（Session）和"长期可检索记忆"（ContextProvider）分成两层： 前者简单透传，后者可插拔。需求小就只用 Session，需求大再加 Provider，复杂度按需付费。
第三部分 · 内部源码

08 · Agent 内部

你用的 Agent 背后有两层：最底层是抽象基类 BaseAgent，上面是具体类 Agent。 了解这两层，才看得懂框架如何"驱动"一个 Agent 跑完整个循环。

🏗️ 生活类比
BaseAgent 像一份岗位说明书（"你要能接单、能跑、能交付"）， Agent 则是真人上岗——读说明书、准备工具箱、接单后反复跑腿，直到任务完成。

两层结构

抽象BaseAgent
定义 run() 协议与扩展点（_agents.py:314）。 所有 Agent 必须实现这份"合同"。
具体Agent
组装 instructions + 消息 + 工具 → 调 ChatClient → 工具循环 → 返回 AgentResponse（_agents.py:1584）。

run() 内部做了什么

1

构建消息列表

把 instructions（system）+ 会话历史 + 新输入拼起来。

2

注入 ContextProvider

把长期记忆 / 外部知识塞进上下文。

3

调用 ChatClient

把消息 + 工具 schema 发给 LLM，拿回 ChatResponse。

4

工具循环

若回复含 function_call，执行工具、追加结果、再回第 3 步。

5

返回

循环结束，包装成 AgentResponse（或逐块 AgentResponseUpdate）。

1 BaseAgent 定义了哪些接口？ 点击展开详解
🧪 示例
BaseAgent（_agents.py:314）规定了 run()（非流式 + 流式共用）、create_session()、get_session()。 子类只需实现这几个方法，循环骨架已由基类搭好。
❓ 为什么这件事必要
如果没有统一接口，每种 Agent 都得各写一套调用协议， 上层编排器无法通用。抽象基类保证"任何 Agent 都能 run()"，这是多态的基础。
✅ MAF 的做法与优点
MAF 用 模板方法模式：BaseAgent 定义骨架，RawAgent / Agent 分层实现。 这样可以在不破坏协议的前提下自由扩展。
🔀 还有什么其他方案
LangChain 用 Runnable 协议（更通用但更松散）； AutoGen 用 ConversableAgent（更紧耦合）。MAF 选择"刚好够用"的抽象层次，避免过度泛化。
2 Agent.run() 内部调用链 点击展开详解
🧪 示例
Agent（_agents.py:1584）的 run() 经过中间件 / 遥测层后进入 RawAgent.run()（_agents.py:889），依次调用： 
_prepare_run_context()   # 准备消息、session、工具、选项
_call_chat_client()      # 调用 ChatClient 拿回 ChatResponse
_parse_non_streaming_response()  # 非流式：转为 AgentResponse
_parse_streaming_response()      # 流式：转为 AgentResponseUpdate 流
_run_after_providers()   # 执行 ContextProvider 后置钩子
❓ 为什么这件事必要
理解内部调用链，才知道在哪里挂中间件、在哪里注入上下文、 出错时该看哪一步——不再"黑箱调试"。
✅ MAF 的做法与优点
每个步骤是独立方法，职责单一。 _prepare_run_context() 只管拼消息，_call_chat_client() 只管调模型。 这让子类可以 精确覆写某一步而不动其他步骤。
🔀 还有什么其他方案
有的框架把所有逻辑放进一个大 run() 方法； 也有的用声明式 DAG（如 LangGraph）编排。MAF 的方法函数分拆 + 循环骨架是两者的中间路线。
3 自定义 Agent（RawAgent） 点击展开详解
🧪 示例
RawAgent（_agents.py:578）是核心实现层—— 它继承 BaseAgent，实现了完整的 run()、上下文提供者执行、会话管理、工具解析。 如果你想"完全接管"Agent 行为，就继承 RawAgent 并覆写 _call_chat_client()。
❓ 为什么这件事必要
默认 Agent 自带中间件层和遥测层。 有时你需要跳过这些层，或者完全替换 LLM 调用逻辑（比如做 mock 测试），这时需要 RawAgent。
✅ MAF 的做法与优点
Agent = AgentMiddlewareLayer + AgentTelemetryLayer + RawAgent。 三层用 Python 多继承组合，你可以只要其中一层或全部。这种 Mixin 模式比单一继承链灵活得多。
🔀 还有什么其他方案
可以用装饰器模式逐层包裹（增加运行时开销）， 或用配置开关控制功能（不够灵活）。MAF 选择 Mixin 继承，编译期确定行为、零额外运行时开销。
4 AgentResponse 的结构 点击展开详解
🧪 示例
AgentResponse（_types.py:2530）的核心字段： 
response.text           # 所有消息的拼合文本
response.messages       # list[Message] — 完整消息列表
response.usage_details  # UsageDetails — prompt/completion token 计数
response.finish_reason  # "stop" / "tool_calls" / "length"

❓ 为什么这件事必要
了解返回结构，你才能正确地：提取回复文本、检查 token 用量做成本控制、 判断模型是"正常结束"还是"截断了"、拿到结构化数据而不是手动解析 JSON。
✅ MAF 的做法与优点
.text 是只读属性（自动拼合所有 message）， .value 支持泛型——如果你声明了 response_format=MyModel， .value 自动返回 MyModel 实例，无需手动反序列化。
🔀 还有什么其他方案
OpenAI SDK 直接返回 dict/dataclass；LangChain 用 AIMessage。 MAF 的 AgentResponse 多了 .value 泛型和 .continuation_token （可恢复长对话），更贴近生产需求。

# _agents.py — RawAgent.run() 核心（简化版）

async def _prepare_run_context():
    return await self._prepare_run_context(
        messages=messages, session=session,
        tools=tools, options=options, ...)

if not stream:
    async def _run_non_streaming():
        ctx = await _prepare_run_context()
        response = await self._call_chat_client(ctx, stream=False)
        return await self._parse_non_streaming_response(ctx, response)
    return _run_non_streaming()

# stream=True 分支
async def _run_streaming():
    ctx = await _prepare_run_context()
    stream_response = self._call_chat_client(ctx, stream=True)
    return self._parse_streaming_response(ctx, stream_response)
❓ 为什么看这段代码有价值
三步清晰可见：①准备上下文 → ②调 ChatClient → ③解析响应。 流式和非流式共用同一个 _prepare_run_context，区别只在第②③步。 工具循环藏在 _parse_non_streaming_response 里——它会检查 function_call，执行工具，再回调 _call_chat_client。
✅ _call_chat_client 做了什么
它直接调用 self.client.get_response(messages=..., stream=..., options=...)—— 把准备好的消息、工具 schema、ChatOptions 透传给 ChatClient。 这就是 Agent 和 ChatClient 的交界面：Agent 负责"组装"，ChatClient 负责"通信"。
🔀 你可以在哪些点介入
覆写 _call_chat_client()：自定义"怎么调模型"。 覆写 _prepare_run_context()：自定义"怎么组装消息"。 加中间件：不改源码也能拦截。 三个扩展点，粒度从大到小。
✅ 关键要点
  • BaseAgent（抽象）定义协议；Agent（具体）实现组装 + 循环。
  • run() = 构建消息 → 注入上下文 → 调 ChatClient → 工具循环 → 返回。
  • 返回类型：非流式 AgentResponse；流式 AgentResponseUpdate。
  • 真实代码三步：_prepare_run_context → _call_chat_client → _parse_response。
💡 设计亮点
循环骨架由基类掌控，子类只插入"怎么调模型"这一块——经典的模板方法模式。 三个扩展点（_prepare_run_context / _call_chat_client / _parse_response）让你在不同粒度介入。

🔧 生活类比

1

你写函数 + @tool

2

1 FunctionTool 里装了什么？ 点击展开详解
🧪 示例
FunctionTool（_tools.py:240）持有：原始函数引用、生成的 JSON Schema、 approval_mode（调用前是否需要人工审批）、函数名、描述。 @tool（_tools.py:1145）是构造 FunctionTool 的语法糖。
❓ 为什么这件事必要
知道 FunctionTool 的结构，才能理解 schema 是怎么生成的、 执行时参数怎么验证的、approval_mode 在哪里拦截。调试工具调用问题必须从这里入手。
✅ MAF 的做法与优点
FunctionTool 把函数元信息（名字、描述、schema）和运行时行为 （执行、审批、序列化）封装在同一个对象里，是"函数即工具"哲学的载体。
🔀 还有什么其他方案
有的框架用 dict 描述工具（无类型安全）； 有的让你手写 JSON Schema。MAF 从类型注解自动生成 schema，消除"代码与 schema 不一致"的风险。

4 FunctionTool 的执行过程 点击展开详解
🧪 示例
FunctionTool.invoke()（_tools.py:574）的执行步骤： 
1. 验证参数 → arguments 对照 schema 检查类型
2. 创建 FunctionInvocationContext
3. 合并参数 → 把 context 参数注入 kwargs
4. 调用 _invoke_function() → 执行你的 Python 函数
5. 解析结果 → result_parser 或 parse_result()
6. 返回 list[Content] → 包装为 function_result
❓ 为什么这件事必要
出错时（参数验证失败、函数抛异常、结果解析错误），需要知道在哪一步出了问题。 invoke() 的 6 步流水线给你精确的排查路径。
✅ MAF 的做法与优点
验证发生在调用之前，提前拦截非法参数。 如果启用了 observability（遥测），每次 invoke() 会创建 span 和 histogram， 自动记录执行时间和异常——无需额外代码就有生产级监控。
🔀 还有什么其他方案
有的框架在调用时才验证（报错晚）； 有的不做结果解析（直接返回原始值）。MAF 的"先验证 → 再调用 → 后解析"三段式最健壮。
5 并行工具调用 点击展开详解
🧪 示例
当模型一次返回多个 function_call（如同时查天气和汇率）， 框架在 _try_execute_function_calls()（_tools.py:1655）中用 asyncio.gather() 并行执行所有调用： 
results = await asyncio.gather(*[
    invoke_with_termination_handling(fc, idx)
    for idx, fc in enumerate(function_calls)
])
❓ 为什么这件事必要
如果 3 个工具各需 1 秒，串行要 3 秒，并行只要 1 秒。 对于 I/O 密集型工具（API 调用、数据库查询），并行执行能大幅降低延迟。
✅ MAF 的做法与优点
用 asyncio.gather() 实现真正并发。 每个调用独立包裹异常处理（invoke_with_termination_handling）， 一个工具失败不会影响其他工具。返回值是 (list[Content], should_terminate) 元组。
🔀 还有什么其他方案
线程池（ThreadPoolExecutor）适合 CPU 密集型但对异步不友好； 串行执行最简单但最慢。MAF 选择 asyncio.gather()，完美适配 I/O 密集场景且与框架的 async 架构一致。
✅ 关键要点
  • @tool → FunctionTool → JSON Schema → 随请求发给模型。
  • 模型回 function_call → 框架执行 → function_result 回灌 → 再让模型继续。
  • 整个循环在 Agent 内部自动跑，调用方无感。
💡 设计亮点
类型注解就是 schema——不存在"代码改了但忘记更新 schema"的问题， 因为它们在同一份源码里。这是"函数即工具"哲学的核心。

11 · 中间件 Middleware

中间件让你不改 Agent / ChatClient 源码就能横切地加入日志、重试、审批等逻辑。 MAF 有三层中间件，每层包裹不同粒度的操作。

🧅 生活类比
中间件像洋葱圈：请求从外到内穿过每一层，到达核心执行后，结果再从内到外穿出来。 每一层都可以在"进去前"和"出来后"做事（记日志、改参数、重试……）。

三层中间件

AGENTAgentMiddleware
包裹整个 agent.run()——最外层。用 AgentContext。
CHATChatMiddleware
包裹每次 LLM 调用。用 ChatContext。
FUNCFunctionMiddleware
包裹每次工具执行。用 FunctionInvocationContext。

统一签名

中间件模板
from agent_framework import AgentMiddleware, AgentContext

class MyLoggingMiddleware(AgentMiddleware):
    async def process(self, context: AgentContext, call_next):
        print("before")
        await call_next()   # ← 无参！
        print("after", context.result)

重点：await call_next() 不传任何参数——它调用下一层或最终执行。 执行结果挂在 context.result 上。

1 也可以用装饰器写法 点击展开详解
🧪 示例

    print("before")

同样有 @function_middleware 和 @chat_middleware。
❓ 为什么这件事必要
类写法适合有状态的中间件（如计数器）；装饰器适合简单的无状态逻辑（如打日志）。 两种风格共存，让你按场景选择最简洁的写法。
✅ MAF 的做法与优点
@agent_middleware（_middleware.py:682） 内部用 MiddlewareWrapper 把函数包装成类协议——对管线来说，两种写法完全等价。
🔀 还有什么其他方案
有的框架只支持类写法（啰嗦）；有的只支持函数写法（难以持有状态）。 MAF 两者都支持，且在内部统一为同一协议。
2 执行顺序（洋葱模型） 点击展开详解
🧪 示例
假设注册了 A → B → C 三个中间件，执行顺序： 
A.process() 进入 → "A before"
  B.process() 进入 → "B before"
    C.process() 进入 → "C before"
      ── 核心执行（call_next 到底）──
    C.process() 返回 → "C after"
  B.process() 返回 → "B after"
A.process() 返回 → "A after"
每个中间件在 await call_next() 前后各有一次执行机会。
❓ 为什么这件事必要
理解洋葱模型，才能正确安排中间件顺序： 想"最早记录 + 最晚结束"的日志中间件应放最外层；想"只拦截异常"的重试中间件应放内层。
✅ MAF 的做法与优点
管线（AgentMiddlewarePipeline，_middleware.py:847） 用闭包递归构建 call_next 链：从最后一个中间件开始，每层包裹前一层。 执行结果统一挂在 context.result，无需返回值传递。
🔀 还有什么其他方案
Express.js 用线性 next()（无"出来"阶段）； Django 用 __call__ 包裹（类似但不直观）。MAF 的 call_next() 洋葱模型最清晰—— before 和 after 在同一个函数体里，代码局部性好。

4 中间件间的数据传递 点击展开详解
🧪 示例
中间件 A 记录开始时间，中间件 B 读取并计算耗时： 
# 中间件 A（外层）
async def process(self, ctx, call_next):
    ctx.metadata["start_time"] = time.time()
    await call_next()

# 中间件 B（内层，call_next 之后读）
async def process(self, ctx, call_next):
    await call_next()
    elapsed = time.time() - ctx.metadata["start_time"]
关键：用 context.metadata，不用全局变量！
❓ 为什么这件事必要
中间件之间经常需要协作：计时器中间件记录开始时间，日志中间件读取耗时。 如果用全局变量，并发请求会互相干扰。
✅ MAF 的做法与优点
context.metadata 是每次请求独立的 dict[str, Any]， 天然线程/协程安全。中间件只需约定 key 名即可通信，无需导入彼此。
🔀 还有什么其他方案
Python contextvars（更隐式，调试困难）； 闭包捕获（仅限同一管线内）。metadata dict 最直观、最易调试。
5 真实中间件示例 点击展开详解
🧪 示例
三个生产级中间件： 
# 1. 日志中间件（AgentMiddleware）
class LogMiddleware(AgentMiddleware):
    async def process(self, ctx, call_next):
        logger.info(f"Agent {ctx.agent.name} start")
        await call_next()
        logger.info(f"Agent done: {len(ctx.result.messages)} msgs")

# 2. Token 计数中间件（ChatMiddleware）
class TokenCounter(ChatMiddleware):
    async def process(self, ctx, call_next):
        await call_next()
        usage = ctx.result.usage_details
        ctx.metadata["total_tokens"] = usage.prompt_tokens + usage.completion_tokens

# 3. 限流中间件（ChatMiddleware）
class RateLimiter(ChatMiddleware):
    async def process(self, ctx, call_next):
        await self.semaphore.acquire()
        try:
            await call_next()
        finally:
            self.semaphore.release()
❓ 为什么这件事必要
这三个覆盖了最常见的生产需求：可观测性（日志）、成本控制（token 计数）、流量管理（限流）。 它们展示了 call_next() 前后分别适合做什么。
✅ MAF 的做法与优点
日志放 AgentMiddleware（整个 run 级别）， token 计数和限流放 ChatMiddleware（每次 LLM 调用级别）—— 三层粒度让每个中间件精确拦截它关心的操作。
🔀 还有什么其他方案
用 AOP 框架（如 aspectlib）做切面（太重）； 在 Agent 类里加 hook 方法（不够灵活）。MAF 的中间件管线是最标准的横切关注点解决方案。
✅ 关键要点
  • 三层：AgentMiddleware（整个 run）→ ChatMiddleware（每次 LLM 调用）→ FunctionMiddleware（每次工具执行）。
  • 统一签名 process(self, context, call_next)；await call_next() 无参。
  • 可用类写法，也可用 @agent_middleware 等装饰器。
💡 设计亮点
三层粒度 × 洋葱模型：你可以只拦截"每次 LLM 调用"（ChatMiddleware）而不碰工具执行， 或只拦截工具执行而不碰 LLM——关注点彻底分离。

12 · Workflows 工作流引擎

Workflows 是 MAF 的图执行引擎：把多个步骤（Executor） 用边（Edge）连成有向图，由 WorkflowBuilder 构建、Workflow.run() 驱动。

🗺️ 生活类比
把 Workflow 想成地铁线路图：每个站（Executor）做一件事， 铁轨（Edge）决定下一站去哪。WorkflowBuilder 画图，run() 发车。

核心概念

概念作用源码
Executor图中的一个节点，处理消息_workflows/_executor.py
Edge连接两个节点的有向边_workflows/_edge.py
WorkflowBuilder用 add_edge/add_chain 构建图_workflows/_workflow_builder.py
WorkflowContext节点内发消息/输出的句柄_workflows/_workflow_context.py

最小示例

samples/01-get-started/07_first_graph_workflow.py
from agent_framework import Executor, WorkflowBuilder, WorkflowContext, executor, handler

class UpperCase(Executor):
    @handler
    async def to_upper(self, text: str, ctx: WorkflowContext[str]):
        await ctx.send_message(text.upper())

@executor(id="reverse")
async def reverse(text: str, ctx: WorkflowContext):
    await ctx.yield_output(text[::-1])

upper = UpperCase(id="upper")
wf = WorkflowBuilder(start_executor=upper) \
    .add_edge(upper, reverse).build()
events = await wf.run("hello")  # → "OLLEH"
1 Executor 两种写法 点击展开详解
🧪 示例
Class-based（Executor 子类 + @handler）： 
class UpperCase(Executor):
    @handler
    async def to_upper(self, text: str, ctx: WorkflowContext):
        await ctx.send_message(text.upper())
Function-based（@executor 装饰独立函数）： 
@executor(id="reverse")
async def reverse(text: str, ctx: WorkflowContext):
    await ctx.yield_output(text[::-1])
函数式写法会自动包装成 FunctionExecutor，功能完全等价。
❓ 为什么这件事必要
不同场景有不同诉求：简单节点写一个函数最快，复杂节点需要在类里维护 __init__ 参数、多个 handler、甚至复用继承。 两种写法让框架同时服务脚本级原型和生产级代码。
✅ MAF 的做法与优点
MAF 让 @executor 装饰器自动把函数包成 FunctionExecutor， 内部共享同一套 handler 注册和消息分发机制。你可以在同一张图里混用两种写法——类节点和函数节点通过边自由连接。
🔀 还有什么其他方案
LangGraph 只支持函数节点（无类继承概念）； Prefect 只支持 @task 函数。MAF 两者兼备，是更灵活的选择。
2 Edge 的高级模式 点击展开详解
🧪 示例
# 1-to-1
builder.add_edge(node_a, node_b)
# 1-to-many (fan-out)
builder.add_fan_out_edges(splitter, [worker1, worker2, worker3])
# many-to-1 (fan-in)
builder.add_fan_in_edges([worker1, worker2, worker3], aggregator)
# 条件分支 (switch-case)
builder.add_switch_case_edge_group(router, [
    Case(target=fast_path, condition=lambda msg: msg.priority == "high"),
    Default(target=slow_path),
])
# 链式快捷 (等价于连续 add_edge)
builder.add_chain([step1, step2, step3])
❓ 为什么这件事必要
真实工作流不只是线性管线——你需要并行 map-reduce（fan-out/fan-in）、条件路由（switch-case）等拓扑。 如果框架只提供 add_edge，复杂图的构建代码会非常冗长且易出错。
✅ MAF 的做法与优点
MAF 在 WorkflowBuilder 上提供五种边方法，覆盖所有常见拓扑。 还有 add_multi_selection_edge_group（动态多选）用于"根据消息内容选择下游子集"的场景。 所有方法返回 Self，支持链式调用。
🔀 还有什么其他方案
Airflow 用 >> 运算符连边，可读但只支持 1-to-1； LangGraph 用字典声明条件路由。MAF 用显式方法名（add_fan_out_edges）让拓扑意图一目了然。
3 WorkflowContext 的 API 点击展开详解
🧪 示例
@handler
async def process(self, msg: str, ctx: WorkflowContext):
    ctx.set_state("count", ctx.get_state("count", 0) + 1)  # 读写共享状态
    await ctx.send_message(result, target_id="next")  # 转发给下一节点
    await ctx.yield_output(final)  # 输出最终结果
    await ctx.add_event(WorkflowEvent.status(...))  # 自定义事件
❓ 为什么这件事必要
WorkflowContext 是节点与引擎之间的唯一通信通道。 没有它，节点无法知道自己的上游是谁（source_executor_ids）、 无法向下游传数据、无法把结果暴露给调用者、也无法操作跨节点的共享状态。
✅ MAF 的做法与优点
Context 提供四大能力： ① send_message() 向下游传消息（可指定 target_id）； ② yield_output() 向调用者输出结果； ③ get_state/set_state 读写工作流级共享状态； ④ request_info() 请求外部输入（Human-in-the-Loop）。 还有 is_streaming() 让节点感知当前是否流式运行。
🔀 还有什么其他方案
Temporal 把状态放在 workflow 函数的局部变量里； LangGraph 用全局 State 字典。MAF 选择显式 Context 对象——既不污染函数签名，也不引入全局可变状态。
4 workflow.run() 返回值 点击展开详解

❓ 为什么这件事必要
工作流执行后，你可能只关心最终输出（get_outputs），也可能需要调试每一步的事件轨迹。 WorkflowRunResult 同时提供两种视角，让"用"和"调"都方便。
✅ MAF 的做法与优点
WorkflowRunResult 继承自 list[WorkflowEvent]， 所以你可以当列表遍历所有事件，也可以用语义化方法提取： get_outputs()（终端输出）、get_intermediate_outputs()（中间结果）、 get_request_info_events()（HITL 请求）、status_timeline()（状态变更时间线）。
🔀 还有什么其他方案
Prefect 返回 FlowRun 对象需要额外 API 查询事件； Airflow 通过 XCom 取中间值。MAF 把事件列表和便捷方法融为一体——一次 run() 全部到手。
✅ 关键要点
  • Workflow = Executor（节点）+ Edge（边）组成的有向图。
  • WorkflowBuilder 用链式 API 构图；.build() 得到 Workflow。
  • 节点通过 ctx.send_message() 传数据、ctx.yield_output() 输出最终结果。
💡 设计亮点
消息驱动：节点之间传递的是"消息"而非函数调用返回值—— 这意味着节点天然支持异步、fan-out/fan-in，且可在边上加条件/开关。

13 · 编排模式

当你需要多个 Agent 协作，MAF 提供五种现成的编排模式—— 不用手写调度逻辑，选一个 Builder、传入参与者，.build() 就行。

🎼 生活类比
编排模式像乐团编制：Sequential 是依次独奏，Concurrent 是齐奏， Handoff 是接力棒传递，Group Chat 是圆桌讨论，Magentic 是指挥家调度全局。

五种模式

模式Builder一句话
SequentialSequentialBuilderAgent A 做完 → Agent B 接着做
ConcurrentConcurrentBuilderAgent A 和 B 同时做，汇总结果
HandoffHandoffBuilderAgent A 主动把任务"交接"给 B
Group ChatGroupChatBuilder多个 Agent 在群聊中轮流发言

Sequential 示例
from agent_framework.orchestrations import SequentialBuilder

workflow = SequentialBuilder(participants=[writer, reviewer]).build()
result = await workflow.run("Write a poem about the sea")
1 Handoff 和 Group Chat 有什么区别？ 点击展开
🔬 关键差异
Handoff：当前 Agent 显式决定"我做不了，交给 X"，控制权单向传递。 Group Chat：一个 selector 函数（或模型）每轮选谁发言，所有 Agent 看到完整群聊记录。 Handoff 更适合专家流转，Group Chat 更适合辩论 / 头脑风暴。
2 SequentialBuilder 深入 点击展开详解
🧪 示例
workflow = SequentialBuilder(
    participants=[writer, reviewer, editor],
    intermediate_output_from="all",  # 每个参与者的输出都作为中间结果
    output_from=[reviewer],  # 只有 reviewer 的输出算最终结果
).build()

# result.get_intermediate_outputs() 包含所有人的中间输出
# result.get_outputs() 只包含 reviewer 的输出
❓ 为什么这件事必要
在多步链中，你可能只关心最终结果，也可能需要看到每一步的中间输出来做质量检查。 intermediate_output_from 和 output_from 让你精确控制哪些输出可见。
✅ MAF 的做法与优点
SequentialBuilder 接受 participants（有序列表）、 output_from（终端输出来源）和 intermediate_output_from（中间输出来源）。 还支持 chain_only_agent_responses=True 让后一个 Agent 只看到前一个的 AgentResponse，而非整个对话历史。 可通过 with_request_info() 启用 Human-in-the-Loop。
🔀 还有什么其他方案
LangChain 的 SequentialChain 只传最终输出； CrewAI 的 Process.sequential 自动传全部上下文。 MAF 让你自选粒度——是传完整历史还是只传 AgentResponse。
3 ConcurrentBuilder 深入 点击展开详解
🧪 示例
from agent_framework.orchestrations import ConcurrentBuilder

workflow = ConcurrentBuilder(
    participants=[analyst_a, analyst_b, analyst_c],
).with_aggregator(
    lambda responses: "\n---\n".join(r.text for r in responses)
).build()
result = await workflow.run("Analyze Q3 revenue")
❓ 为什么这件事必要
很多任务天然可并行：让三个分析师同时分析不同维度，最后汇总。 串行执行浪费时间——Concurrent 模式将延迟从 sum(各Agent时间) 降到 max(各Agent时间)。
✅ MAF 的做法与优点
ConcurrentBuilder 将所有 participants fan-out 并行执行， 然后在 fan-in 节点用聚合器合并结果。默认聚合器拼接所有输出； 你也可以用 with_aggregator() 传入自定义 Executor 或 lambda 做 map-reduce 风格的汇总。 同样支持 output_from、intermediate_output_from 和 with_request_info()。
🔀 还有什么其他方案
LangGraph 需要手动构建 fan-out/fan-in 图； AutoGen 没有内置并行模式。MAF 的 ConcurrentBuilder 一行声明并行 + 一行声明聚合器，极其简洁。
4 HandoffBuilder 深入 点击展开详解

workflow = HandoffBuilder(

在客服/专家路由场景中，当前 Agent 判断"这个问题我不擅长"后需要显式交接给另一个 Agent。 Handoff 模式让 Agent 自己决定交接时机和目标，而不是由外部调度器硬编码路由规则。
✅ MAF 的做法与优点
HandoffConfiguration 用 target + description 描述每条交接路径。 框架会自动给当前 Agent 注入一个"交接工具"——Agent 调用该工具即触发切换。 被交接的 Agent 会收到完整对话历史。如果 Agent 想让用户提供额外信息，可以发出 HandoffAgentUserRequest。
🔀 还有什么其他方案
OpenAI Swarm 也有 handoff 概念，但通过函数返回值实现，不支持异步和持久化。 AutoGen 的 SwarmAgent 类似但 API 更复杂。 MAF 的 Handoff 基于 Workflow 引擎——天然支持检查点和恢复。
5 MagenticBuilder 深入 点击展开详解
🧪 示例

workflow = MagenticBuilder(

❓ 为什么这件事必要
复杂任务（如"调研+编码+测试"）需要一个全局规划者分解子任务并分配给最合适的 Agent。 没有指挥官，Agent 之间会陷入无方向的对话循环。
✅ MAF 的做法与优点
MagenticBuilder 实现了 Plan → Review → Execute 循环： ① MagenticManager（指挥官）用 TaskLedger 维护事实和计划； ② 每轮通过 MagenticProgressLedger 评估进展，选出 next_speaker； ③ 检测到卡住（is_in_loop）会自动重置计划。 支持 enable_plan_review=True 让人工在计划阶段介入审核。
🔀 还有什么其他方案
AutoGen 的 MagenticOne 是该模式的原型；CrewAI 的 hierarchical process 类似但无 ProgressLedger 反馈机制。 MAF 的实现加入了卡住检测和自动重置，更适合长时间运行的复杂任务。
✅ 关键要点
  • 五种编排：Sequential / Concurrent / Handoff / Group Chat / Magentic。
  • 全部来自 agent_framework.orchestrations，选 Builder → 传参与者 → .build()。
  • 底层都是 Workflow 图——编排是高级糖。
💡 设计亮点
编排模式 = 预置拓扑的 Workflow：你用 Builder 声明意图，框架帮你画出正确的图。 需要更复杂的拓扑？直接用 WorkflowBuilder 手画。

2 AgentResponseUpdate 结构 点击展开详解
🧪 示例
async for chunk in agent.run("Tell me a joke", stream=True):
    print(chunk.text, end="")       # 增量文本
    print(chunk.contents)            # [TextContent(...)]
    print(chunk.finish_reason)       # None → ... → "stop"
    print(chunk.author_name)         # 多Agent时标识是谁说的
最后一个 chunk 的 finish_reason 为 "stop"，表示生成完毕。 把所有 chunk 的 .text 拼起来就是完整的 AgentResponse。
❓ 为什么这件事必要
流式场景中，你需要知道每个 chunk 包含什么、何时结束、谁在说话。 理解 AgentResponseUpdate 的字段才能正确地构建 UI 流式渲染。
✅ MAF 的做法与优点
AgentResponseUpdate 包含： .contents（Content 列表，可含 TextContent / 图片 / 工具调用）、 .text（所有 TextContent 拼接的纯文本快捷属性）、 .finish_reason（"stop" / "length" / "tool_calls"）、 .author_name / .agent_id（多 Agent 场景标识来源）。 结构与非流式的 AgentResponse 对齐，切换模式时代码改动最小。
🔀 还有什么其他方案
OpenAI SDK 返回 ChatCompletionChunk（仅文本 delta）； LangChain 返回 AIMessageChunk。MAF 的 chunk 带有 agent_id 和 author_name， 天然适合多 Agent 流式场景。
3 Workflow 的流式 点击展开详解
🧪 示例
async for event in wf.run("hello", stream=True):
    if event.type == "output":
        print("Final:", event.data)
    elif event.type == "intermediate":
        print("Step:", event.data)
    elif event.type == "executor_invoked":
        print("Running:", event.executor_id)
流式模式下 run() 返回 AsyncIterator[WorkflowEvent]，而非 WorkflowRunResult。
❓ 为什么这件事必要
工作流可能包含多个 Agent、运行数分钟。用户不能干等到整个图跑完—— 流式事件让前端实时展示进度：哪个节点在跑、中间结果是什么、最终输出何时到。
✅ MAF 的做法与优点
WorkflowEvent 有丰富的事件类型： started / executor_invoked / executor_completed（生命周期）、 output / intermediate（数据）、 request_info（HITL 请求）、failed（错误）。 每个事件携带 executor_id、iteration、state 等元数据。
🔀 还有什么其他方案
LangGraph 的 streaming 返回纯文本 chunk，无结构化事件； Temporal 有事件历史但不支持实时推送。MAF 的 WorkflowEvent 结构化且类型丰富—— 前端可以据此渲染进度条、节点高亮、错误提示。
4 OTel span 层次 点击展开详解
🧪 示例
MAF 自动产生的 span 层次： 
agent.run (parent span)
  ├── chat_client.call  # 每次 LLM 调用
  │     attrs: input_tokens, output_tokens, model
  ├── tool.execute      # 每次工具执行
  │     attrs: tool.name, tool.call.id
  └── chat_client.call  # 工具循环再次调用

workflow.run (parent span)
  ├── executor: upper   # 每个节点一个子 span
  │     attrs: executor.id, executor.type
  ├── message.send      # 节点间消息传递
  │     attrs: source_id, target_id
  └── executor: reverse
❓ 为什么这件事必要
当 Agent 链上某步慢了或报错，你需要知道具体是哪个 LLM 调用还是哪个工具执行的问题。 分层 span 让你在 Jaeger/Grafana 中像看调用栈一样定位瓶颈。
✅ MAF 的做法与优点
observability.py 定义了 OtelAttr 枚举，自动填充 GenAI 语义约定属性： gen_ai.agent.id、gen_ai.usage.input_tokens、gen_ai.tool.name 等。 Workflow 层还追踪 workflow.id、executor.id、message.send。 零额外代码——只需配置 exporter 即可在 Jaeger / Zipkin / OTLP Collector 中查看。
🔀 还有什么其他方案
LangSmith 是 LangChain 的专有追踪方案（厂商锁定）； LiteLLM 只追踪 LLM 调用不追踪工具和工作流。MAF 用标准 OTel—— 兼容所有 OTel 生态工具，无厂商锁定。
5 自定义 span / 指标 点击展开详解
🧪 示例
from agent_framework.observability import create_workflow_span, OtelAttr

with create_workflow_span(
    "my_custom_step",
    attributes={OtelAttr.EXECUTOR_ID: "validator"},
) as span:
    result = validate(data)
    span.set_attribute("validation.passed", result.ok)
❓ 为什么这件事必要
框架自动 span 覆盖 LLM 和工具调用，但你的业务逻辑（如自定义验证、数据库查询、外部 API 调用） 也需要被追踪。自定义 span 填补这些盲区。
✅ MAF 的做法与优点
MAF 暴露 create_workflow_span() 作为创建自定义 span 的便捷入口， 自动挂到当前 trace 上下文中。你也可以直接用 OTel SDK 的 tracer.start_as_current_span()。 框架提供的 OtelAttr 枚举确保属性名与内置 span 一致——查询时可以统一过滤。
🔀 还有什么其他方案
有些框架（如 Haystack）不暴露 tracer，只能用日志做追踪； LangSmith 需要用其 SDK 的 @traceable 装饰器。 MAF 完全拥抱 OTel 标准——你的自定义 span 和框架内置 span 在同一条 trace 中无缝衔接。
✅ 关键要点
  • run(stream=True) 逐块返回 AgentResponseUpdate。
  • 内置 OpenTelemetry：agent run / LLM 调用 / 工具执行自动产出 span。
  • 配好 exporter 即可在 Jaeger / Grafana 等工具中查看追踪与指标。
💡 设计亮点
可观测性是内置的，不是你自己加的——框架自动在关键操作上挂 span， 零额外代码就能看到"这次 run 调了几次模型、每次多少 token、工具花了多久"。

1 uv 为什么比 pip 好 点击展开详解
🧪 示例
速度对比：uv sync 在秒级完成，而 pip install 需要数分钟。 uv.lock 是锁定文件，记录所有传递依赖的精确版本。 Workspace 模式支持 monorepo，多个包可以一次性安装： 
# uv.lock 记录了整个依赖树
uv sync --all-packages  # 装整个 monorepo
cd packages/core && uv run poe test  # 单包测试
❓ 为什么这件事必要
可复现的构建需要锁定文件（lockfile），pip 本身没有内置锁定机制。 慢速安装会浪费大量 CI 时间。没有 workspace 支持的工具在 monorepo 中需要手动管理多个 requirements.txt。
✅ MAF 的做法与优点
MAF 使用 uv 的 workspace 模式。uv.lock 锁定每一个传递依赖的版本。 uv sync --all-packages 原子式地安装整个 monorepo 的所有包，无需手动进入每个子目录。
🔀 还有什么其他方案
可选方案：pip + pip-tools（生成 requirements.txt.lock）、poetry（有锁定但慢）、pdm（锁定 + PEP 621）。 uv 是最快的，且对 monorepo 的 workspace 原生支持最好。
2 poe 任务速查 点击展开详解
🧪 示例
主要任务清单： 
uv run poe test      # 运行 pytest
uv run poe lint      # ruff check（快速 linter）
uv run poe format    # ruff format（格式化）
uv run poe typing # pyright（类型检查）
单包运行： 
cd packages/core
uv run poe test  # 只测 core 包
❓ 为什么这件事必要
没有任务运行器（task runner），每个贡献者都会发明自己的魔法咒语。 标准化的任务 = 一致的 CI/CD 流水线，新人上手只需记住几条命令。
✅ MAF 的做法与优点
MAF 使用 poethepoet（简称 poe）。 任务定义在 pyproject.toml 的 [tool.poe.tasks] 区块。 每个质量门都有一条对应命令，本地开发和 CI 使用完全相同的命令。
🔀 还有什么其他方案
可选方案：Makefile（跨平台支持差）、just（需额外安装）、nox（偏重测试矩阵）、tox（配置复杂）。 poe 的优点是集成在 pyproject.toml 中，且跨平台支持好。
3 怎么写测试 点击展开详解
🧪 示例
测试文件命名为 test_*.py，放在 tests/ 或 packages/*/tests/。 使用 pytest + pytest-asyncio 处理异步： 
import pytest

@pytest.mark.asyncio
async def test_agent_run():
    agent = Agent()
    result = await agent.run("hello")
    assert result.status == "success"
使用 fixture 提供 mock 的 ChatClient。
❓ 为什么这件事必要
没有测试，重构就像走钢丝。异步代码尤其容易出错——pytest-asyncio 让异步测试变得可管理。
✅ MAF 的做法与优点
MAF 使用 pytest + pytest-asyncio。 测试与对应的包放在一起（packages/*/tests/）。 单元测试用 mock ChatClient，避免真实 API 调用。uv run poe test 跑所有测试。
🔀 还有什么其他方案
可选方案：unittest（Python 标准库，但啰嗦）、ward（极简但小众）、hypothesis（属性测试，适合复杂逻辑）。 pytest 是 Python 社区事实标准；asyncio 插件对异步框架是必需品。

1 完整 YAML schema 点击展开详解
🧪 示例

18 · 写自己的中间件

第 11 课讲了中间件是什么；本课教你写一个自己的——从零到能用。

🧱 生活类比
写中间件像在流水线上加一道工序：你可以在产品进入下一站前做质检（日志）， 在出站后贴标签（计费），或者发现次品时退回重做（重试）——不改流水线本身。

实战：重试中间件

自定义 ChatMiddleware
from agent_framework import ChatMiddleware, ChatContext

class RetryChatMiddleware(ChatMiddleware):
    def __init__(self, max_retries: int = 3):
        self.max_retries = max_retries

    async def process(self, context: ChatContext, call_next):
        for attempt in range(self.max_retries):
            try:
                await call_next()
                return
            except Exception:
                if attempt == self.max_retries - 1:
                    raise

挂到 Agent 上：Agent(client=client, chat_middleware=[RetryChatMiddleware(3)])。

1 完整的日志中间件 点击展开详解
🧪 示例
完整代码，带计时： 
import logging
import time
from agent_framework import ChatMiddleware, ChatContext

logger = logging.getLogger(__name__)

class LoggingChatMiddleware(ChatMiddleware):
    async def process(self, context: ChatContext, call_next):
        logger.info(f"Input: {context.messages}")
        start = time.monotonic()
        
        await call_next()
        
        duration = time.monotonic() - start
        logger.info(f"Output: {context.result}")
        logger.info(f"Duration: {duration:.2f}s")
约 15 行完整日志中间件。call_next() 前记输入，之后记输出和耗时。
❓ 为什么这件事必要
日志是第一常见中间件。没有它，调试生产 Agent 就是盲飞。看不到输入输出和耗时，无法定位问题。
✅ MAF 的做法与优点
MAF 的中间件模式让日志变得简单：用 before/after 逻辑包装 call_next()。访问 context.messages 获取输入，context.result 获取输出。
🔀 还有什么其他方案
基于装饰器的日志、OpenTelemetry 自动埋点。中间件是显式的且可组合的。
2 审批中间件 点击展开详解
🧪 示例

class ApprovalMiddleware(ChatMiddleware):
    async def process(self, context: ChatContext, call_next):
        user_input = context.messages[-1].content
        
        if "publish" in user_input or "delete" in user_input:
            # 暂停，等待人工确认（与 HITL 机制集成）

消息包含"publish"或"delete"时暂停，等人签字后再继续。
❓ 为什么这件事必要
自主 Agent 需要护栏。某些操作（发布、删除、付款）应该需要人工批准。没有审批，风险不可控。
✅ MAF 的做法与优点
MAF 中间件可以拦截任何调用。结合 request_info 进行异步人工输入，创建完整的审批流程。
🔀 还有什么其他方案
独立审批服务、基于 webhook 的审批。中间件保持在进程内且可组合。
3 Token 计费中间件 点击展开详解
🧪 示例
在 await call_next() 后读取用量： 
class BillingMiddleware(ChatMiddleware):
    def __init__(self):
        self.total_cost = 0.0
    
    async def process(self, context: ChatContext, call_next):
        await call_next()
        
        usage = context.result.usage
        # 假设价格：输入 $0.01/1k，输出 $0.03/1k
        cost = (usage.input_tokens * 0.01 + 
                usage.output_tokens * 0.03) / 1000
        self.total_cost += cost
        logger.info(f"Cost: ${cost:.4f}, Total: ${self.total_cost:.4f}")
约 12 行实时成本追踪。读取 context.result.usage，计算成本，累加。
❓ 为什么这件事必要
LLM 成本可能爆炸。按请求成本追踪启用预算、告警和按用户计费。没有它，账单成谜。
✅ MAF 的做法与优点
MAF 在每次调用后的 context.result.usage 上暴露 token 用量。中间件可以读取它而不修改响应。
🔀 还有什么其他方案
厂商控制台计费、外部代理（如 Helicone）。中间件提供实时、进程内追踪。
4 中间件的错误处理 点击展开详解
🧪 示例
在 await call_next() 周围加 try/except： 
class ErrorHandlingMiddleware(ChatMiddleware):
    async def process(self, context: ChatContext, call_next):
        try:
            await call_next()
        except Exception as e:
            logger.error(f"Call failed: {e}")
            # 可选：重试逻辑
            # 可选：返回后备响应
            # 或重新抛出
            raise
失败时：记录错误、可选重试、可选后备响应。模式：捕获异常，记录后重新抛出。
❓ 为什么这件事必要
LLM 调用会失败（速率限制、超时、错误响应）。没有错误处理中间件，失败会让整个 Agent 崩溃。
✅ MAF 的做法与优点
MAF 的管道自然传播异常。中间件可以在任何层捕获、记录、重试或转换错误。
🔀 还有什么其他方案
熔断器库（tenacity）、全局错误处理器。中间件是按层的且可组合的。
✅ 关键要点
  • 继承 *Middleware，实现 process(self, context, call_next)。
  • await call_next() 无参；结果在 context.result。
  • 用 Agent(middleware=…, chat_middleware=…, function_middleware=…) 挂载。
💡 设计亮点
中间件是组合式的：重试、日志、审批各自独立实现，按需拼装，互不干扰。

19 · 检查点 · 人在环 · 持久化

生产环境需要：跑到一半能存盘（检查点）、关键操作人工审批（人在环）、 挂了能续跑（持久化）。MAF 把这三件事做成一等公民。

💾 生活类比
检查点像游戏存档：进度存下来，挂了从存档恢复。 人在环像审批流：到关键节点暂停，等人签字再继续。 DurableTask 像云存档：存档不在本地，搬到另一台机器也能续玩。

检查点（Checkpoint）

工具可设置 approval_mode="always_require"，执行前暂停等人确认。 工作流层面也有 request_info 机制：节点暂停、发问、等回答再继续。

MAF 提供所有生产构建块：OTel 集成、持久化存储包、重试/日志/计费中间件。无需第三方胶水。
🔀 还有什么其他方案
平台特定解决方案（Azure Monitor、Datadog）。MAF 是云无关的；OTel 导出到任何后端。
✅ 关键要点
  • 多 Agent 工作流 = 几个 Agent + 一个 Builder + .build().run()。
  • 工具、中间件、检查点、人在环——全部可以叠加进去。
  • 从"hello agent"到"生产级多 Agent"，代码增量很小。
💡 设计亮点
复杂度是增量的：单 Agent → 加工具 → 加编排 → 加检查点 → 加审批，每一步只增加几行代码。 这就是"从原型到生产"的体验。

21 · Agent Skills 技能系统

Agent Skills（技能）让你把领域知识打包成可发现、可复用的模块—— Agent 不再只有工具，还有知识库。

📚 生活类比
工具是锤子、扳手（能做动作），技能是操作手册 + 参考资料（知道怎么做、什么背景知识）。 一个老师傅 = 工具 + 技能：既能动手，又有经验。

核心概念

概念作用源码
Skill一个完整技能 = 资源 + 脚本 + 元数据_skills.py
SkillResource技能附带的知识文件（文本/代码/文档）_skills.py
SkillScript技能可以执行的脚本（代码片段）_skills.py
SkillsSource技能的来源（文件夹 / 代码 / MCP）_skills.py
InlineSkill代码中直接定义的技能_skills.py

定义一个技能

代码定义技能
from agent_framework import InlineSkill, InlineSkillResource

skill = InlineSkill(
    name="company-policies",
    description="Company HR policies and guidelines",
    resources=[
        InlineSkillResource(
            name="leave-policy",
            content="Employees get 20 days PTO per year...",
            mime_type="text/plain",
        ),
    ],
)
1 技能的三种来源 点击展开详解
🧪 示例
技能可以从三种来源加载： 
# 1. 代码内联定义（InlineSkill）
skill = InlineSkill(name="...", resources=[...])

# 2. 文件系统加载（文件夹里放 .md/.py 等）
# samples/02-agents/skills/file_based_skill/

# 3. MCP 服务器提供（MCPSkill）
from agent_framework import MCPSkill
# 通过 MCP 协议远程获取技能
❓ 为什么这件事必要
Agent 光有工具（能做动作）不够——它还需要领域知识才能正确使用工具。 比如客服 Agent 需要知道公司的退货政策才能正确回答退货问题。 技能把"知识"变成可管理、可版本控制、可分享的模块。
✅ MAF 的做法与优点
MAF 把技能做成一等公民：Skill 对象有 name、description、resources（知识）、scripts（可执行代码）， 通过 SkillsSource 和 AggregatingSkillsSource 聚合多个来源。 Agent 在 run 时自动发现并注入相关技能到上下文。
🔀 还有什么其他方案
把知识硬编码进 instructions（简单但不可复用）； 用 ContextProvider + RAG（适合大规模知识库，但缺少"脚本"能力）； 用 MCP 资源（通过协议暴露知识，MAF 的 MCPSkill 正是这种方式）。
2 SkillResource vs SkillScript 点击展开详解
🧪 示例
SkillResource 是只读知识（文本、文档、数据文件）， SkillScript 是可执行代码（Python 脚本片段）： 
# Resource: 只读知识
InlineSkillResource(name="faq", content="Q: ... A: ...")

# Script: 可执行代码
InlineSkillScript(name="calc", code="result = price * 1.1")
❓ 为什么这件事必要
有些领域知识是静态的（退货政策文档），有些需要动态计算（税率计算公式）。 把两者都放在技能里，Agent 既能读知识又能跑计算。
✅ MAF 的做法与优点
Resource 和 Script 都挂在同一个 Skill 下，通过 SkillFrontmatter 描述元数据（名称、描述、兼容性）。 框架在 Agent run 时把 Resource 内容注入上下文，Script 则可通过 SkillScriptRunner 执行。
🔀 还有什么其他方案
Tool 里内嵌知识（不够模块化）； 独立的知识管理服务（更灵活但更复杂）； LangChain 的 Document + Retriever（纯检索，不支持脚本执行）。
3 技能发现与聚合 点击展开详解
🧪 示例
多个来源的技能可以聚合：

❓ 为什么这件事必要
真实项目里知识来自多处：团队内部文档、外部 API、代码库。 AggregatingSkillsSource 让你把这些来源统一聚合， Agent 只需要从一个入口发现所有可用技能。
✅ MAF 的做法与优点
聚合是可插拔的：每个 SkillsSource 独立实现 "列出技能" 接口， AggregatingSkillsSource 合并它们。新来源只需实现 SkillsSource 协议。
🔀 还有什么其他方案
单一来源硬编码（简单但不可扩展）； 用搜索引擎做技能发现（更灵活但更复杂）； 用 MCP resource 列表（协议标准化，但要求所有来源都支持 MCP）。

22 · MCP 工具协议

MCP（Model Context Protocol）是连接工具/资源到 LLM 的开放标准—— MAF 既能调用 MCP 服务器上的工具，也能把 Agent 自身暴露为 MCP 服务器。

📚 生活类比
MCP 就像USB 接口标准：不管你插的是键盘、鼠标还是硬盘，只要都走 USB 协议就能即插即用。 MCP 让 LLM 和工具之间有了统一的"接口协议"，不用为每个工具写定制代码。

三种传输方式

传输类型类名适用场景
Stdio（子进程）MCPStdioTool本地 CLI 工具，开发/测试阶段最常用
HTTP/SSE（Streamable HTTP）MCPStreamableHTTPTool远程 Web API，生产部署首选
WebSocketMCPWebsocketTool需要双向实时通信的场景

连接 MCP 服务器

使用 MCPStdioTool
from agent_framework import Agent, MCPStdioTool

mcp_tool = MCPStdioTool(
    name="filesystem",
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/data"],
)

async with Agent(
    client=client,
    tools=mcp_tool,
    name="fs-agent",
) as agent:
    response = await agent.run("List all .txt files")
1 三种传输方式深入 点击展开详解
🧪 示例
三种传输各有用法： 
# 1. Stdio — 本地子进程
MCPStdioTool(name="fs", command="npx", args=["-y", "server-fs"])

# 2. HTTP/SSE — 远程 Web 服务
MCPStreamableHTTPTool(name="api", url="https://api.example.com/mcp")

# 3. WebSocket — 双向实时
MCPWebsocketTool(name="rt", url="wss://service.example.com/mcp")
❓ 为什么这件事必要
不同部署环境需要不同传输方式：本地开发用 Stdio 最方便（无需网络）， 生产环境用 HTTP/SSE 最稳定，需要实时双向推送时用 WebSocket。 统一基类 MCPTool 让上层 Agent 代码无需关心传输细节。
✅ MAF 的做法与优点
三个子类都继承自 MCPTool（2400+ 行），自动处理连接生命周期、 工具发现和 JSON-RPC 通信。通过 MCPTaskOptions 统一配置超时、 取消策略等。Agent 使用 async with 自动管理连接。
🔀 还有什么其他方案
直接用 HTTP REST（简单但无标准化的工具发现协议）； gRPC（高性能但 LLM 生态支持少）； LangChain ToolNode（框架内工具，不跨框架通用）。
2 MCP 审批模型 点击展开详解
🧪 示例
MCPTaskOptions 控制长时间任务的生命周期： 
from datetime import timedelta
from agent_framework import MCPStdioTool, MCPTaskOptions

tool = MCPStdioTool(
    name="long-task",
    command="python", args=["server.py"],
    task_options=MCPTaskOptions(
        default_ttl=timedelta(minutes=2),
        max_task_wait=timedelta(minutes=5),
        cancel_remote_task_on_local_cancellation=True,
    ),
)
❓ 为什么这件事必要
有些 MCP 工具执行时间很长（数据分析、文件转换等）， 需要轮询状态、超时控制和取消机制。 MCPTaskOptions 透明处理 tools/call → tasks/get → tasks/result 生命周期。
✅ MAF 的做法与优点
遵循 SEP-2663 长时间任务规范：提交任务后自动轮询， 支持取消时自动清理远端资源，对不支持 tasks 的旧服务器自动降级。 还有 header_provider 做认证注入（如 Bearer token）。
🔀 还有什么其他方案
手动轮询 + 超时（繁琐且容易出错）； 后台任务队列（如 Celery，太重量级）； Server-Sent Events（HTTP SSE 已内置在 MCPStreamableHTTPTool 中）。
3 Agent 作为 MCP 服务器 点击展开详解
🧪 示例
MAF Agent 不仅能调用 MCP 工具，还能作为 MCP 服务器被其他客户端调用： 
# samples/02-agents/mcp/agent_as_mcp_server.py
# Agent 把自身注册为 MCP 服务器
# 外部 MCP 客户端可以调用此 Agent 的能力
# 实现 Agent ↔ Agent 的 MCP 互调
❓ 为什么这件事必要
多 Agent 系统中，一个 Agent 的能力可以被其他 Agent 通过标准 MCP 协议复用。 比如一个"翻译 Agent"作为 MCP 服务器暴露自己的翻译能力， 其他 Agent 通过 MCPStdioTool 调用它——无需知道内部实现。
✅ MAF 的做法与优点
框架双向支持 MCP：消费端通过三种传输类型调用外部工具， 服务端把 Agent 能力暴露为 MCP 工具。 这让 MAF Agent 可以无缝融入任何 MCP 生态系统。
🔀 还有什么其他方案
A2A 协议（Agent-to-Agent，更高层的 Agent 互调协议）； 自定义 REST API（灵活但缺乏标准化发现机制）； 消息队列（适合异步场景但延迟较高）。
4 MCP vs 直接 @tool 点击展开详解
🧪 示例
对比两种方式： 
# 直接 @tool —— 代码内定义
@tool
def read_file(path: str) -> str:
    return open(path).read()

# MCP Tool —— 外部服务提供
MCPStdioTool(name="fs", command="npx",
    args=["-y", "server-fs", "/data"])
❓ 为什么这件事必要
@tool 是进程内的 Python 函数，简单快速但只限本项目使用； MCP Tool 走标准协议，可以跨语言、跨项目、跨框架复用。 两者可以混合使用——Agent(tools=[my_tool, mcp_tool])。
✅ MAF 的做法与优点
MAF 统一了两种工具模型：@tool 和 MCPTool 都实现相同的工具接口， Agent 无需区分工具来源。MCP 工具的 schema 通过协议自动发现， 无需手动维护 JSON Schema。
🔀 还有什么其他方案
全部用 @tool（最简单但不可跨项目复用）； 全部用 MCP（最标准化但本地简单工具开销大）； OpenAPI 插件（REST 标准化但缺少 LLM 特有的工具发现）。
✅ 关键要点
  • MCP 是 LLM 工具连接的开放标准——即插即用，跨框架通用。
  • 三种传输：Stdio（本地开发）、HTTP/SSE（生产部署）、WebSocket（实时通信）。
  • MCPTaskOptions 处理长时间任务的超时、轮询和取消。
  • MAF Agent 既能调用 MCP 工具，也能作为 MCP 服务器暴露能力。
💡 设计亮点
@tool 和 MCPTool 在 Agent 眼里没有区别——都是"能做事的工具"。 你可以从 @tool 起步做快速原型，之后把成熟的工具迁移为 MCP 服务， 实现从本地开发到标准化分发的平滑过渡。

23 · Foundry 托管 Agent

Foundry 托管 Agent——只需 ~2 行额外代码，就能把本地 Agent 部署到 Azure AI Foundry 云端， 获得自动伸缩、会话管理和企业级监控。

📚 生活类比
本地跑 Agent 像在自家厨房做饭（灵活但只能服务自己）； Foundry 托管就像把菜谱交给云厨房——它帮你准备食材、管理订单、扩容厨师，你只管出菜谱。

两种托管模式

模式类名特点适用场景
Responses APIResponsesHostServer完整的 Azure AI Foundry Responses 协议，支持流式、审批工作流需要与 Foundry 生态深度集成
InvocationsInvocationsHostServer轻量级 JSON 请求/响应，支持流式快速部署，简单场景

最小托管模式

Invocations 模式
from agent_framework_foundry_hosting import InvocationsHostServer

server = InvocationsHostServer(agent=my_agent)
server.run()
# 就这么简单——Agent 已在云端运行！
1 Responses vs Invocations 点击展开详解
🧪 示例
两种模式的初始化： 
# Responses 模式 — 完整 Foundry API 集成
from agent_framework_foundry_hosting import ResponsesHostServer
server = ResponsesHostServer(agent=my_agent)

# Invocations 模式 — 轻量级 JSON
from agent_framework_foundry_hosting import InvocationsHostServer
server = InvocationsHostServer(agent=my_agent)
❓ 为什么这件事必要
不同场景对 API 复杂度要求不同：Responses 模式提供完整的 Foundry Responses API （包括类型转换、审批存储、流式事件），适合企业级集成； Invocations 模式更简洁，适合快速原型和简单部署。
✅ MAF 的做法与优点
两种模式都自动管理 AgentSession（按 session_id 隔离会话状态）， 支持流式响应（StreamingResponse）， 且都用 async 实现高并发。切换模式只需换一个类名。
🔀 还有什么其他方案
自建 FastAPI 服务（灵活但要自己处理会话管理、伸缩）； LangServe（LangChain 的部署方案，不兼容 Foundry 生态）； 容器化 + K8s（完全自主但运维成本高）。

✅ MAF 的做法与优点
只需 pip install + 2-3 行代码，Agent 就变成可部署的 Web 服务。 ResponsesHostServer 还自动处理 Responses API 的类型转换（Message → Item）和 ApprovalStorage（函数调用审批）。
🔀 还有什么其他方案
Azure Container Apps（更底层控制但更多配置）； AWS Lambda + API Gateway（无服务器但冷启动慢）； 自建 Docker + Nginx（完全自主但运维成本高）。

🔀 还有什么其他方案
FastAPI + Agent.run()（自建最灵活）； A2A 协议（跨系统 Agent 互调）； MCP 服务器模式（把 Agent 暴露为 MCP 工具供其他系统调用）。
✅ 关键要点
  • 两种模式：ResponsesHostServer（完整 Foundry API）和 InvocationsHostServer（轻量 JSON）。
  • ~2 行代码把本地 Agent 变成云端服务——会话管理、伸缩、监控自动搞定。

24 · A2A + AG-UI 协议

A2A（Agent-to-Agent）让 Agent 作为服务暴露给其他 Agent 调用； AG-UI让 Agent 与前端 UI 实时结构化通信——两个协议合力打通"Agent ↔ Agent"和"Agent ↔ 用户界面"。

📚 生活类比
A2A 像企业间的 B2B 接口——公司 A 的 Agent 可以调用公司 B 的 Agent 服务； AG-UI 像客服前台的显示屏——后台 Agent 的进度、中间结果实时推送到用户看到的界面上。

✅ MAF 的做法与优点

🔀 还有什么其他方案
Server-Sent Events 自定义（灵活但没有标准事件格式）； WebSocket 自定义（双向但要自己定义协议）； Vercel AI SDK useChat（前端友好但绑定 Vercel 生态）。
3 A2A + AG-UI 组合 点击展开详解
🧪 示例

# 用户看到：Agent B 返回了翻译结果...
❓ 为什么这件事必要
真实场景中，用户需要看到多 Agent 协作的全过程： A2A 管理 Agent 间的调用，AG-UI 把过程实时展示给用户。 两者缺一不可——缺了 A2A 就没有 Agent 互调，缺了 AG-UI 用户就看不到过程。
✅ MAF 的做法与优点
两个协议正交设计：A2A 解决"Agent 间如何通信"，AG-UI 解决"Agent 如何向用户汇报"。 框架内的事件（usage、custom events）自动映射到 AG-UI 的 CUSTOM 事件类型， 多模态内容（图片、文件）也有标准化支持。
🔀 还有什么其他方案
单体 Agent + 直接 UI（简单但不可扩展到多 Agent）； 消息总线 + 自定义 UI 协议（灵活但开发量大）； LangGraph Studio（可视化调试但不是生产 UI 方案）。
4 什么时候用哪个 点击展开详解
🧪 示例
选择指南： 
# 需要 Agent 互相调用？ → A2A
# 需要向用户实时展示进度？ → AG-UI
# 需要跨框架工具复用？ → MCP (L24)
# 需要云端托管？ → Foundry Hosting (L25)

# 多 Agent + 用户界面 → A2A + AG-UI 组合
# 单 Agent + 简单部署 → Foundry Hosting
❓ 为什么这件事必要
MAF 提供了多种"对外暴露"方式（MCP / Foundry / A2A / AG-UI）， 选错方式会增加不必要的复杂度。理解每种协议的定位才能做出正确选择。
✅ MAF 的做法与优点
每种协议都是可选的薄包装层——Agent 核心逻辑完全不变。 你可以先用 Foundry 托管单 Agent，之后加 A2A 做多 Agent 协作， 再加 AG-UI 做实时 UI。渐进式采用，不用一次全上。
🔀 还有什么其他方案
全部 REST API 自定义（最灵活但重复造轮子）； GraphQL subscriptions（适合复杂查询但 Agent 场景过于复杂）； gRPC streaming（高性能但生态支持有限）。
✅ 关键要点
  • A2A：Agent-to-Agent 协议——A2AAgent（客户端）+ A2AExecutor（服务端），支持 AgentCard 发现。
  • AG-UI：Agent-to-UI 协议——AgentFrameworkAgent 包装 + FastAPI 端点一行集成。
  • 两者正交：A2A 管"Agent 间"，AG-UI 管"Agent → 用户"，可独立或组合使用。
  • 所有协议都是可选薄层，Agent 核心代码不变。
💡 设计亮点
四种协议（MCP / Foundry / A2A / AG-UI）覆盖 Agent 对外通信的所有方向： 工具调用、云端托管、Agent 互调、UI 推送。 每个都是可选的薄适配层——Agent 核心逻辑写一次，按需插上不同的"通信插头"。
第六部分 · 协议与生态

25 · 评估与时间旅行

Evaluation（评估）系统化测试 Agent 输出质量； Time-travel（时间旅行）通过检查点回放调试工作流——两者合力让 Agent 从"能跑"进化到"可靠"。

📚 生活类比
Evaluation 像考试阅卷——给 Agent 一组题目，用评分标准打分看它答得好不好； Time-travel 像比赛录像回放——出了问题可以倒回任意时刻，逐帧分析哪里出了错。

核心评估概念

概念作用源码
EvalItem一条评估数据 = 输入 + 预期输出_evaluation.py
Evaluator评估器协议（Azure Foundry / 本地 LLM-as-judge / 自定义）_evaluation.py
RubricScore多维度评分（如相关性、准确性、完整性）_evaluation.py
EvalResults评估结果汇总（通过率、每项得分、报告链接）_evaluation.py

手动测试（不可重复、不可扩展）； OpenAI Evals（OpenAI 专属）； RAGAS（专注 RAG 评估）； LangSmith（LangChain 生态的追踪 + 评估）。
2 RubricScore 多维评分 点击展开详解
🧪 示例

# EvalScoreResult 中的维度评分
# score.dimensions 包含：
#   RubricScore(name="relevance", score=0.9)

✅ MAF 的做法与优点
EvalScoreResult 包含总分 + 维度分 + 原始理由（sample）。 AgentEvalConverter 自动把 Agent 的输入输出转换为评估格式。 结果可直接 raise_for_status() 用于 CI 门控。
🔀 还有什么其他方案
LLM-as-judge 单维度（简单但信息量少）； 人工标注（最准确但成本高、速度慢）； 自定义 scorer 函数（灵活但需要更多代码，MAF 的 @evaluator 就是简化版）。
3 Time-travel 机制 点击展开详解
🧪 示例
通过检查点实现工作流回放： 
from agent_framework import InMemoryCheckpointStorage

storage = InMemoryCheckpointStorage()
workflow = builder.build()

# 首次运行——保存检查点
async for event in workflow.run(message=10, stream=True):
    if should_interrupt(): break

# 从检查点恢复——跳过已完成的步骤
cp = await storage.get_latest(workflow_name=workflow.name)
async for event in workflow.run(
    checkpoint_id=cp.checkpoint_id, stream=True
):
    # 已完成的 @step 直接返回缓存结果
    # 只有未完成的步骤真正执行
❓ 为什么这件事必要
工作流可能因为网络故障、超时或人为中断而停在中途。 没有检查点就得从头重跑（浪费时间和 token 费用）。 Time-travel 让你从断点继续，已完成的步骤用缓存结果跳过。
✅ MAF 的做法与优点
WorkflowCheckpoint 捕获完整状态：消息历史、Executor 状态、 迭代计数、待处理的 HITL 事件。 CheckpointStorage 协议有内存和文件两种实现。 Executor 通过 on_checkpoint_save/restore 钩子保存自定义状态。
🔀 还有什么其他方案
Durable Functions（Azure 的持久化执行，更底层）； Temporal.io（专业的工作流引擎，更重量级）； 手动保存中间状态（可行但容易遗漏边界情况）。
4 评估 + 回放组合 点击展开详解
🧪 示例
评估和 time-travel 可以组合使用： 
# 1. 跑评估，发现某个 query 失败
results = await evaluate_agent(agent=agent, queries=[...])

# 2. 对失败 query 的工作流做 time-travel 调试
# 从检查点回放，逐步检查每个 @step 的输入输出

# 3. 修复后重新评估，确认改进
# results[0].raise_for_status() 通过 = 修复成功
❓ 为什么这件事必要
评估发现问题，time-travel 定位原因——这是发现 → 诊断 → 修复 → 验证的完整闭环。 没有 time-travel，你只知道"这个 query 失败了"但不知道哪个步骤出了问题。
✅ MAF 的做法与优点
评估和回放共享同一套 Agent / Workflow 抽象——评估跑 agent.run()， 回放也跑 workflow.run(checkpoint_id=...)。 HITL 场景下 _set_responses 可以预填人类回复，让回放完全自动化。
🔀 还有什么其他方案
纯日志分析（信息量不如检查点完整）； LangSmith Trace（可视化追踪但不能从断点恢复执行）； 单元测试 mock（快但不测真实 LLM 行为）。
✅ 关键要点
  • 评估 = Agent 的单元测试：EvalItem（输入）→ Evaluator（打分）→ EvalResults（结果）。
  • RubricScore 支持多维度评分；raise_for_status() 用于 CI 门控。
  • Time-travel通过 WorkflowCheckpoint 保存/恢复完整状态，已完成步骤用缓存跳过。
  • 两者组合实现"发现问题 → 定位原因 → 修复 → 验证"的完整闭环。
💡 设计亮点
评估和回放共享同一套 Agent/Workflow 抽象——不需要额外的调试工具或追踪系统。 一个 evaluate_agent() 调用 = 批量跑 Agent + 自动评分 + CI 集成。 一个 checkpoint_id 参数 = 从任意断点恢复执行，逐步诊断问题。

1 MAF vs LangGraph 深入对比 点击展开详解
🧪 示例
同一件事——"两个 Agent 串行"——在两个框架里的写法： 
# MAF：用 SequentialBuilder
from agent_framework.orchestrations import SequentialBuilder
wf = SequentialBuilder(participants=[writer, reviewer]).build()
result = await wf.run("Write a poem")

# LangGraph：手画 StateGraph
from langgraph.graph import StateGraph
graph = StateGraph(State)
graph.add_node("writer", writer_fn)
graph.add_node("reviewer", reviewer_fn)
graph.add_edge("writer", "reviewer")
app = graph.compile()
result = app.invoke({"input": "Write a poem"})
❓ 为什么这件事必要
LangGraph 是 LangChain 生态的图编排层，用户基数大、文档丰富。 做技术选型时，这两个框架经常被放到一起比较，你需要知道它们的本质差异在哪—— 是"图模型"还是"编排抽象层级"。
✅ MAF 的做法与优点
MAF 提供两个抽象层：底层 WorkflowBuilder（和 LangGraph 的 StateGraph 同级，手动画图）， 上层预置编排（Sequential / Concurrent / Handoff / Group / Magentic）。大部分场景用预置编排几行搞定， 复杂拓扑再下沉到手动图。LangGraph 只有手动图这一级——简单任务也要手画。 另外 MAF 原生双语言（Python + .NET），LangGraph 主要 Python。
🔀 还有什么其他方案
LangGraph 适合已在 LangChain 生态里、需要最细粒度图控制的团队。 两者混用也是可行的——用 MAF 的 Agent + ChatClient，但用 LangGraph 做编排（它们不冲突，只是编排层替换）。 Temporal / Prefect等通用工作流引擎也能编排 Agent，但缺乏 AI 原生抽象。
2 MAF vs AutoGen 深入对比 点击展开详解
🧪 示例
AutoGen 的范式是"多个 Agent 在群聊里对话"： 
# AutoGen 风格（MAF 里用 MagenticBuilder 实现）
from agent_framework.orchestrations import MagenticBuilder
wf = MagenticBuilder(
    participants=[coder, reviewer, tester],
    manager=manager,
).build()
result = await wf.run("Build a calculator app")
AutoGen 原版需要自己搭 GroupChat + GroupChatManager， MAF 把这个模式封装成了 MagenticBuilder。
❓ 为什么这件事必要
AutoGen 是微软研究院出的多 Agent 框架，开创了"多 Agent 对话"范式。 MAF 直接继承了 AutoGen 的 Magentic-One 思想（指挥官 + 工人）， 所以了解两者关系能帮你判断"用 MAF 就够了，还是仍需要原版 AutoGen"。
✅ MAF 的做法与优点
MAF 把 AutoGen 的多 Agent 对话做成了编排模式之一（MagenticBuilder / GroupChatBuilder）， 而不是唯一范式。你可以在同一个项目里混用 Sequential（简单串行）和 Magentic（指挥官调度）， 而 AutoGen 里所有事都是"对话"，简单任务也被迫用群聊。 另外 MAF 的生产特性（检查点、OTel、DurableTask）远超 AutoGen。
🔀 还有什么其他方案
原版 AutoGen 仍适合纯研究 / 快速原型（API 更简单，社区活跃）。 CrewAI 是另一个多 Agent 框架，角色定义更"人性化"但生产特性弱。 如果你只要"两个 Agent 对话"，不需要编排引擎，手写循环其实最简单。
3 MAF vs Semantic Kernel 深入对比 点击展开详解
🧪 示例
SK 的核心抽象是 Kernel + Plugin + Planner： 
# Semantic Kernel 风格
kernel = Kernel()
kernel.add_plugin(WeatherPlugin(), "weather")
result = await kernel.invoke_prompt("What's the weather in Seattle?")

# MAF 风格——同样的事

    instructions="Answer weather questions.")
result = await agent.run("What's the weather in Seattle?")
❓ 为什么这件事必要
Semantic Kernel 是 MAF 的前身之一——很多企业已经在用 SK。 理解 SK → MAF 的演进，能帮已有 SK 用户判断是否迁移、怎么迁移。
✅ MAF 的做法与优点
SK 强在企业连接器（几十种现成 Plugin）和Planner（LLM 自动规划步骤）。 MAF 继承了这些能力，并新增：图式 Workflow 编排（SK 没有）、多 Agent 协作（SK 没有）、 DurableTask 持久化、统一的 ChatClient 抽象（SK 的 ChatCompletionService 更分散）。 MAF 是微软官方推荐的"下一代"方向。
🔀 还有什么其他方案
继续用 SK——如果已有大量 SK Plugin 且不需要多 Agent / 工作流，短期内不急着迁。 渐进迁移——SK 和 MAF 可以共存，先在新功能上用 MAF，老功能保持 SK。 直接 MAF——新项目建议直接用 MAF，因为 SK 的维护重心已转向 MAF。

❓ 为什么这件事必要
社区大小影响：遇到问题能不能搜到答案、有没有第三方插件、招聘时候选人熟不熟。 这不是技术问题，但实际上经常是选型的决定性因素。
✅ MAF 的做法与优点
MAF 虽年轻但背靠微软全力推：官方文档在 MS Learn、有 Discord 社区、 与 Azure AI Foundry 深度集成。企业用户天然信任微软背书。 且 MAF 吸收了 SK + AutoGen 两个社区的用户，增长曲线陡。
🔀 还有什么其他方案
如果你最看重社区和生态丰富度，LangChain 仍是最大的。 如果看重学术前沿，AutoGen 论文产出最多。 如果看重企业稳定性 + 微软生态，MAF 或 SK。 没有"最好"——只有"最适合你的场景"。
✅ 关键要点
  • MAF = SK + AutoGen 合并演进，面向"原型到生产"。
  • LangGraph 强在图控制流精度；AutoGen 强在多 Agent 对话探索。
  • 选框架看你的核心需求：语言、生产特性、控制粒度、社区生态。
  • MAF 提供两层抽象（预置编排 + 手动图），覆盖从简到繁。
💡 设计亮点
MAF 把"图编排"和"多 Agent 对话"统一到同一个框架——你不用在 LangGraph 和 AutoGen 之间二选一。 预置编排是糖，底层 Workflow 是引擎，两者可以混用。

1 L5 推理层深入 点击展开详解
🧪 示例
推理层的三种选择： 
# vLLM — 高吞吐 GPU 推理服务
vllm serve meta-llama/Llama-3-8B --port 8000

# llama.cpp — CPU / 边缘设备推理
./main -m model.gguf -p "Hello"

# Ollama — 本地一键跑模型
ollama run llama3
❓ 为什么这件事必要
MAF 通过 ChatClient 调用模型，但模型从哪来？如果你用 OpenAI API 就不用管； 但如果要私有化部署（数据安全、成本控制、低延迟），就需要了解推理层。 vLLM 适合高并发 GPU 场景，llama.cpp 适合边缘/嵌入式，Ollama 适合开发者本地调试。
✅ MAF 的做法与优点
MAF 不绑定推理层：OpenAIChatClient 可以指向任何兼容 OpenAI API 的端点 （vLLM、llama.cpp 的 server 模式、Ollama 都兼容）。所以你可以先用 OpenAI API 开发， 上线时切到私有 vLLM，Agent 代码不用改。
🔀 还有什么其他方案
TGI（HuggingFace 的推理服务器）、TensorRT-LLM（NVIDIA 优化）、 Azure AI Foundry（托管推理，零运维）。如果你不想自己运维 GPU，用云端 API 最省心。
2 L4 向量检索 / RAG 深入 点击展开详解
🧪 示例
向量检索的核心流程： 
# 1. 文本 → Embedding 向量
vector = embedding_model.encode("What is MAF?")

# 2. 向量存入数据库
db.insert(vector, metadata={"source": "docs/readme.md"})

# 3. 查询时找最相似的向量
results = db.search(query_vector, top_k=5)

# 4. 把检索到的文本塞给 Agent 作上下文
context = "\n".join(r.text for r in results)
await agent.run(f"Based on: {context}\nAnswer: {question}")
❓ 为什么这件事必要
LLM 不知道你的私有数据。RAG（检索增强生成）通过在提示词里塞进相关文档片段， 让模型能"看到"你的知识库。向量检索是 RAG 的核心引擎——把"语义相似度"变成数据库查询。
✅ MAF 的做法与优点
MAF 通过 ContextProvider 机制集成 RAG： packages/azure-ai-search 封装了 Azure AI Search（企业级向量检索）， 你也可以自己写 ContextProvider 接 pgvector / Qdrant / Pinecone。 Agent 不需要知道知识从哪来——ContextProvider 在 run 前自动注入。
🔀 还有什么其他方案
pgvector（熟悉 SQL 的首选，PostgreSQL 扩展）、 Qdrant（云原生向量数据库，专为向量设计）、 Chroma（轻量嵌入式，适合本地原型）、 Azure AI Search（企业级，MAF 有现成包）。
3 L7 应用层深入 点击展开详解
🧪 示例
把 MAF Agent 暴露为 Web 端点： 
# FastAPI + MAF Agent
from fastapi import FastAPI
app = FastAPI()

@app.post("/chat")
async def chat(prompt: str):
    result = await agent.run(prompt)
    return {"response": str(result)}
❓ 为什么这件事必要
Agent 不能只在终端里跑——最终要面向用户。应用层负责UI、API、认证、限流等。 了解怎么把 Agent 包成 API / Web 应用，是从"能跑"到"能用"的关键一步。
✅ MAF 的做法与优点
MAF 的 hosting 包提供了多种部署方式： ASP.NET Core / Azure Functions（.NET 端）、 FastAPI / Azure Functions（Python 端）、 A2A 协议（Agent-to-Agent，让 Agent 作为服务被其他 Agent 调用）、 Foundry 托管 Agent（零运维部署到 Azure）。
🔀 还有什么其他方案
Chainlit（一行代码搞定聊天 UI，适合 demo）、 Streamlit（快速数据应用 + 聊天界面）、 Gradio（ML demo 界面）、 自建 React/Vue 前端（最灵活但工作量最大）。
