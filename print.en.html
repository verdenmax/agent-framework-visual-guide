Part 1 · Big Picture

01 · What is Agent Framework

Microsoft Agent Framework (MAF) is an open-source framework written in Python and .NET that connects large language models (LLMs) to real apps and orchestrates them into useful agents and multi-agent workflows. It does not train models — it owns all the plumbing around the model, and it is built for production.

🔌 Analogy
Think of an LLM as a powerful but isolated engine: it emits text, but knows nothing about your database, can't call tools by itself, and every vendor's interface is different. MAF is the standardized "drivetrain + dashboard + connector kit" — drive any engine with one codebase, wire it to tools, memory and other agents, and monitor, restart and gate it in production.

What does it actually solve?

Calling a vendor SDK directly works, but real apps hit these pain points fast — exactly what MAF smooths over:

PainWithout a frameworkWhat MAF does
Vendor lock-inSwitching models rewrites a lot of codeOne ChatClient + Agent; switching vendors is ~one line
Assembling chatHand-build role/content dictsStructured Message / Role / Content
Calling toolsParse which function & args yourself@tool auto-generates schema + parses + executes
Multi-step / multi-agentHand-write the think–act loop & coordinationAgent loop + graph-based Workflows
Going to productionRoll your own tracing, persistence, approvalsBuilt-in OpenTelemetry, checkpoints, human-in-the-loop, hosting

What the smallest agent looks like

samples/01-get-started/01_hello_agent.pyminimal
from agent_framework import Agent
from agent_framework.foundry import FoundryChatClient
from azure.identity import AzureCliCredential

client = FoundryChatClient(
    project_endpoint="https://your-project.services.ai.azure.com",
    model="gpt-4o", credential=AzureCliCredential(),
)
agent = Agent(
    client=client, name="HelloAgent",
    instructions="You are a friendly assistant. Keep your answers brief.",
)

result = await agent.run("What is the capital of France?")
print(result)

Three steps: pick a ChatClient (connect to a model) → wrap it in an Agent (name + system instructions) → run a prompt. Switch vendors by replacing FoundryChatClient with OpenAIChatClient — nothing else changes.

1 How does it relate to LangChain / AutoGen / Semantic Kernel? expand
❓ One-line positioning
MAF is Microsoft's convergence of Semantic Kernel (enterprise, strongly typed, rich connectors) and AutoGen (multi-agent conversations & research), into one framework aimed at prototype-to-production, with aligned Python and .NET implementations.
✅ Its trade-offs
It wants both LangGraph-style graph orchestration (controllable, resumable) and AutoGen-style multi-agent collaboration, while making observability / persistence / approvals first-class — that's what "production-grade" means.
2 How do you escape vendor lock-in? expand
🧪 Example
Each SDK looks different: 
# OpenAI
from openai import OpenAI
client = OpenAI()
r = client.chat.completions.create(model="gpt-4o", messages=[...])

# Anthropic
from anthropic import Anthropic
client = Anthropic()
r = client.messages.create(model="claude-3-7-sonnet", max_tokens=1024, messages=[...])
With MAF only the client swaps; the rest stays: 
from agent_framework import Agent
from agent_framework.openai import OpenAIChatClient
# from agent_framework.anthropic import AnthropicClient  # only this line changes
agent = Agent(client=OpenAIChatClient(model="gpt-4o"), instructions="…")
await agent.run("hi")
❓ Why this matters
Three very real reasons:
① cost — pricing for the same task differs 5–20× across models;
② fast model turnover — a new SOTA arrives every quarter; lock-in means missing it;
③ compliance & availability — finance/gov demand private deployment; some regions need Foundry, others a corporate gateway.
✅ How MAF does it
MAF abstracts every vendor into a uniform ChatClient interface. FoundryChatClient, OpenAIChatClient, AnthropicClient and OllamaChatClient all implement the same surface (get_response(), get_streaming_response()). Agents, tools and workflows depend on the interface only.
🔀 Alternatives
① LiteLLM — external proxy speaking OpenAI's protocol; simple, but one extra hop & service.
② Hand-rolled adapter — exact fit for your domain, but you maintain streaming/tools/function-call differences.
③ Cloud gateways (Azure AI Gateway / AWS Bedrock) — great for compliance & quotas, still locks you to one cloud.
3 How to assemble conversations safely? expand
🧪 Example
Raw dict vs MAF's typed messages: 
# Raw dict — typos in "role" only surface at runtime
messages = [
  {"role": "sytsem", "content": "You are helpful"},  # typo!
  {"role": "user",   "content": "hi"},
]

# MAF — type-safe, IDE completes everything
from agent_framework import Message
messages = [
  Message("system", "You are helpful"),
  Message("user", "hi"),
]
❓ Why this matters
Real workloads carry more than strings: images, tool calls, tool results, thinking blocks, citations. Raw dicts force a project-wide if/else rewrite for each new kind; typed Contents means adding a new content type leaves old code untouched.
✅ How MAF does it
See agent_framework/_types.py: Role is an enum (system / user / assistant / tool), Message holds contents: list[Contents], and Contents is the union of Content — a unified type built via factory methods like Content.from_text(). Wins: ① static checking + completion; ② multimodal & tool results fit naturally; ③ free serialization for Workflow cross-process transport.
🔀 Alternatives
① Raw dicts + JSON Schema validation — light, but still runtime-only;
② Roll your own Pydantic models — MAF already is Pydantic v2 under the hood, you're reinventing it;
③ LangChain's HumanMessage / AIMessage — same idea, weaker content-block coverage.
4 Why not hand-write tool-call JSON? expand
🧪 Example
Raw function-calling vs MAF's @tool: 
# Raw SDK: write schema, dispatch, feed result back yourself
tools = [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "parameters": {"type": "object",
      "properties": {"city": {"type": "string"}},
      "required": ["city"]}}}]
# Then: parse tool_calls → find function → invoke → append result → call again…

# MAF: decorator generates schema, agent runs the loop
from agent_framework import tool

@tool
def get_weather(city: str) -> str:
    "Return the weather for a city."
    return f"{city} is 23°C"

agent = Agent(client=client, tools=[get_weather])
❓ Why this matters
Hand-written JSON schema breeds three bug families: ① parameter names/types drift from the function signature; ② you change the function and forget the schema; ③ each vendor supports a different JSON-Schema subset. Auto-generation makes the function the contract; refactor cost goes to zero.
✅ How MAF does it
@tool (see _tools.py) uses inspect + type hints to produce a JSON Schema, auto-injects it into ChatClient requests; when the model returns FunctionCallContent, the Agent — in the same loop — executes the function, appends FunctionResultContent to the messages, and calls the model again. No glue code from you.
🔀 Alternatives
① Hand-written schema — max control, max error rate;
② OpenAI's official function-calling SDK — OpenAI-only;
③ LangChain Tool / StructuredTool — similar idea, no native middleware/Workflow integration;
④ MCP protocol — out-of-process tool hosting; MAF can also surface MCP tools as local ones.
5 Multi-step & multi-agent without a while-monster? expand
🧪 Example
Hand-rolled loops go bad fast: 
messages = [...]
while True:
    resp = client.chat.completions.create(model=..., messages=messages, tools=tools)
    msg = resp.choices[0].message
    if not msg.tool_calls:
        break
    for tc in msg.tool_calls:
        result = dispatch(tc.function.name, json.loads(tc.function.arguments))
        messages.append({"role": "tool", ...})
    # No max iterations, no retries, no observability…

# MAF: delegated to agent.run() / Workflow
agent = Agent(client=client, tools=[get_weather, search_web])
result = await agent.run("Check Shanghai weather then suggest what to wear")
❓ Why this matters
"Loop" sounds simple. Productionizing it requires max-iteration limits, retries on errors, context trimming, parallel tools, middleware hooks (trace/cost), inter-agent message routing, resumable checkpoints… each item is hundreds of lines and many tests.
✅ How MAF does it
Single agent → built-in loop with DEFAULT_MAX_ITERATIONS, middleware pipeline and streaming aggregation; multi-agent → agent_framework._workflows provides graph orchestration (nodes / edges / shared state / checkpoints / human approval), natively wired with ChatClient, tools and observability.
🔀 Alternatives
① LangGraph — original graph orchestrator, tightly coupled to LangChain;
② CrewAI — role-based multi-agent; ergonomic but light on productionization;
③ Hand-rolled state machines / Temporal / Durable Functions — robust but disconnected from LLM semantics, you rebuild the tool loop yourself.
✅ Key points
  • MAF = ChatClient (model) + Agent (loop) + Tools + Workflows + production features.
  • It does not train models; it owns the plumbing. Python and .NET both.
  • Positioning: the unified successor to Semantic Kernel + AutoGen, prototype to production.
💡 Design highlight
"Switch models with one line" is the default: the ChatClient is a vendor-agnostic abstraction, and agents / tools / workflows are all built on top — so portability is free from line one.

🏢 Analogy
Picture the repo as an office building: core is the foundation and load-bearing walls (everyone depends on it), each provider package is a department on a floor (OpenAI, Anthropic…), and lab is the rooftop R&D lab (cutting-edge, unstable). The Python tower and the .NET tower stand side by side with the same floor plan.

1 What lives inside the core package? expand
🧪 Example
core is "one file, one job": 
python/packages/core/agent_framework/
├── _agents.py        # Agent class, run() loop, DEFAULT_MAX_ITERATIONS
├── _clients.py       # BaseChatClient ABC + Supports* protocols
├── _tools.py         # @tool decorator, FunctionTool class
├── _middleware.py    # middleware pipeline: trace / retry / custom
├── _types.py         # Message / Role / Contents union
├── _workflows/       # graph orchestration: nodes, edges, state, checkpoints
├── observability/    # OpenTelemetry traces / cost / token metrics
└── __init__.py       # public API — what `from agent_framework import` exposes
❓ Why this matters
If core is split into dozens of micro-packages, newcomers spend their first week learning imports; if it's a single god-module, you get circular deps, slow loads and untestable seams. "Single package, many internal files" is the standard, stable compromise: one import path, clean inner layering.
✅ How MAF does it
All abstractions are re-exported from agent_framework (Agent, Message, tool, WorkflowBuilder…); files prefixed with _ are internal and surfaced via __all__ in __init__.py — internal refactors never break user code.
🔀 Alternatives
① Single-file god-module — fastest start, long-term disaster;
② Micro-package architecture (one PyPI package per abstraction) — dependency hell;
③ Plugin-only — core ships interfaces, everything else is a plugin; flexible, no batteries included.
2 How does provider lazy-loading actually work? expand
🧪 Example
Submodule __init__.py defers imports with __getattr__: 
# agent_framework/azure/__init__.py (sketch)
import importlib
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from ._chat_client import AzureOpenAIChatClient

_LAZY = {"AzureOpenAIChatClient": "._chat_client"}

def __getattr__(name: str):
    if name in _LAZY:
        mod = importlib.import_module(_LAZY[name], __name__)
        return getattr(mod, name)
    raise AttributeError(name)

__all__ = list(_LAZY)
So import agent_framework doesn't drag in azure-identity; it loads only when you actually touch AzureOpenAIChatClient.
❓ Why this matters
① Startup speed — each extra SDK adds tens-to-hundreds of ms; critical for CLI & serverless;
② Optional dependencies — a user who only installed the OpenAI extras shouldn't crash on Anthropic imports;
③ Install size — core stays minimal, extras opt-in via pip install agent-framework[azure].
✅ How MAF does it
PEP 562 module-level __getattr__ combined with a TYPE_CHECKING-guarded real import — keeps lazy semantics at runtime while preserving full IDE / mypy navigation. Pyright and PyCharm jump-to-definition still work.
🔀 Alternatives
① Eager imports — simple but slow + polluted deps;
② entry_points / plugin protocol — full decoupling, harder discovery & debugging;
③ try/except ImportError — common trick, doesn't scale to many providers.

03 · Lifecycle of a Run

You write just one line — await agent.run("…") — but a chain of events happens underneath. Understand this lifecycle and every later "internals" lesson gets easy.

🍽️ Analogy
An Agent is like a waiter: you order (input) → they combine your words with the "house rules" (instructions) into a standard ticket (messages) → hand it to the kitchen (ChatClient → LLM) → if the chef says "fetch an ingredient first" (tool call), the waiter fetches it (executes the tool) and brings the result back → until the dish is ready (final answer), served to you (AgentResponse).

The full data flow of one run

1

Your input

A string or a list of Message, arriving together with conversation history.

2

Agent assembles

Combine instructions (system prompt) + history + new input + available tools into one request.

3

ChatClient call

The vendor-agnostic interface sends it to a concrete LLM (Foundry / OpenAI / …) and returns a ChatResponse.

4

Need a tool?

If the response contains a function_call, the Agent executes the function, appends the function_result to the messages, and loops back to step 3.

5

Converge & return

When the model stops asking for tools, the loop ends with an AgentResponse (or a stream of AgentResponseUpdate when streaming).

🌍 Big picture
This is the classic agent loop (think → act → observe): the model "thinks", the framework "acts" for it (runs tools), feeds the "observation" back, until done. You call run() once; the loop runs to completion internally.
1 In multi-turn chat, where does history come from? expand
🧪 Example

2 What does message assembly actually look like? expand
🧪 Example
The list sent to the LLM on one run() roughly looks like: 
[
  SystemMessage("You are a concise weather assistant."),  # ← instructions
  UserMessage("My name is Sam"),                          # ← history 1
  AssistantMessage("Hi Sam!"),                             # ← history 2
  UserMessage("Weather in Shanghai today?"),               # ← this input
]
tools = [
  {"name": "get_weather", "parameters": {...}},   # ← auto-generated
]
Instructions go first, history in chronological order, current input last, tool schemas attached alongside.
❓ Why this matters
Three hidden traps: ① system position — some models require system at index 0; ② context-window budget — history + tool schema + input must fit in the token cap; ③ tool-schema overhead — 20 tools can eat several thousand tokens.
✅ How MAF does it
In _agents.py the Agent assembles in a fixed order: instructions → system, tools → schema, history → ordered messages, with fallbacks for content kinds a ChatClient doesn't support. Callers only think about business input; assembly is the framework's job.
🔀 Alternatives
① Fully manual assembly — maximum flexibility, maximum footguns;
② Templated (Jinja / Handlebars) — great for prompt-heavy workflows, loses type safety;
③ Pure middleware pipeline — every step as middleware; flexible but long debug chain.
3 Where does the tool loop stop? expand
🧪 Example
The Agent ships with an iteration cap that breaks the loop: 
# agent_framework/_agents.py
DEFAULT_MAX_ITERATIONS = 10

class Agent:
    def __init__(self, ..., max_iterations: int = DEFAULT_MAX_ITERATIONS):
        self.max_iterations = max_iterations

    async def run(self, input, ...):
        for i in range(self.max_iterations):
            resp = await self._client.get_response(...)
            if not _has_tool_calls(resp):
                return AgentResponse(...)
            await self._execute_tools(resp)
        # Cap hit: return a partial result with a reason
        return AgentResponse(..., terminated_reason="max_iterations")
Tune per agent: Agent(..., max_iterations=20).
❓ Why this matters
Uncapped loops = bill explosion: a model can re-call the same tool forever, deadlock between dependent tools, or be steered by prompt injection. Even normal usage needs a stop-loss.
✅ How MAF does it
Default DEFAULT_MAX_ITERATIONS ships a sane value, overridable per Agent; when it trips, the call returns a structured terminated_reason instead of raising — upper layers can choose to retry, escalate or surface an error.
🔀 Alternatives
① No limit — outright dangerous;
② Token-budget based — more economical, harder to implement;
③ Wall-clock timeout — protects latency-sensitive paths;
④ Human approval per iteration — most expensive, safest (finance/medical); also doable via Workflow human approval.
4 Streaming vs non-streaming internals expand
🧪 Example
Same Agent, two entry points: 
# Non-streaming: one full result
result: AgentResponse = await agent.run("Write a short autumn poem")
print(result.text)

# Streaming: AgentResponseUpdate chunks
async for update in agent.run_stream("Write a short autumn poem"):
    if update.text:
        print(update.text, end="", flush=True)
❓ Why this matters
① Time-to-first-token matters most for long answers;
② UX — non-streamed long answers feel like a 30-second freeze; streaming feels like a typewriter;
③ Early debugging / cancellation — streaming lets you spot drift early and abort.
✅ How MAF does it
Same Agent, same tools: run() returns a complete AgentResponse; run_stream() returns AsyncIterable[AgentResponseUpdate], emitting text, tool calls and thinking blocks as chunks — all over the same internal loop, so switching modes doesn't change your business code.
🔀 Alternatives
① Pure SSE push — simple protocol, you handle reconnect & heartbeats;
② WebSocket — bidirectional, better for live interaction;
③ Polling — broadest compatibility, worst UX;
④ Client-side buffering — reassemble chunks into final text on the client; MAF supports this too.
5 Error handling inside the loop expand
🧪 Example
Three classic failures: 
# 1) LLM-side error: 429 / 500 / timeout
   → ChatClient raises ChatClientError

# 2) Tool function raises
@tool
def get_weather(city: str) -> str:
    raise RuntimeError("weather API down")
   → Agent wraps it as FunctionResultContent(error=...),
     hands it back to the model to degrade or apologize

# 3) Tool execution timeout
   → middleware layer catches, writes a trace span
❓ Why this matters
Inside an agent loop, "retry / skip / abort / partial" can all be the right call — there's no silver bullet. The framework has to provide a structured, customizable failure model, or you'll either swallow errors silently or crash constantly.
✅ How MAF does it
Errors flow through the middleware pipeline (_middleware.py): users register retry policies, circuit breakers, fallbacks; tool exceptions become FunctionResultContent fed back to the model; unrecoverable failures surface on AgentResponse with a terminated_reason and original exception chain for structured upstream handling.
🔀 Alternatives
① try/except everywhere — fast to write, near-zero observability;
② Circuit breaker — protects downstream, watch for false trips;
③ Let-it-crash (Erlang style) — restart the agent on failure, rely on upstream retries — simple but costly.
✅ Key points
  • One run() = assemble messages → call LLM → (loop tools as needed) → return AgentResponse.
  • Tool calling is a loop, not one-shot: the model may request tools multiple times.
  • The streaming variant yields AgentResponseUpdate chunks that compose the full response.
💡 Design highlight
The loop is encapsulated in the framework: callers see only "input → output", while the think–act–think complexity is absorbed by the Agent — that's why it's calmer than raw LLM SDK calls.

04 · Messages & Content

Talking to a model is really passing a list of messages back and forth. MAF makes messages structured objects (Message) instead of bare dicts — type-safe, and able to carry tool calls, images and more.

✉️ Analogy
A Message is like an envelope: the outside states the sender's identity (role: user / assistant / system / tool), and inside you can place several content cards (contents: some text, an image, a tool call, a tool result…).

Three core types

TypeRoleFrom
Messageone message = role + contents_types.py
Roleidentity: "system"/"user"/"assistant"/"tool"_types.py
Contentunified content type, built via factory methods_types.py

Hand-built dicts vs structured messages

😣 Bare dicts

messages = [
  {"role": "system", "content": "You are a bot"},
  {"role": "user", "content": "hi"},
]
# typo-prone keys; tool calls by hand

🙂 Message objects

from agent_framework import Message
messages = [
  Message("system", "You are a bot"),
  Message("user", "hi"),
]
# type-safe, carries any Content

Message's second argument contents accepts a string (auto-converted to text), a Content object, or a list of them. Read the text via msg.text.

1 What can a Content hold? click to expand
🧪 Example
Content is a unified type; class methods create each kind:

05 · ChatClient & Creating Agents

A ChatClient is the vendor-agnostic "connect to a model" interface; an Agent adds a name, system instructions, tools and a loop on top. This lesson builds an Agent from a ChatClient and runs it with run.

🎧 Analogy
A ChatClient is like a walkie-talkie: it can talk to a channel (model) but has no persona. An Agent is the operator holding that walkie-talkie who has been briefed on duties (instructions) and tools — you talk to the operator, who gets the job done.

Two ways to create

A: Agent(client=…)

from agent_framework import Agent
agent = Agent(
  client=client,
  name="HelloAgent",
  instructions="You are friendly.",
)

B: client.as_agent(…)

agent = client.as_agent(
  name="HelloAgent",
  instructions="You are friendly.",
)
# equivalent, reads nicer

Both work; as_agent reads more fluently. Same Agent underneath.

Run it: blocking and streaming

non-streaming vs streaming
# non-streaming: full answer at once
result = await agent.run("What is the capital of France?")
print(result)

# streaming: tokens as they arrive
async for chunk in agent.run("Tell me a fun fact.", stream=True):
    if chunk.text:
        print(chunk.text, end="", flush=True)

One run(): without stream it returns a full AgentResponse; with stream=True it returns an async iterator yielding AgentResponseUpdate chunks.

🔬 Switching vendors
Replace FoundryChatClient with OpenAIChatClient, AnthropicChatClient, OllamaChatClient… and the Agent layer doesn't change at all. Each client comes from its provider package (Lesson 16).

3 Streaming internals click to expand
🧪 Example
async for chunk in agent.run("Write a poem", stream=True):
    print(f"type={chunk.type}")      # "text_delta" / "tool_call" / "final"
    print(f"text={chunk.text}")      # text delta for this chunk
    print(f"is_final={chunk.is_final}")  # whether last chunk
    
    if chunk.is_final:
        print(f"full_response={chunk.response}")  # complete AgentResponse
❓ Why this matters
Streaming responses aren't just "typewriter effect":
  • Lower perceived latency: time-to-first-token (TTFT) matters more than total duration.
  • Long outputs: generating hundreds or thousands of tokens, users can't wait for completion.
  • Early cancellation: user sees wrong direction, stops immediately (saves cost).
  • Real-time processing: parse while generating (e.g., live translation, code highlighting).
Just returning raw text stream isn't enough: need to know "tool call started", "final completion" events to update UI correctly.
✅ How MAF does it
MAF streams AgentResponseUpdate objects (see python/packages/core/agent_framework/_types.py):
  • type field: "text_delta" (text increment) / "tool_call" (tool invocation) / "final" (end).
  • text field: new text in this chunk.
  • is_final: True for last chunk; .response property holds complete AgentResponse.
  • Metadata: usage (token consumption), finish_reason (why stopped), etc.
Framework auto-accumulates text, parses tool calls, handles multi-turn loops; user just async for consumes.
🔀 Alternatives
  • OpenAI SDK: returns SSE event stream, user must manually parse delta, accumulate text, detect end.
  • Anthropic SDK: MessageStream object, many event types (content_block_start, content_block_delta…), steep learning curve.
  • LangChain: astream returns raw chunks, format depends on underlying LLM.
  • MAF unified Update object, abstracts vendor differences, high-level semantics ("text delta", "tool call", "done") clear.

💡 Design highlight
Streaming and non-streaming share one run(), toggled by a single stream flag. One mental model, no second API.

06 · Tools

Tools let an Agent not just "talk" but "do": fetch weather, read a database, call an API. Write an ordinary Python function, tag it with @tool, and the model can call it.

🧰 Analogy
The model is a smart brain with short arms: it knows "time to check the weather" but can't reach the thermometer. Tools are the handy instruments you hand it, each with a manual (function signature + docstring) it follows.

Define a tool

samples/01-get-started/02_add_tools.py
from typing import Annotated
from agent_framework import Agent, tool
from pydantic import Field

@tool(approval_mode="never_require")
def get_weather(
    location: Annotated[str, Field(description="The location to get weather for.")],
) -> str:
    """Get the weather for a given location."""
    return f"It's sunny in {location}."

agent = Agent(client=client, name="WeatherAgent",
    instructions="Use get_weather to answer.",
    tools=[get_weather])

result = await agent.run("What's the weather in Seattle?")

Three things happen automatically

1

Generate schema

A JSON Schema is built from the signature + Annotated[..., Field(description=…)] + docstring, and handed to the model.

2

Model decides to call

The model emits a function_call (function name + arguments) in its response.

3

Framework executes & feeds back

The Agent runs your function, appends the function_result, and lets the model continue.

⚠️ Approval mode
approval_mode="never_require" is just for sample brevity — in production use "always_require" to require human confirmation before a tool runs (especially for writes / spend).

🧪 Example
import httpx

# Sync tool (blocks event loop)
@tool(approval_mode="never_require")
def get_weather_sync(city: str) -> str:
    """Get weather (blocks event loop)."""
    resp = httpx.get(f"https://api.weather.com?q={city}")  # blocking!
    return resp.json()["temp"]

# Async tool (non-blocking)
@tool(approval_mode="never_require")
async def get_weather_async(city: str) -> str:
    """Get weather (async, doesn't block)."""
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"https://api.weather.com?q={city}")
        return resp.json()["temp"]

# Agent auto-handles: sync via run_in_executor, async via direct await
❓ Why this matters
Tools often do I/O:
  • HTTP requests: calling third-party APIs (weather, maps, payments).
  • Database queries: reading user info, order history.
  • File I/O: reading config, writing logs.
Synchronous I/O blocks the event loop: one tool call taking 2 seconds freezes the entire Agent for 2 seconds, can't handle other requests. Async I/O lets the event loop continue, multiple tool calls can execute concurrently (one waiting on network while another runs CPU tasks). Python's asyncio and .NET's Task both require async contagion — async all the way.
✅ How MAF does it
MAF's @tool supports both sync and async (see ToolDefinition.invoke in python/packages/core/agent_framework/_tools.py):
  • Sync tools: framework uses asyncio.to_thread (or run_in_executor) to run in thread pool, avoiding blocking.
  • Async tools: framework directly awaits, doesn't block event loop.
  • Auto-detection: inspect.iscoroutinefunction(...) determines if async.
  • Concurrent execution: multiple tool calls can use asyncio.gather for concurrency (future support for parallel tool calls).
Developers don't care about sync/async details; framework ensures efficient execution.
🔀 Alternatives
  • LangChain: @tool supports async, but AgentExecutor's sync/async paths separated, easy to get wrong.
  • OpenAI SDK: doesn't care if tools are sync/async, application layer handles it.
  • Sync only: simple but poor performance, Agent handling concurrent requests will block.
  • MAF transparent handling: write sync tools (simple) or async tools (efficient), framework auto-optimizes.

  • Feed back results: appends function_result to conversation history; model reads and decides: call more tools or give final answer.
  • Loop until done: max max_tool_rounds (default 10), prevents infinite loops.
Developers just define tools, pass them to Agent; scheduling and composition done by framework.
🔀 Alternatives
  • OpenAI parallel_tool_calls: supports returning multiple tool_calls at once, MAF will support in future (concurrent tool execution).
  • Anthropic tool_use blocks: one message can contain multiple tool_use, MAF already abstracts in Content.from_function_call.
  • LangChain ToolChain: must manually orchestrate tool call order (A → B → C), less flexible than letting model plan.
  • MAF auto-loop + model planning: provide tools, model composes them, framework ensures safe execution (approval + round limits).
✅ Key points
  • @tool turns a plain function into a model-callable tool; the schema is auto-generated.
  • Use Annotated[..., Field(description=…)] for params and a docstring for purpose.
  • Put tools in Agent(tools=[…]); execution + feedback is handled by the framework.
💡 Design highlight
"A function is a tool": you never hand-write JSON Schema — type hints and the docstring are the contract. Code and the model-facing description can't drift, because they're the same thing.

07 · Sessions & Memory

By default each run() is "amnesiac". To make an Agent remember, pass the same session (AgentSession) across calls. For longer-term memory, use a ContextProvider.

📒 Analogy
An AgentSession is a shared notebook: every turn writes into the same book, so next turn the model "remembers" by reading it. A ContextProvider is an assistant that quietly slips "relevant old memories / external knowledge" into the context before each answer.

Multi-turn: carry a session

samples/01-get-started/03_multi_turn.py
session = agent.create_session()

result = await agent.run(
    "My name is Alice and I love hiking.", session=session)

result = await agent.run(
    "What do you remember about me?", session=session)
# → remembers Alice, likes hiking

The whole trick: pass the same session into every run() and history accumulates. Omit the session and each call starts fresh.

Longer-term memory / external knowledge

🔬 ContextProvider
A session only accumulates within "this conversation". To remember user preferences across sessions, or to inject retrieved knowledge (RAG) before answering, use a ContextProvider — e.g. MemoryContextProvider stores memories in a searchable store and splices relevant entries into context before each run. (Memory stores / backends: Lesson 16 and the provider packages.)
1 With vs without session click to expand
🧪 Example
# Without session: each call is a new conversation (amnesiac)
result1 = await agent.run("I'm Alice")
result2 = await agent.run("What's my name?")
# → Model doesn't know; previous "Alice" is lost

# With session: remembers context
session = agent.create_session()
result1 = await agent.run("I'm Alice", session=session)
result2 = await agent.run("What's my name?", session=session)
# → Model answers "Alice"

# View session history
print(session.history)  # [Message("user", "I'm Alice"), Message("assistant", ...), ...]
❓ Why this matters
Many AI apps need context continuity:
  • Conversational UI: user asks "What's the weather?" → "Tomorrow?" → "Day after?", each relies on prior turns.
  • Task flows: user says "Book me a hotel" → model asks "Which city?" → "Seattle" → "Check-in date?", needs to maintain state.
  • Personalization: user says "I'm vegetarian", later conversations remember this.
If default is stateful (implicit global session), you get: different users' conversations mixed, tests hard to isolate, concurrent requests interfere. MAF chooses stateless as default, explicit session when needed.
✅ How MAF does it
AgentSession (see python/packages/core/agent_framework/_sessions.py):
  • Explicit creation: agent.create_session() returns a new session object.
  • Pass-through: pass the same session object to each run().
  • Auto-accumulation: after each run, user message + model reply (+ tool calls/results) auto-append to session.history.
  • No side effects: without session, run mutates no global state, fully stateless.
This design ensures concurrent safety (each user's session doesn't interfere), testability (each test has independent session), understandability (memory or not is obvious).
🔀 Alternatives
  • OpenAI Assistants API: uses thread_id to identify sessions, server-managed history. Pros: no client storage. Cons: can't debug locally, vendor switch requires refactor.
  • LangChain Memory: uses ConversationBufferMemory classes, must manually attach to Chain. Easy to forget to clear, causing history bloat.
  • Implicit global session: framework internally maintains session dict (user_id → history), simplifies API but concurrency-unsafe, hard to test.
  • MAF explicit session object: clear, safe, controllable.

4 Context window compaction click to expand

from agent_framework import (
    CompactionProvider,
    SlidingWindowStrategy,
    SummarizationStrategy,
    ContextWindowCompactionStrategy,

# Strategy A: sliding window (keep recent N groups, drop oldest)
strategy = SlidingWindowStrategy(keep_last_groups=20, preserve_system=True)

# Strategy B: summarization (LLM summarizes old messages; needs a client)
strategy = SummarizationStrategy(client=client, target_count=4)

# Strategy C: compact by context-window token budget (two-phase: tool-result eviction + truncation)
strategy = ContextWindowCompactionStrategy(
    max_context_window_tokens=128_000,
    max_output_tokens=16_384,
)

# Wrap the strategy in a CompactionProvider, inject as a context provider
compaction = CompactionProvider(before_strategy=strategy)
agent = Agent(
    client=client,
    context_providers=[compaction]
)

# As the conversation grows, the framework compacts before each run
session = agent.create_session()
for i in range(30):
    await agent.run(f"Message {i}", session=session)
    # → When over threshold the strategy kicks in: drop oldest groups or summarize
❓ Why this matters
Conversation history grows unbounded, problems:
  • Token limits: models have context window caps (e.g., GPT-4 128k tokens), exceeding causes errors or truncation.
  • Cost: input tokens also billed, longer history = more expensive each call.
  • Latency: sending and processing more tokens increases latency.
  • Relevance decay: 50 turns ago may be irrelevant to current question, but still occupies context.
Need auto-compaction strategies: control context size without losing key info.
✅ How MAF does it
MAF ships several compaction strategies (SlidingWindowStrategy / SummarizationStrategy / ContextWindowCompactionStrategy, see _compaction.py):
  • Sliding window: keep recent N messages, delete oldest (good for short-term conversations).
  • Summarization: summarize old messages into one system message ("Previously user mentioned…"), preserve semantics, reduce tokens.
  • Hybrid strategy: keep system messages (important instructions) + recent messages (current context) + summarize middle messages.
  • Auto-trigger: Agent checks history length before run, calls strategy to compact if over threshold.
  • Configurable: keep_last_groups, target_count, max_context_window_tokens and more.
Developers don't manually manage context; framework auto-optimizes.
🔀 Alternatives
  • LangChain ConversationSummaryMemory: calls LLM to generate summary after each turn, but expensive, timing inflexible.
  • Manual truncation: messages[-10:] keeps last 10, simple but loses early important info.
  • Vector retrieval: store history in vector DB, retrieve relevant snippets each time, but needs extra infrastructure.
  • MAF multiple strategies: simple cases use sliding window, complex use summarization, can also combine with ContextProvider for vector retrieval.
✅ Key points
  • Stateless by default; use AgentSession to carry multi-turn history.
  • agent.create_session() creates one; run(…, session=session) reuses it.
  • Cross-session / external knowledge → ContextProvider (e.g. MemoryContextProvider).
💡 Design highlight
Short-term history (Session) and long-term searchable memory (ContextProvider) are two layers: the former is a simple pass-through, the latter is pluggable. Use just Session for small needs, add a Provider for big ones — complexity is pay-as-you-go.

08 · Agent Internals

The Agent you use has two layers: the abstract BaseAgent at the bottom, and the concrete Agent on top. Understand them and you'll see how the framework drives an agent through its full loop.

🏗️ Analogy
BaseAgent is a job description ("you must take orders, run errands, deliver results"); Agent is the person on duty — reads the description, packs the toolkit, takes orders and runs errands in a loop until the task is done.

Two layers

AbstractBaseAgent
Defines the run() protocol and extension points (_agents.py:314). Every Agent must fulfil this "contract".
ConcreteAgent
Assembles instructions + messages + tools → calls ChatClient → tool loop → returns AgentResponse (_agents.py:1584).

What run() does inside

1

Build message list

Concatenate instructions (system) + session history + new input.

2

Inject ContextProviders

Splice long-term memory / external knowledge into the context.

3

Call ChatClient

Send messages + tool schemas to the LLM, get back a ChatResponse.

4

Tool loop

If the reply contains a function_call, execute the tool, append the result, loop to step 3.

5

Return

Loop ends; wrap into AgentResponse (or stream AgentResponseUpdate chunks).

1 What does BaseAgent define? expand
🧪 Example
BaseAgent (_agents.py:314) mandates run() (shared by streaming and non-streaming), create_session(), get_session(). Subclasses only implement these methods — the loop skeleton is in the base.
❓ Why this matters
Without a unified interface every Agent type would need its own calling protocol, and orchestrators couldn't be generic. The abstract base guarantees "any Agent can run()" — the foundation of polymorphism.
✅ How MAF does it
MAF uses the Template Method pattern: BaseAgent defines the skeleton, RawAgent / Agent implement in layers. This allows free extension without breaking the protocol.
🔀 Alternatives
LangChain uses the Runnable protocol (more generic but looser); AutoGen uses ConversableAgent (tighter coupling). MAF picks a "just right" abstraction level and avoids over-generalisation.

# _agents.py — RawAgent.run() core (simplified)

    return await self._prepare_run_context(
        messages=messages, session=session,
        tools=tools, options=options, ...)

        ctx = await _prepare_run_context()

        return await self._parse_non_streaming_response(ctx, response)
    return _run_non_streaming()

    ctx = await _prepare_run_context()
    stream_response = self._call_chat_client(ctx, stream=True)
    return self._parse_streaming_response(ctx, stream_response)
❓ Why this code matters
Three steps are clearly visible: ①prepare context → ②call ChatClient → ③parse response. Streaming and non-streaming share the same _prepare_run_context; they differ only in steps ②③. ✅ What _call_chat_client does
It directly calls self.client.get_response(messages=..., stream=..., options=...) — forwarding assembled messages, tool schemas and ChatOptions to the ChatClient. This is the boundary between Agent and ChatClient: Agent owns "assembly", ChatClient owns "communication".

Override _call_chat_client(): customise "how to call the model". Override _prepare_run_context(): customise "how to assemble messages". Add middleware: intercept without touching source. Three extension points, from coarsest to finest grain.
✅ Key points
  • BaseAgent (abstract) defines the protocol; Agent (concrete) implements assembly + loop.
  • run() = build messages → inject context → call ChatClient → tool loop → return.
  • Return types: non-streaming AgentResponse; streaming AgentResponseUpdate.
  • Real code: _prepare_run_context → _call_chat_client → _parse_response.
💡 Design highlight
The loop skeleton is owned by the base class; subclasses only plug in "how to call the model" — the classic Template Method pattern. Three extension points (_prepare_run_context / _call_chat_client / _parse_response) let you intervene at different granularities.

11 · Middleware

Middleware lets you add logging, retries, approvals and more without touching Agent or ChatClient source. MAF has three layers, each wrapping a different granularity.

🧅 Analogy
Middleware is an onion: the request passes through each layer from outside in, reaches the core execution, then the result passes back out. Each layer can act "on the way in" and "on the way out" (log, modify params, retry…).

Three middleware layers

AGENTAgentMiddleware
Wraps the entire agent.run() — the outermost layer. Uses AgentContext.
CHATChatMiddleware
Wraps each LLM call. Uses ChatContext.
FUNCFunctionMiddleware
Wraps each tool execution. Uses FunctionInvocationContext.

Unified signature

middleware template
from agent_framework import AgentMiddleware, AgentContext

class MyLoggingMiddleware(AgentMiddleware):
    async def process(self, context: AgentContext, call_next):
        print("before")
        await call_next()   # ← no arguments!
        print("after", context.result)

Key: await call_next() takes no arguments — it invokes the next layer or the final execution. The result lives on context.result.

1 Decorator shortcut expand
🧪 Example
Don't want a class? Use a decorator: 
from agent_framework import agent_middleware

@agent_middleware
async def my_log(context, call_next):
    print("before")
    await call_next()
    print("after")
Similarly @function_middleware and @chat_middleware.
❓ Why this matters
Class-based suits stateful middleware (e.g. counters); decorators suit simple stateless logic (e.g. logging). Both styles coexist so you pick the most concise one for your scenario.
✅ How MAF does it
@agent_middleware (_middleware.py:682) internally uses MiddlewareWrapper to convert the function into the class protocol — to the pipeline, both styles are completely equivalent.
🔀 Alternatives
Some frameworks only support class-based (verbose); others only function-based (hard to hold state). MAF supports both and unifies them into one protocol internally.
2 Execution order (onion model) expand
🧪 Example
Given middleware registered A → B → C, the execution order is: 
A.process() enters → "A before"
  B.process() enters → "B before"
    C.process() enters → "C before"
      ── core execution (call_next bottoms out) ──
    C.process() returns → "C after"
  B.process() returns → "B after"
A.process() returns → "A after"
Each middleware gets one chance before and one after await call_next().
❓ Why this matters
Understanding the onion model is essential for ordering middleware correctly: a logger that should "start first + finish last" belongs outermost; a retry interceptor belongs inner.
✅ How MAF does it
The pipeline (AgentMiddlewarePipeline, _middleware.py:847) builds the call_next chain via closure recursion: starting from the last middleware, each wraps the previous. Results are placed on context.result — no return-value passing needed.
🔀 Alternatives
Express.js uses linear next() (no "way out" phase); Django uses __call__ wrapping (similar but less intuitive). MAF's call_next() onion model is clearest — before and after live in the same function body, excellent code locality.

Each layer's context has different fields but a consistent structure: all have metadata (shared) and result (outcome). FunctionInvocationContext additionally provides add_tools() / remove_tools() methods for dynamic tool modification (takes effect next loop iteration).

4 Passing data between middleware expand
🧪 Example

❓ Why this matters
Middleware often need to cooperate: a timer records start time, a logger reads elapsed time. Global variables would cause interference between concurrent requests.
✅ How MAF does it

🔀 Alternatives
Python contextvars (more implicit, harder to debug); closure capture (only within same pipeline). The metadata dict is the most straightforward and debuggable.

# 2. Token-counting middleware (ChatMiddleware)

        usage = ctx.result.usage_details

# 3. Rate-limit middleware (ChatMiddleware)

        await self.semaphore.acquire()
        try:
            await call_next()
        finally:
            self.semaphore.release()
❓ Why this matters
These three cover the most common production needs: observability (logging), cost control (token counting), traffic management (rate limiting). They show what's best done before vs after call_next().
✅ How MAF does it
Logging goes in AgentMiddleware (whole-run level), token counting and rate limiting go in ChatMiddleware (per-LLM-call level) — three granularity levels let each middleware precisely intercept what it cares about.
🔀 Alternatives
AOP frameworks like aspectlib (too heavy); hook methods in the Agent class (not flexible enough). MAF's middleware pipeline is the standard cross-cutting concern solution.
✅ Key points
  • Three layers: AgentMiddleware (whole run) → ChatMiddleware (each LLM call) → FunctionMiddleware (each tool execution).
  • Unified signature process(self, context, call_next); await call_next() takes no args.
  • Class-based or decorator-based: @agent_middleware, @function_middleware, @chat_middleware.
💡 Design highlight
Three granularities × onion model: you can intercept "every LLM call" (ChatMiddleware) without touching tool execution, or intercept tool execution without touching LLM — concerns are fully separated.

12 · Workflows Engine

Workflows are MAF's graph execution engine: wire multiple steps (Executor) into a directed graph with Edges, built by WorkflowBuilder, driven by Workflow.run().

🗺️ Analogy
Think of a Workflow as a subway map: each station (Executor) does one thing, the tracks (Edges) decide where to go next. WorkflowBuilder draws the map; run() dispatches the train.

Core concepts

ConceptRoleSource
ExecutorA node in the graph; processes messages_workflows/_executor.py
EdgeA directed edge connecting two nodes_workflows/_edge.py
WorkflowBuilderChain API: add_edge/add_chain to build the graph_workflows/_workflow_builder.py
WorkflowContextHandle for sending messages / yielding output inside a node_workflows/_workflow_context.py

Minimal example

samples/01-get-started/07_first_graph_workflow.py
from agent_framework import Executor, WorkflowBuilder, WorkflowContext, executor, handler

class UpperCase(Executor):
    @handler
    async def to_upper(self, text: str, ctx: WorkflowContext[str]):
        await ctx.send_message(text.upper())

@executor(id="reverse")
async def reverse(text: str, ctx: WorkflowContext):
    await ctx.yield_output(text[::-1])

upper = UpperCase(id="upper")
wf = WorkflowBuilder(start_executor=upper) \
    .add_edge(upper, reverse).build()
events = await wf.run("hello")  # → "OLLEH"

✅ How MAF does it
The @executor decorator auto-wraps the function into a FunctionExecutor, sharing the same handler registry and message dispatch mechanism as class-based nodes. You can mix both styles in the same graph — class nodes and function nodes connect via edges freely.

LangGraph supports only function nodes (no class inheritance); Prefect only supports @task functions. MAF offers both — a more flexible choice.

🎼 Analogy
Orchestration patterns are like ensemble formats: Sequential is solos one after another, Concurrent is playing together, Handoff is passing the baton, Group Chat is a roundtable, Magentic is a conductor assigning parts.

from agent_framework.orchestrations import SequentialBuilder

workflow = SequentialBuilder(participants=[writer, reviewer]).build()

🔬 Key difference
Handoff: the current Agent explicitly decides "I can't do this, hand to X" — control flows unidirectionally. Group Chat: a selector function (or model) picks who speaks each turn; all Agents see the full chat history. Handoff suits expert routing; Group Chat suits debate / brainstorming.

18 · Writing Your Own Middleware

🧱 Analogy
Writing middleware is like adding a station to an assembly line: you can inspect products before the next station (logging), stamp labels after (billing), or send defects back for rework (retry) — without modifying the line itself.

Hands-on: retry middleware

custom ChatMiddleware
from agent_framework import ChatMiddleware, ChatContext

class RetryChatMiddleware(ChatMiddleware):
    def __init__(self, max_retries: int = 3):
        self.max_retries = max_retries

    async def process(self, context: ChatContext, call_next):
        for attempt in range(self.max_retries):
            try:
                await call_next()
                return
            except Exception:
                if attempt == self.max_retries - 1:
                    raise

Attach to an Agent: Agent(client=client, chat_middleware=[RetryChatMiddleware(3)]).

19 · Checkpointing, HITL & Durability

Production needs: save progress mid-run (checkpoints), human approval at critical steps (HITL), resume after crashes (durability). MAF makes all three first-class.

💾 Analogy
Checkpoints are game saves: save progress, crash, reload from save. HITL is an approval workflow: pause at a critical node, wait for a signature. DurableTask is cloud saves: saves aren't local — move to another machine and keep playing.

Checkpoints

Workflows auto-save at each superstep boundary. Default: InMemoryCheckpointStorage; swap to persistent storage (Redis, Cosmos) for production. After a crash, restart and resume from the latest save.

Human-in-the-Loop (HITL)

Tools can set approval_mode="always_require" to pause for human confirmation. At the workflow level, request_info lets a node pause, ask a question, and wait for a reply.

Without checkpoints, a crash in step 5 of a 10-step workflow means restarting from step 1. Wasted time and LLM tokens.
✅ How MAF does it
MAF auto-saves at superstep boundaries. InMemoryCheckpointStorage is zero-config for development.
🔀 Alternatives
Manual state serialization, database snapshots. MAF's checkpoint API is automatic and transparent.

Every protocol is an optional thin wrapper — Agent core logic stays unchanged. Start with Foundry hosting for a single Agent, add A2A for multi-Agent collaboration, then layer AG-UI for real-time UI. Adopt incrementally, not all at once.
🔀 Alternatives
All-custom REST APIs (most flexible but reinvents the wheel); GraphQL subscriptions (great for complex queries but overkill for Agent scenarios); gRPC streaming (high performance but limited ecosystem support).
✅ Key points
  • A2A: Agent-to-Agent protocol — A2AAgent (client) + A2AExecutor (server), with AgentCard discovery.
  • AG-UI: Agent-to-UI protocol — AgentFrameworkAgent wrapper + one-line FastAPI integration.
  • The two are orthogonal: A2A handles "inter-Agent", AG-UI handles "Agent → user". Use independently or together.
  • All protocols are optional thin layers — core Agent code remains unchanged.
💡 Design highlight
Four protocols (MCP / Foundry / A2A / AG-UI) cover every direction of Agent external communication: tool calls, cloud hosting, Agent interop, UI streaming. Each is an optional thin adapter — write Agent logic once, plug in whichever "communication socket" you need.
