每个箭头都对应你前面学过的一课：Provider（L16）接模型，工具 / 中间件（L06 / L18）增强单个 Agent，Builder（L12-13）把多个 Agent 编排起来，检查点（L19）让它能恢复。capstone 的价值就是看清这些零件如何正交组合——各自独立，又能拼在一起。

动手追踪：一次端到端的多 Agent 运行

把上面的"零件图"换成一次真实输入，端到端走一遍——看用户的一句话如何被编排装配、经过两个 Agent（其中一个还会调工具），最后收敛成一段完整对话。这条链路就是真实样例 sequential_agents.py 的运行轨迹。

1

用户给一句话

入口只有一行：await workflow.run("给一款平价电动自行车写条广告语")。这句 prompt 会成为整段共享对话的第一条 user 消息（第 4 课）。

2

编排装配（build 时已完成）

SequentialBuilder(participants=[writer, reviewer]).build() 早在运行前就把链路接好了：它在参与者之间插入适配节点（input-conversation → writer → to-conversation → reviewer → complete），把一段共享对话顺着这条链往下传。

3

Writer 跑，可能先调工具

writer 拿到 prompt，若需要先 web_search(...)——这正是第 10 课的工具循环：模型回 function_call → 框架执行工具 → 把 function_result 回灌 → 模型再作答。最后产出一条 assistant 消息，append 进共享对话。

4

对话往下传，串行交棒

框架把"到此为止的整段对话"（user + writer 的回复）作为 reviewer 的输入。这就是 SequentialBuilder 的本质：不是把孤立结果拼接，而是让一段对话顺序流过每个参与者。

5

Reviewer 跑

reviewer 读到 writer 的产出，给出审稿意见，同样 append 进对话。两个 Agent 都不知道自己身处一个 workflow——它们只是各自 run 了一次（第 5 课）。

6

收集结果

await workflow.run(...) 返回一个 WorkflowRunResult；result.get_outputs() 给出每个参与者的 AgentResponse，遍历 response.messages 就能拼出最终对话——user 的需求、writer 的广告语、reviewer 的点评，依次排好。

基于 samples/03-workflows/orchestrations/sequential_agents.py（简化）
import asyncio
from typing import Annotated, cast

from agent_framework import Agent, AgentResponse, tool
from agent_framework.openai import OpenAIChatClient
from agent_framework.orchestrations import SequentialBuilder
from pydantic import Field


@tool
def web_search(query: Annotated[str, Field(description="搜索关键词")]) -> str:
    """查一句话事实。"""
    return f"(stub) results for {query}"


async def main() -> None:
    client = OpenAIChatClient(model="gpt-4o")

    writer = Agent(
        client=client, name="writer",
        instructions="写一句精炼广告语，必要时调用 web_search。",
        tools=[web_search])
    reviewer = Agent(
        client=client, name="reviewer",
        instructions="审阅上一条 assistant 消息，给出简短改进意见。")

    # 编排：writer -> reviewer，二者共享同一段对话
    workflow = SequentialBuilder(
        participants=[writer, reviewer], output_from="all").build()

    result = await workflow.run("给一款平价电动自行车写条广告语")
    for output in result.get_outputs():
        response = cast(AgentResponse, output)
        for msg in response.messages:
            print(f"[{msg.author_name}] {msg.text}")


asyncio.run(main())

为什么这一课把前面全串起来了

这段不到 30 行的代码，其实是把前面每一课的产出物各取一件、拼在一起。Message（第 4 课）是 writer 和 reviewer 之间那段"共享对话"的原子；ChatClient → Agent（第 5 课）把一个模型句柄变成带人设的参与者；@tool（第 6 课 / 第 10 课）让 writer 能在动笔前查资料；SequentialBuilder（第 12 / 13 课）再把两个独立 Agent 接成一条有向工作流。

关键在"正交组合"：每个零件都不知道别的零件存在。writer 不知道自己身处一个 workflow；SequentialBuilder 不关心 writer 内部有没有工具；换 provider（第 16 课）、加中间件（第 18 课）、开检查点（第 19 课）都是在某一根正交轴上加东西，互不干扰。正因如此，复杂度才是"增量"而非"指数"——从 hello agent 到生产级多 Agent，每一步只加几行。

这也让调试和演进变得自然：想加可观测性？在某个 Agent 上挂一个 TimingMiddleware（第 18 课），workflow 一行不改。想让它崩溃后能续跑？给 builder 传一个 checkpoint_storage（第 19 课）。想从 OpenAI 切到本地 Ollama？只换 client 那一行（第 16 课）。capstone 的"完成感"不在于代码有多长，而在于你已经认识每一个零件，剩下的只是把它们摆在一起。

顺着这条思路往下走，扩展同样是"换零件"：把 SequentialBuilder 换成 ConcurrentBuilder，两个 Agent 就从串行交棒变成并行各写一版再汇总（第 13 课）；再加第三个参与者，只是往 participants 列表里多塞一个 Agent；想边跑边看输出，把 run 换成 run(stream=True) 即可（第 5 课 / 第 14 课）。每一种"升级"都不需要重写主干——这正是把前面 19 课学到的正交能力，一次性兑现的地方。

from agent_framework import Agent, tool
from agent_framework.openai import OpenAIChatClient
from agent_framework.orchestrations import SequentialBuilder
from agent_framework import InMemoryCheckpointStorage

# 工具
@tool
def web_search(query: str) -> str:
    """搜索网络"""
    return f"Results for {query}"

# 中间件
class LoggingMiddleware(ChatMiddleware):
    async def process(self, context, call_next):
        logger.info(f"Input: {context.messages}")
        await call_next()
        logger.info(f"Output: {context.result}")

# Agents
client = OpenAIChatClient(model="gpt-4o")
writer = client.as_agent(name="Writer",
    instructions="Write articles",
    tools=[web_search],
    middleware=[LoggingMiddleware()])

reviewer = client.as_agent(name="Reviewer",
    instructions="Review and improve")

# 工作流
storage = InMemoryCheckpointStorage()
workflow = SequentialBuilder(
    participants=[writer, reviewer],
    checkpoint_storage=storage
).build()

result = await workflow.run("Write about MAF")

Worked example: one end-to-end multi-agent run

Let's replace the "parts diagram" with one real input and trace it end to end — watching how a single user sentence gets assembled by the orchestration, passes through two Agents (one of which even calls a tool), and finally converges into a complete conversation. This path is exactly the run trace of the real sample sequential_agents.py.

1

The user gives one sentence

The entry point is a single line: await workflow.run("Write a tagline for a budget eBike"). That prompt becomes the first user message of the shared conversation (Lesson 4).

2

Orchestration assembly (done at build time)

SequentialBuilder(participants=[writer, reviewer]).build() wired the chain before the run even started: it inserts adapter nodes between participants (input-conversation → writer → to-conversation → reviewer → complete) and flows one shared conversation down that chain.

3

Writer runs, maybe calls a tool first

The writer gets the prompt and may first call web_search(...) — exactly the tool loop from Lesson 10: model returns a function_call → framework runs the tool → feeds back a function_result → model answers. It produces an assistant message appended to the shared conversation.

4

The conversation flows on — sequential hand-off

The framework passes "the whole conversation so far" (user + writer's reply) as the reviewer's input. That's the essence of SequentialBuilder: not stitching isolated results, but letting one conversation flow in order through each participant.

5

Reviewer runs

The reviewer reads the writer's output and gives feedback, also appended to the conversation. Neither Agent knows it lives inside a workflow — each simply run once (Lesson 5).

6

Collect the results

await workflow.run(...) returns a WorkflowRunResult; result.get_outputs() gives each participant's AgentResponse, and iterating response.messages reconstructs the final conversation — the user's ask, the writer's tagline, the reviewer's critique, in order.

based on samples/03-workflows/orchestrations/sequential_agents.py (simplified)
import asyncio
from typing import Annotated, cast

from agent_framework import Agent, AgentResponse, tool
from agent_framework.openai import OpenAIChatClient
from agent_framework.orchestrations import SequentialBuilder
from pydantic import Field


@tool
def web_search(query: Annotated[str, Field(description="search keywords")]) -> str:
    """Look up a one-line fact."""
    return f"(stub) results for {query}"


async def main() -> None:
    client = OpenAIChatClient(model="gpt-4o")

    writer = Agent(
        client=client, name="writer",
        instructions="Write one punchy tagline; call web_search if needed.",
        tools=[web_search])
    reviewer = Agent(
        client=client, name="reviewer",
        instructions="Review the previous assistant message; give brief feedback.")

    # orchestration: writer -> reviewer, sharing one conversation
    workflow = SequentialBuilder(
        participants=[writer, reviewer], output_from="all").build()

    result = await workflow.run("Write a tagline for a budget eBike")
    for output in result.get_outputs():
        response = cast(AgentResponse, output)
        for msg in response.messages:
            print(f"[{msg.author_name}] {msg.text}")


asyncio.run(main())

Why this lesson ties everything together

This sub-30-line program is really one item taken from every earlier lesson, snapped together. Message (Lesson 4) is the atom of the "shared conversation" passed between writer and reviewer; ChatClient → Agent (Lesson 5) turns a model handle into a participant with a persona; @tool (Lesson 6 / Lesson 10) lets the writer look things up before drafting; and SequentialBuilder (Lesson 12 / 13) wires two independent Agents into one directed workflow.

The key is orthogonal composition: no piece knows the others exist. The writer doesn't know it lives in a workflow; SequentialBuilder doesn't care whether the writer has tools inside; switching provider (Lesson 16), adding middleware (Lesson 18), enabling checkpoints (Lesson 19) each add something on a separate orthogonal axis, without interfering. That's why complexity is incremental, not exponential — from hello agent to production multi-agent, each step adds only a few lines.

It also makes debugging and evolution natural: want observability? Attach a TimingMiddleware (Lesson 18) to an Agent and the workflow doesn't change a line. Want it to resume after a crash? Pass a checkpoint_storage to the builder (Lesson 19). Want to switch from OpenAI to local Ollama? Change only the client line (Lesson 16). The capstone's sense of "done" isn't about how much code there is — it's that you now recognize every piece, and the rest is just arranging them.

Following that thread, extending it is also "swap a part": replace SequentialBuilder with ConcurrentBuilder and the two Agents go from serial hand-off to writing competing drafts in parallel, then merging (Lesson 13); add a third participant by dropping one more Agent into the participants list; want to watch output as it streams? Swap run for run(stream=True) (Lesson 5 / Lesson 14). None of these upgrades require rewriting the backbone — which is exactly where the orthogonal skills from the previous 19 lessons all pay off at once.

Checklist of gaps from demo to production.
❓ Why this matters
Demo code ≠ production code. Knowing the gaps prevents outages and cost overruns.
✅ How MAF does it
MAF provides all production building blocks: OTel integration, persistent storage packages, middleware for retries/logging/billing. No third-party glue needed.
🔀 Alternatives
Platform-specific solutions (Azure Monitor, Datadog). MAF is cloud-agnostic; OTel exports to any backend.
✅ Key points
  • Multi-Agent workflow = a few Agents + one Builder + .build().run().
  • Tools, middleware, checkpoints, HITL — all stackable.
  • From "hello agent" to "production multi-Agent" with minimal code increase.
💡 Design highlight
Complexity is incremental: single Agent → add tools → add orchestration → add checkpoints → add approvals, each step adds only a few lines. That's the "prototype to production" experience.

🧪 Self-test - think about the design

1. The capstone assembles provider / tools / middleware / orchestration / checkpointing. Which MAF design does that best illustrate?
  1. All the features are really one giant class
  2. These capabilities are orthogonal: independent with stable interfaces, so they compose like LEGO without changing each other's code
  3. They must be wired in a fixed order; swap one and everything breaks
  4. Composition only works in the enterprise edition
Show answer & explanation click to expand
Answer: B. Each brick is exposed via a stable interface (ChatClient, @tool, middleware=, *Builder, checkpoint_storage=). Orthogonal means composable: adding middleware doesn't affect orchestration, swapping providers doesn't affect tools. The capstone makes that visible.
2. In the writer → reviewer SequentialBuilder workflow, how does checkpointing get wired in?
  1. Manually save inside each Agent's run()
  2. Checkpointing must be wrapped in a separate with block
  3. Pass storage to SequentialBuilder(participants=[…], checkpoint_storage=storage); the workflow auto-saves at superstep boundaries
  4. Sequential workflows don't support checkpointing
Show answer & explanation click to expand
Answer: C. Checkpointing is a Builder parameter; the orchestration layer owns saving, and the Agent need not know about persistence. That's layered composition: the Agent "thinks", the Builder handles "orchestration + saving" - separate concerns that don't leak into each other.
