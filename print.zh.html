01 · Agent Framework 是什么

Microsoft Agent Framework（MAF）是一个用 Python 和 .NET 编写的开源框架， 帮你把"大语言模型（LLM）"接进真实应用，并编排成能干活的 Agent 和多 Agent 工作流。 它不替你训练模型，而是负责模型周边的所有管道，并面向生产环境。

🔌 生活类比
把大语言模型想成一台很强但很孤立的发动机：它能输出文字，却不知道你的数据库、 不会自己调用工具，不同厂商的接口还都不一样。MAF 就是那套标准化的"传动系统 + 仪表盘 + 配件接口"—— 让你用同一套代码驱动任何品牌的发动机，把它接到工具、记忆、其他 Agent 上，还能在生产里监控、重启、审批。

它到底解决什么问题？

直接调用某个厂商的 SDK 当然能跑，但真实应用里你很快会撞上这几类麻烦，正是 MAF 要替你抹平的：

痛点没有框架时MAF 的做法
厂商锁定换模型要重写一大片调用代码统一的 ChatClient + Agent，换厂商基本只改一行
对话拼装手动拼 role/content 的字典结构化的 Message / Role / Content
调用工具自己解析模型要调哪个函数、传什么参@tool 自动生成 schema + 解析 + 执行
多步 / 多 Agent手写"想—做—再想"循环和协作逻辑Agent 循环 + 图式 Workflows 编排
上生产自己搞监控、持久化、人工审批内置 OpenTelemetry、检查点、人在环、托管

最小的一个 Agent 长什么样

samples/01-get-started/01_hello_agent.py最小示例
from agent_framework import Agent
from agent_framework.foundry import FoundryChatClient
from azure.identity import AzureCliCredential

client = FoundryChatClient(
    project_endpoint="https://your-project.services.ai.azure.com",
    model="gpt-4o", credential=AzureCliCredential(),
)
agent = Agent(
    client=client, name="HelloAgent",
    instructions="You are a friendly assistant. Keep your answers brief.",
)

result = await agent.run("What is the capital of France?")
print(result)

三步：选一个 ChatClient（连到某个模型）→ 包成一个 Agent（给名字和系统指令）→ run 一句话。 换厂商？把 FoundryChatClient 换成 OpenAIChatClient 即可，其余不动。

1 它和 LangChain / AutoGen / Semantic Kernel 什么关系？ 点击展开
❓ 一句话定位
MAF 是微软把 Semantic Kernel（企业级、强类型、连接器丰富）和 AutoGen（多 Agent 对话与研究探索）合并演进而来的统一框架， 目标是"从原型到生产"一条路走到底，且 Python 与 .NET 双实现、API 对齐。
✅ 它的取舍
既要 LangGraph 那样的图式编排（可控、可恢复），又要 AutoGen 那样的多 Agent 协作， 还把可观测性 / 持久化 / 审批做成一等公民——这就是"生产级"的含义。
✅ 关键要点
  • MAF = ChatClient（连模型）+ Agent（循环）+ Tools（工具）+ Workflows（编排）+ 生产能力。
  • 它不训练模型，负责模型周边的全部管道；Python 和 .NET 双实现。
  • 定位：Semantic Kernel + AutoGen 的统一继任者，从原型直达生产。
💡 设计亮点
把"换模型只改一行"做成默认体验：ChatClient 是厂商无关的统一抽象， Agent / 工具 / 工作流全部构建在它之上，于是可移植性从第一行代码就免费获得。

02 · Monorepo 全景

MAF 是一个 monorepo：一个仓库里同时放着 Python 和 .NET 两套实现，外加文档、声明式 Agent 和 schema。理解了目录结构，你就有了一张源码导航地图。

🏢 生活类比
把仓库想成一座办公楼：core 是地基与承重墙（所有人都依赖）， 各 provider 包是不同楼层的部门（OpenAI 部、Anthropic 部……）， lab 是顶楼的实验室（前沿但不稳定）。Python 楼和 .NET 楼并排而立，户型一致。

顶层结构

PY/.NETpython/ · dotnet/
两套实现并列，API 对齐。本教程聚焦 python/。
DOCSdocs/ · declarative-agents/ · schemas/
设计决策记录（ADR）、声明式 YAML Agent、JSON schema。

Python 这边怎么分层

COREpackages/core → agent_framework
核心抽象：Agent / Message / tool / 中间件 / Workflows，以及内置 OpenAI / Azure OpenAI 支持。
PROVIDERSpackages/{foundry, anthropic, ollama, …}
各厂商 / 集成包，在 core 之上扩展具体的 ChatClient 与连接器。
LABpackages/lab
实验性功能：基准测试、强化学习、研究项目。
你想找去哪里
核心类型与 Agent 实现python/packages/core/agent_framework/
公共 API（__all__）core/agent_framework/__init__.py
新手样例python/samples/01-get-started/
.NET 对照实现dotnet/src/Microsoft.Agents.AI*/
🔬 细节 · 懒加载
provider 子模块（如 agent_framework.azure）用 __getattr__ 做懒加载：只有真正 import 时才拉起对应依赖，让 core 保持轻量。
✅ 关键要点
  • 一个仓库、两套对齐实现：python/ 与 dotnet/。
  • Python：core 是地基，provider 包按需扩展，lab 装前沿。
  • 读源码先看 core/agent_framework/__init__.py 的 __all__。
💡 设计亮点
core 不依赖任何具体厂商：厂商代码全部下沉到独立 provider 包， 通过懒加载接入。于是核心 API 稳定，新增厂商不动地基。

03 · 一次 run() 的生命周期

你写的只是 await agent.run("…") 一行，但底下发生了一串事。 看懂这条生命周期，后面所有"内部源码"课都会变得轻松。

🍽️ 生活类比
Agent 像一位餐厅服务员：你点单（输入）→ 他把你的话连同"店规"（instructions）整理成标准工单（消息） → 递进后厨（ChatClient → LLM）→ 如果厨师说"需要先去仓库取货"（工具调用），服务员就去取（执行工具）再把结果回递 → 直到厨师出菜（最终回答），服务员端给你（AgentResponse）。

一次 run 的完整数据流

1

你的输入

字符串或一组 Message，连同会话历史一起进来。

2

Agent 组装

把 instructions（系统提示）+ 历史 + 新输入 + 可用 tools 拼成一次请求。

3

ChatClient 调用

厂商无关接口把请求发给具体 LLM（Foundry / OpenAI / …），拿回 ChatResponse。

4

要调工具吗？

若响应里含 function_call，Agent 执行对应函数，把 function_result 追加进消息，再回到第 3 步。

5

收敛与返回

当模型不再要工具，循环结束，得到 AgentResponse（流式则是一串 AgentResponseUpdate）。

🌍 宏观理解
这就是经典的 Agent 循环（think → act → observe）：模型"想"，框架替它"做"（调工具）， 把"观察"喂回去，直到任务完成。你只调用一次 run()，循环在内部自动跑完。
1 多轮对话时历史从哪来？ 点击展开
🧪 示例
把同一个 会话（session）传给连续的 run，历史会自动累积： 
from agent_framework import Agent
agent = Agent(client=client, instructions="…")
session = agent.create_session()
await agent.run("我叫小明", session=session)
await agent.run("我叫什么？", session=session)  # 记得"小明"
（会话与记忆见第 07 课，这里只需知道历史是"会话"携带的。）
✅ 关键要点
  • 一次 run() = 组装消息 → 调 LLM →（按需循环调工具）→ 返回 AgentResponse。
  • 工具调用是循环，不是一次性：模型可以多次要工具。
  • 流式版本逐块返回 AgentResponseUpdate，最终拼成完整响应。
💡 设计亮点
循环被封装在框架里：调用方只看到"输入→输出"，而"想—做—再想"的复杂度被 Agent 吸收， 这正是它比裸调 LLM SDK 省心的根源。

04 · 消息与内容

和模型对话，本质是来回传递一串消息。MAF 把消息做成结构化对象 Message，而不是裸字典——类型更安全，还能携带工具调用、图片等多种内容。

✉️ 生活类比
一条 Message 像一个信封：信封上写着寄件人身份（role： user / assistant / system / tool），信封里可以装多张内容卡片（contents： 一段文字、一张图、一次工具调用、一份工具结果……）。

三个核心类型

类型作用来自
Message一条消息 = role + contents_types.py
Role身份："system"/"user"/"assistant"/"tool"_types.py
Content统一内容类型，用工厂方法构造_types.py

手拼 dict vs 结构化消息

😣 裸字典

messages = [
  {"role": "system", "content": "你是助手"},
  {"role": "user", "content": "你好"},
]
# key 容易拼错，工具调用要手搓

🙂 Message 对象

from agent_framework import Message
messages = [
  Message("system", "你是助手"),
  Message("user", "你好"),
]
# 类型安全，可带多种 Content

Message 的第二个参数 contents 接受字符串（自动转成文本内容）、 Content 对象，或它们的列表。读文本用 msg.text。

1 Content 能装哪些东西？ 点击展开
🧪 用工厂方法构造
Content 是统一类型，用类方法创建不同种类： 
Content.from_text("一段文字")
Content.from_data(data=..., media_type="image/png")  # 图片/二进制
Content.from_uri(uri="https://…", media_type="image/png")
Content.from_function_call(...)      # 模型要调工具
Content.from_function_result(...)    # 工具执行结果
所以一条 Message 可以图文混排，也能承载工具调用 / 结果。
✅ 关键要点
  • 对话 = 一串 Message；每条 = role + contents。
  • Role 有四种：system / user / assistant / tool。
  • Content 是统一类型，用 from_text/from_data/from_function_call… 构造。
💡 设计亮点
把"文本、图片、工具调用、工具结果"统一成一种 Content，靠 type 字段区分。 消息结构因此既简单又可扩展——新增一种内容不破坏老代码。

05 · ChatClient 与创建 Agent

ChatClient 是"连到某个模型"的厂商无关接口；Agent 在它之上加了 名字、系统指令、工具和循环。本课讲怎么从 ChatClient 造出 Agent，并用 run 跑起来。

🎧 生活类比
ChatClient 像对讲机：能和某个频道（模型）通话，但不带"人设"。 Agent 像拿着对讲机、并被交代了岗位职责（instructions）和工具的值班员——你对值班员说话，他负责完成任务。

两种创建方式

方式 A：Agent(client=…)

from agent_framework import Agent
agent = Agent(
  client=client,
  name="HelloAgent",
  instructions="You are friendly.",
)

方式 B：client.as_agent(…)

agent = client.as_agent(
  name="HelloAgent",
  instructions="You are friendly.",
)
# 等价，更顺手

两种都行；as_agent 读起来更顺。底下都是同一个 Agent。

跑起来：run 与流式

非流式 vs 流式
# 非流式：一次拿到完整回答
result = await agent.run("What is the capital of France?")
print(result)

# 流式：逐块拿到 token
async for chunk in agent.run("Tell me a fun fact.", stream=True):
    if chunk.text:
        print(chunk.text, end="", flush=True)

同一个 run()：不传 stream 返回完整 AgentResponse； 传 stream=True 返回一个异步迭代器，逐块给 AgentResponseUpdate。

🔬 换厂商
把 FoundryChatClient 换成 OpenAIChatClient、 AnthropicChatClient、OllamaChatClient……Agent 那层一行都不用改。 各 client 来自对应 provider 包（见第 16 课）。
✅ 关键要点
  • ChatClient = 连模型（厂商无关）；Agent = ChatClient + 人设 + 工具 + 循环。
  • 创建：Agent(client=…) 或 client.as_agent(…)，二选一。
  • run() 默认完整返回；run(stream=True) 逐块流式返回。
💡 设计亮点
流式与非流式共用一个 run()，靠一个 stream 开关切换返回形态。 调用心智统一，省掉两套 API。
第二部分 · 用户视角

06 · 工具 Tools

工具（Tool）让 Agent 不只是"会说"，还能"会做"：查天气、读数据库、调 API。 你写一个普通 Python 函数，用 @tool 一标，模型就能调用它。

🧰 生活类比
模型像个聪明但手短的大脑：它知道"该查天气了"，但自己摸不到温度计。 工具就是你递给它的一件件趁手家伙，并附上说明书（函数签名 + docstring），它照着说明书使用。

定义一个工具

samples/01-get-started/02_add_tools.py
from typing import Annotated
from agent_framework import Agent, tool
from pydantic import Field

@tool(approval_mode="never_require")
def get_weather(
    location: Annotated[str, Field(description="The location to get weather for.")],
) -> str:
    """Get the weather for a given location."""
    return f"It's sunny in {location}."

agent = Agent(client=client, name="WeatherAgent",
    instructions="Use get_weather to answer.",
    tools=[get_weather])

result = await agent.run("What's the weather in Seattle?")

三件事自动发生

1

生成 schema

从函数签名 + Annotated[..., Field(description=…)] + docstring 自动生成 JSON Schema，交给模型。

2

模型决定调用

模型在回答里产出一个 function_call（函数名 + 参数）。

3

框架执行并回灌

Agent 调用你的函数，把 function_result 追加进对话，再让模型继续。

⚠️ 审批模式
approval_mode="never_require" 仅为示例图省事——生产中应使用 "always_require"，在工具执行前要求人工确认（尤其是写操作 / 花钱的操作）。
✅ 关键要点
  • @tool 把普通函数变成模型可调用的工具，schema 自动生成。
  • 用 Annotated[..., Field(description=…)] 给参数写说明，docstring 写函数用途。
  • 把工具放进 Agent(tools=[…])；执行 + 回灌由框架完成。
💡 设计亮点
"函数即工具"：你不用手写 JSON Schema，类型注解和 docstring 就是契约。 代码与给模型的描述永远同步，因为它们本来就是同一份。

07 · 会话与记忆

默认情况下，每次 run() 都是"失忆"的。要让 Agent 记住上文， 就把同一个 会话（AgentSession）传给连续的调用。更长期的记忆，则交给 ContextProvider。

📒 生活类比
AgentSession 像一本共享记事本：每轮对话都写进同一本，下一轮模型翻看它就"记得"。 ContextProvider 则像一位助理，在每次回答前把"相关的旧记忆 / 外部知识"悄悄塞进上下文。

多轮对话：带上会话

samples/01-get-started/03_multi_turn.py
session = agent.create_session()

result = await agent.run(
    "My name is Alice and I love hiking.", session=session)

result = await agent.run(
    "What do you remember about me?", session=session)
# → 记得 Alice、喜欢徒步

关键就一点：把同一个 session 透传给每次 run()，历史便自动累积。 不传 session，则每次都是全新对话。

更长期的记忆 / 外部知识

🔬 ContextProvider
会话只在"本轮对话"内累积。要跨会话记住用户偏好，或在回答前注入检索到的知识（RAG），用 ContextProvider：例如 MemoryContextProvider 把记忆存进可检索的库， 每次 run 前自动把相关条目拼进上下文。（记忆库 / 各存储后端见第 16 课与各 provider 包。）
✅ 关键要点
  • 无状态是默认；用 AgentSession 携带多轮历史。
  • agent.create_session() 建会话，run(…, session=session) 复用它。
  • 跨会话 / 外部知识用 ContextProvider（如 MemoryContextProvider）。
💡 设计亮点
把"短期对话历史"（Session）和"长期可检索记忆"（ContextProvider）分成两层： 前者简单透传，后者可插拔。需求小就只用 Session，需求大再加 Provider，复杂度按需付费。
第三部分 · 内部源码

08 · Agent 内部

你用的 Agent 背后有两层：最底层是抽象基类 BaseAgent，上面是具体类 Agent。 了解这两层，才看得懂框架如何"驱动"一个 Agent 跑完整个循环。

🏗️ 生活类比
BaseAgent 像一份岗位说明书（"你要能接单、能跑、能交付"）， Agent 则是真人上岗——读说明书、准备工具箱、接单后反复跑腿，直到任务完成。

两层结构

抽象BaseAgent
定义 run() 协议与扩展点（_agents.py:314）。 所有 Agent 必须实现这份"合同"。
具体Agent
组装 instructions + 消息 + 工具 → 调 ChatClient → 工具循环 → 返回 AgentResponse（_agents.py:1584）。

run() 内部做了什么

1

构建消息列表

把 instructions（system）+ 会话历史 + 新输入拼起来。

2

注入 ContextProvider

把长期记忆 / 外部知识塞进上下文。

3

调用 ChatClient

把消息 + 工具 schema 发给 LLM，拿回 ChatResponse。

4

工具循环

若回复含 function_call，执行工具、追加结果、再回第 3 步。

5

返回

循环结束，包装成 AgentResponse（或逐块 AgentResponseUpdate）。

1 BaseAgent 定义了哪些接口？ 点击展开
🔬 核心协议
BaseAgent 规定了 run()（非流式 + 流式共用）、 create_session()、get_session() 等。 子类只需关注"怎么组装消息、怎么调模型"——循环骨架已由基类搭好。
✅ 关键要点
  • BaseAgent（抽象）定义协议；Agent（具体）实现组装 + 循环。
  • run() = 构建消息 → 注入上下文 → 调 ChatClient → 工具循环 → 返回。
  • 返回类型：非流式 AgentResponse；流式 AgentResponseUpdate。
💡 设计亮点
循环骨架由基类掌控，子类只插入"怎么调模型"这一块——经典的模板方法模式。 这意味着你可以自定义 Agent 行为而不破坏循环逻辑。
第三部分 · 内部源码

09 · ChatClient 内部

BaseChatClient 是"和某个 LLM 通话"的厂商无关协议。 你平时只碰 get_response()，厂商做的事全藏在 _inner_get_response() 里。

📞 生活类比

10 · 工具调用内部

@tool 在用户那一课看起来很"魔法"——这里拆开看它内部做了什么： 从 Python 函数到 JSON Schema，再到模型来回调用的完整闭环。

🔧 生活类比
写一个工具 = 在工具架上挂了一把锤子：你写好锤子的使用说明（类型注解 + docstring）， 框架自动打印成规范卡片（JSON Schema）贴在锤子旁边，模型读卡片决定"我要用这把"，框架帮它拿起来锤。

完整闭环

1

你写函数 + @tool

框架用 FunctionTool（_tools.py:240）包装它。

2

生成 JSON Schema

从 Annotated[..., Field(description=...)] + 返回类型自动构建 schema。

3

Schema 发给模型

ChatClient 在请求里带上所有工具的 schema（tools 字段）。

4

模型返回 function_call

回复的 Content 里有一个 function_call（函数名 + JSON 参数）。

5

框架反序列化 + 执行

JSON 参数 → Python 对象 → 调用你的函数 → 拿到返回值。

6

function_result 回灌

返回值打包成 function_result Content，追加进消息，回到第 3 步让模型继续。

1 FunctionTool 里装了什么？ 点击展开
🔬 核心属性
FunctionTool 持有：原始函数引用、生成的 JSON Schema、 approval_mode（调用前是否需要人工审批）、函数名、描述。 @tool 装饰器（_tools.py:1145）是构造 FunctionTool 的语法糖。
✅ 关键要点
  • @tool → FunctionTool → JSON Schema → 随请求发给模型。
  • 模型回 function_call → 框架执行 → function_result 回灌 → 再让模型继续。
  • 整个循环在 Agent 内部自动跑，调用方无感。
💡 设计亮点
类型注解就是 schema——不存在"代码改了但忘记更新 schema"的问题， 因为它们在同一份源码里。这是"函数即工具"哲学的核心。

11 · 中间件 Middleware

中间件让你不改 Agent / ChatClient 源码就能横切地加入日志、重试、审批等逻辑。 MAF 有三层中间件，每层包裹不同粒度的操作。

🧅 生活类比
中间件像洋葱圈：请求从外到内穿过每一层，到达核心执行后，结果再从内到外穿出来。 每一层都可以在"进去前"和"出来后"做事（记日志、改参数、重试……）。

三层中间件

AGENTAgentMiddleware
包裹整个 agent.run()——最外层。用 AgentContext。
CHATChatMiddleware
包裹每次 LLM 调用。用 ChatContext。
FUNCFunctionMiddleware
包裹每次工具执行。用 FunctionInvocationContext。

统一签名

中间件模板
from agent_framework import AgentMiddleware, AgentContext

class MyLoggingMiddleware(AgentMiddleware):
    async def process(self, context: AgentContext, call_next):
        print("before")
        await call_next()   # ← 无参！
        print("after", context.result)

重点：await call_next() 不传任何参数——它调用下一层或最终执行。 执行结果挂在 context.result 上。

1 也可以用装饰器写法 点击展开
🧪 函数式中间件
不想写类？用装饰器： 
from agent_framework import agent_middleware

@agent_middleware
async def my_log(context, call_next):
    print("before")
    await call_next()
    print("after")
同样有 @function_middleware 和 @chat_middleware。
✅ 关键要点
  • 三层：AgentMiddleware（整个 run）→ ChatMiddleware（每次 LLM 调用）→ FunctionMiddleware（每次工具执行）。
  • 统一签名 process(self, context, call_next)；await call_next() 无参。
  • 可用类写法，也可用 @agent_middleware 等装饰器。
💡 设计亮点
三层粒度 × 洋葱模型：你可以只拦截"每次 LLM 调用"（ChatMiddleware）而不碰工具执行， 或只拦截工具执行而不碰 LLM——关注点彻底分离。

12 · Workflows 工作流引擎

Workflows 是 MAF 的图执行引擎：把多个步骤（Executor） 用边（Edge）连成有向图，由 WorkflowBuilder 构建、Workflow.run() 驱动。

🗺️ 生活类比
把 Workflow 想成地铁线路图：每个站（Executor）做一件事， 铁轨（Edge）决定下一站去哪。WorkflowBuilder 画图，run() 发车。

核心概念

概念作用源码
Executor图中的一个节点，处理消息_workflows/_executor.py
Edge连接两个节点的有向边_workflows/_edge.py
WorkflowBuilder用 add_edge/add_chain 构建图_workflows/_workflow_builder.py
WorkflowContext节点内发消息/输出的句柄_workflows/_workflow_context.py

最小示例

samples/01-get-started/07_first_graph_workflow.py
from agent_framework import Executor, WorkflowBuilder, WorkflowContext, executor, handler

class UpperCase(Executor):
    @handler
    async def to_upper(self, text: str, ctx: WorkflowContext[str]):
        await ctx.send_message(text.upper())

@executor(id="reverse")
async def reverse(text: str, ctx: WorkflowContext):
    await ctx.yield_output(text[::-1])

wf = WorkflowBuilder(start_executor=UpperCase(id="upper")) \
    .add_edge(UpperCase(id="upper"), reverse).build()
events = await wf.run("hello")  # → "OLLEH"
1 @handler vs @executor 有什么区别？ 点击展开
🔬 两种写法
@handler 标记类方法（在 Executor 子类里）， @executor 标记独立函数（自动包成 FunctionExecutor）。 功能一样，选哪个看你喜不喜欢写类。
✅ 关键要点
  • Workflow = Executor（节点）+ Edge（边）组成的有向图。
  • WorkflowBuilder 用链式 API 构图；.build() 得到 Workflow。
  • 节点通过 ctx.send_message() 传数据、ctx.yield_output() 输出最终结果。
💡 设计亮点
消息驱动：节点之间传递的是"消息"而非函数调用返回值—— 这意味着节点天然支持异步、fan-out/fan-in，且可在边上加条件/开关。

13 · 编排模式

当你需要多个 Agent 协作，MAF 提供五种现成的编排模式—— 不用手写调度逻辑，选一个 Builder、传入参与者，.build() 就行。

🎼 生活类比
编排模式像乐团编制：Sequential 是依次独奏，Concurrent 是齐奏， Handoff 是接力棒传递，Group Chat 是圆桌讨论，Magentic 是指挥家调度全局。

五种模式

模式Builder一句话
SequentialSequentialBuilderAgent A 做完 → Agent B 接着做
ConcurrentConcurrentBuilderAgent A 和 B 同时做，汇总结果
HandoffHandoffBuilderAgent A 主动把任务"交接"给 B
Group ChatGroupChatBuilder多个 Agent 在群聊中轮流发言
MagenticMagenticBuilder有一个"指挥官"分派子任务给各 Agent

最简用法

Sequential 示例
from agent_framework.orchestrations import SequentialBuilder

workflow = SequentialBuilder(participants=[writer, reviewer]).build()
result = await workflow.run("Write a poem about the sea")
1 Handoff 和 Group Chat 有什么区别？ 点击展开
🔬 关键差异
Handoff：当前 Agent 显式决定"我做不了，交给 X"，控制权单向传递。 Group Chat：一个 selector 函数（或模型）每轮选谁发言，所有 Agent 看到完整群聊记录。 Handoff 更适合专家流转，Group Chat 更适合辩论 / 头脑风暴。
✅ 关键要点
  • 五种编排：Sequential / Concurrent / Handoff / Group Chat / Magentic。
  • 全部来自 agent_framework.orchestrations，选 Builder → 传参与者 → .build()。
  • 底层都是 Workflow 图——编排是高级糖。
💡 设计亮点
编排模式 = 预置拓扑的 Workflow：你用 Builder 声明意图，框架帮你画出正确的图。 需要更复杂的拓扑？直接用 WorkflowBuilder 手画。

18 · 写自己的中间件

第 11 课讲了中间件是什么；本课教你写一个自己的——从零到能用。

实战：重试中间件

自定义 ChatMiddleware
from agent_framework import ChatMiddleware, ChatContext

class RetryChatMiddleware(ChatMiddleware):
    def __init__(self, max_retries: int = 3):
        self.max_retries = max_retries

    async def process(self, context: ChatContext, call_next):
        for attempt in range(self.max_retries):
            try:
                await call_next()
                return
            except Exception:
                if attempt == self.max_retries - 1:
                    raise

挂到 Agent 上：Agent(client=client, chat_middleware=[RetryChatMiddleware(3)])。

1 三层中间件分别怎么挂？ 点击展开
🧪 挂载方式
Agent(middleware=[…]) 挂 AgentMiddleware； Agent(chat_middleware=[…]) 挂 ChatMiddleware； Agent(function_middleware=[…]) 挂 FunctionMiddleware。 多个中间件按列表顺序从外到内排列。
✅ 关键要点
  • 继承 *Middleware，实现 process(self, context, call_next)。
  • await call_next() 无参；结果在 context.result。
  • 用 Agent(middleware=…, chat_middleware=…, function_middleware=…) 挂载。
💡 设计亮点
中间件是组合式的：重试、日志、审批各自独立实现，按需拼装，互不干扰。

19 · 检查点 · 人在环 · 持久化

生产环境需要：跑到一半能存盘（检查点）、关键操作人工审批（人在环）、 挂了能续跑（持久化）。MAF 把这三件事做成一等公民。

💾 生活类比
检查点像游戏存档：进度存下来，挂了从存档恢复。 人在环像审批流：到关键节点暂停，等人签字再继续。 DurableTask 像云存档：存档不在本地，搬到另一台机器也能续玩。

检查点（Checkpoint）

Workflow 在每个 superstep 边界自动存档。默认用 InMemoryCheckpointStorage； 生产换成持久化存储（如 Redis、Cosmos）。崩溃后重启，从最近存档恢复。

人在环（HITL）

工具可设置 approval_mode="always_require"，执行前暂停等人确认。 工作流层面也有 request_info 机制：节点暂停、发问、等回答再继续。

1 DurableTask 是什么？ 点击展开
🔬 持久化执行
packages/durabletask 把工作流跑在 Durable Task Framework 上： 状态持久化到外部存储，支持跨进程恢复和长时间等待（比如等人审批几小时）。 配合 Azure Functions 可做无服务器部署。
✅ 关键要点
  • 检查点：Workflow superstep 自动存档，崩溃可恢复。
  • 人在环：工具 approval_mode + 工作流 request_info。
  • 持久化：DurableTask 包让状态存到外部，支持跨进程恢复。
💡 设计亮点
生产能力不是插件，是框架的一部分：检查点、审批、持久化都在核心 API 里， 而不是你自己拼第三方库。

  • 从"hello agent"到"生产级多 Agent"，代码增量很小。
💡 设计亮点
复杂度是增量的：单 Agent → 加工具 → 加编排 → 加检查点 → 加审批，每一步只增加几行代码。 这就是"从原型到生产"的体验。
